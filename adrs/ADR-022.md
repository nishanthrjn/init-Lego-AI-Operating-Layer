# ADR-022 — Provider-neutral structured output for Model chat

Status: Proposed — 2026-10-08. Implemented offline by the MODEL-STRUCTURED-OUTPUT-1
slice (local validation pending). Acceptance is the LegoAI platform
maintainer's decision. Depends on ADR-002, ADR-014, ADR-017, ADR-019 and
ADR-021.

Scope: an optional, provider-neutral requirement on a Model chat request that
the reply be one JSON document matching a bounded schema, plus a binding
capability fact and fail-closed routing. Default chat is unchanged. Agent
contracts and Agent output parsing are unchanged.

## 1. Context

- ADR-017 chose bounded text output for the generic one-step Agent, with "no
  JSON/schema machinery".
- ADR-021 accepted a raw or exactly-fenced JSON document for engineering
  Agents. It deliberately deferred provider-native structured output
  (Option C) as a Core/Model decision. That would change `ChatRequest`, the
  adapters and routing, and it needs a defined answer for providers without
  the feature.
- The sufficiency hardening design (FORGEAI-ANALYST-SUFFICIENCY-HARDENING-DESIGN-1)
  recorded structural failures on legitimate inputs. Disposition values were
  outside the enum, and disposition/request combinations were incoherent. Both
  are constraints a schema can express at generation time.
- `ChatRequest` carried only messages. There was no way to state a
  structured-output requirement without an options bag, which the Model
  contract forbids.

## 2. Decision

1. **Request.** `ChatRequest` gains `response_format:
   StructuredResponseFormat | None = None`. `None` is ordinary text chat,
   byte-for-byte unchanged on the wire.
2. **Schema.** `StructuredResponseFormat(schema: JsonObject)` is a typed,
   immutable, closed subset of JSON Schema, derived from current structured
   Agent results:
   - an object with closed properties (always `additionalProperties: false`)
     and `required`;
   - a string with optional `enum`, `maxLength` and nullability;
   - an array with `items` and optional `maxItems`.

   It has no `$ref`, remote references, recursion, numbers, booleans or
   annotations. Fixed bounds (`StructuredOutputLimits`):
   - depth 6;
   - 32 properties per object and 128 nodes in total;
   - 32 enum values of at most 128 characters each;
   - `maxLength` up to 65,536 and `maxItems` up to 256;
   - a canonical serialized schema of at most 16 KiB.

   Unsupported constructs fail at construction. `json_schema()` returns a
   fresh canonical object, and `digest()` is the SHA-256 of its canonical
   encoding.
3. **Capability.** `ModelBinding.structured_output: bool = False` is a fact
   about the admitted binding, never authority.
   - The host derives it: built-in Ollama bindings declare it, because their
     adapter maps the requirement; OpenAI-compatible bindings do not yet.
   - `TrustedModelContribution.structured_output` (default False) lets an
     operator declare it for a contributed `ModelPort` that genuinely honors
     the requirement.
   - Model names are never used to infer it.
4. **Routing fails closed.** Routing is unchanged: exact profile matching, one
   candidate resolves, otherwise NO_MATCH or AMBIGUOUS, and there is no
   preference or fallback. In routed chat, a request with `response_format`
   whose resolved binding does not declare the capability is refused before
   any call. It settles as FAILED with effect NONE and category
   `VALIDATION_ERROR` (terminal). It is never dropped, downgraded to text,
   retried or rerouted. An explicitly configured incapable binding is never
   substituted.
5. **Adapter backstops.** Adapters without support refuse a structured request
   with `ModelPreflightError` (no request sent), rather than ignoring it. This
   applies to the OpenAI-compatible adapter and the `FixedModel` double.
6. **Ollama mapping.** The Ollama adapter sends the canonical schema as the
   chat request's `format` value only when a requirement is present. The
   provider's reply is returned as text exactly as before.
7. **No parsing in Core.** Core never parses the reply into objects. Consumers
   remain authoritative for parsing, domain construction and invariants.
   Provider enforcement improves first-attempt shape only.
8. **Agents.** The generic Agent boundary still returns text, and
   `AgentDefinition` is unchanged. An Agent adopting a schema is a separate,
   versioned Agent decision (planned as H3).

## 3. Alternatives

- **Provider options bag** (`dict` passed through). Rejected: it breaks the
  Model contract's no-options-bag rule and leaks provider vocabulary.
- **A separate `structured_chat` Port operation.** Rejected: one chat
  semantic with an optional requirement is enough. A new operation would
  duplicate the effect mapping and governance path.
- **Silently ignoring the requirement on incapable providers.** Rejected: it
  is an invisible downgrade that hides model behavior.
- **Falling back to another binding.** Rejected: routing has no fallback, and
  adding one would change ADR-019 selection semantics.
- **Full JSON Schema.** Rejected: unbounded complexity and an uneven provider
  subset.

## 4. Consequences and compatibility

- **Callers:** additive and backward compatible. `ChatRequest(messages)` and
  every existing caller behave exactly as before.
- **Providers:** only the built-in Ollama adapter supports it. Its behavior
  under a given Ollama version is **not yet live-qualified**; a separate,
  authorized compatibility probe is required. The contract is intentionally
  compatible with OpenAI-style JSON-schema response formats, but that adapter
  is not implemented or qualified here.
- **Unsupported capability:** fail closed at routing, with an adapter
  refusal as a backstop.
- **Versioning:** an additive Core contract change. No capability-offer
  version change: the chat offer semantics are unchanged for callers who do
  not opt in.

## 5. Security boundary

Structured output constrains syntax and shape only. It does not widen
grants, bypass authorization, change evidence disclosure or effect
semantics, or make structured content trusted. Capability metadata is never
an authorization input, and authorization is identical with or without a
requirement. Safe diagnostics may record whether a requirement was present,
the schema digest and the binding capability. They never record prompts,
raw output or credentials.

## 6. Relationship to earlier ADRs

- **ADR-017:** amended only for model transport. A caller may request a
  provider-enforced structured reply, while the generic Agent output remains
  validated text.
- **ADR-019:** binding selection is unchanged. The capability is an added
  binding fact.
- **ADR-021:** resolves its deferred Option C for callers that request it.
  ADR-021's decoder and validators remain authoritative and unchanged.

## 7. Revisit

Revisit if:
- a second adapter (for example OpenAI-compatible) needs support;
- live probes show a provider ignoring or partially honoring the schema;
- a consumer needs a construct outside the subset (numbers, booleans);
- capability negotiation beyond a single fact becomes necessary.
