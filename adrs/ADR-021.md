# ADR-021 — JSON document representation for engineering Agent outputs

Status: Proposed — 2026-10-02. Awaiting the maintainer's decision. No code has
been changed. Depends on ADR-002, ADR-017 and ADR-018.

Scope: how `legoai-engineering` Agents turn a model's reply text into the
JSON document their existing parsers validate. No Core, Kernel, Model, Agent
runtime or canonical contract change.

## 1. Context

`legoai-engineering` has three structured-output Agents: `RepositoryAnalyst`
(M8.1), `IndependentReviewer` (M8.2) and `CodingAgent` (M8.3). Each private
`_parse` function calls `json.loads(output, object_pairs_hook=_unique_object)`
directly on the model's reply text:

| Agent | Parse site | Exceptions mapped to "output invalid" |
| --- | --- | --- |
| `RepositoryAnalyst` | `analyst/api.py`, `_parse` | `ValueError`, `TypeError`, `RecursionError`, `WorkspaceError` |
| `IndependentReviewer` | `reviewer/api.py`, `_parse` | `ValueError`, `TypeError`, `RecursionError` |
| `CodingAgent` | `coding/api.py`, `_parse` | `ValueError`, `TypeError`, `RecursionError`, `WorkspaceError` |

**What is shared, and what is not:**
- All three privately duplicate the same helpers: `_unique_object`, `_object`,
  `_array` and `_string`.
- No shared abstraction owns structured-output decoding.
- ADR-017 deliberately keeps the Core Agent runtime at "bounded nonblank UTF-8
  text rather than JSON/schema machinery": `AgentOutputContract` validates
  only size, emptiness and UTF-8.
- JSON structure is therefore owned by each engineering Agent. All three
  instruct the model to "Return only JSON" (Analyst: "only a JSON object").

**Current behavior:**
- A raw JSON reply is parsed.
- A reply wrapped in a Markdown code fence fails at `json.loads`. The Agent
  then returns its `OUTPUT_INVALID` status (Analyst: its output-invalid
  result).

## 2. Evidence

Live measurement: ForgeAI-LQ1, schema-2 report.
- **Model and environment:** `qwen2.5-coder:7b` (digest `sha256:dae161e2…f4364`),
  Ollama 0.35.0, CPU only.
- **Fixtures:** `forgeai-lq1` revision 1, hidden revision 1, N = 3, so 12 runs.
- **Code:** ForgeAI commit `3bc4b8f7`, with no runtime changes.

**Coding Agent (12 calls):**
- 11 were `response_not_json`. All 11 had `markdown_fence = true`,
  `json_parse_succeeded = false` and `output_limit_hit = false`, at
  1,264–2,157 bytes.
- The one reply without a fence was `valid`.

**Independent Reviewer (1 call):** `response_not_json`, with
`markdown_fence = true` and `json_parse_succeeded = false`.

**Observation quality:**
- 13 calls observed, all delivered.
- 0 classifier disagreements, 0 unavailable observations, no anomalies.
- Every category agreed with the runtime's own verdict.

**Downstream:**
- The one valid proposal (`temperature-units`, rep 3) passed Ruff, mypy,
  pytest and the hidden acceptance tests.
- That run still failed with `REVIEW_OUTPUT_INVALID`, because the Reviewer
  fenced its reply.
- No Ruff or pytest failure occurred in this run, and no rework was reached.

**Therefore:** all 12 structured-output failures in this run were the same
representation-level failure: Markdown-fenced replies rejected by a
raw-JSON-only parser. Two distinct Agents (Coding, Reviewer) show it, so the
Rule of Two is met inside `legoai-engineering`.

**Earlier live measurements** (llama3.2, qwen2.5-coder 3b and 7b, schema 1)
showed 27 of 36 Coding calls `PROPOSAL_INVALID`. Those reports cannot say
why; this ADR does not claim they were fenced.

**Limits of the evidence:**
- One model, one machine and N = 3.
- The fence's language label was not recorded.
- The `RepositoryAnalyst` was not exercised live.
- It says nothing about whether models produce *semantically* valid outputs
  once the fence is accepted.

## 3. Decision question

Should engineering Agents keep requiring a literal raw JSON reply, or accept
exactly one narrowly defined Markdown-fenced JSON document, with every
existing schema and semantic validation unchanged?

## 4. Alternatives

**A. Keep raw-JSON-only; mitigate with model choice.** Rejected as the sole
response.
- Raw-only is not more secure. A fenced document with a strict grammar
  carries exactly the same bytes for validation.
- Two Agents fail the same way, and the qwen2.5-coder family is
  coding-specialized. A model change does not address it.

**B. Accept one narrowly defined fenced JSON document.** **Chosen** (§5).
- It addresses exactly the observed failure.
- It is provider-neutral and deterministic.
- It leaves every validator unchanged.

**C. Provider-native structured output** (a provider-neutral requirement
mapped to, for example, Ollama's `format`). Not now.
- It changes generic contracts: `ChatRequest` or `AgentDefinition`,
  `ModelPort` adapters and routing.
- It needs a defined behavior for providers without the feature (fail,
  fall back or ignore), and provider-specific capability metadata.
- That is a Core/Model decision under ADR-017 and ADR-014, far broader than a
  representation mismatch at one package's parser.
- The current evidence does not require it. It also would not remove the
  need for semantic validation.

**D. Prompt-only change** ("do not use Markdown fences"). Not chosen as the
fix.
- The instructions already say "Return only JSON", and the model fenced
  anyway in 11 of 12 Coding calls.
- A prompt change is also a model-facing behavior change. It would invalidate
  comparison with the recorded baselines, and it remains probabilistic.
- It may be assessed separately later. It is not part of this decision.

**E. Output repair or extraction** (search prose for braces, take the first
JSON-looking span, retry or ask a model to repair). Rejected.
- It is unbounded, ambiguous with several candidates, and can turn untrusted
  prose into accepted structure.
- It hides model behavior from evaluation, and retry or repair adds effects
  and cost.
- Nothing in the evidence requires it.

## 5. Decision

`legoai-engineering` structured-output Agents accept a reply in exactly one
of two representations:
- one raw JSON document; or
- one Markdown code fence that encloses one JSON document and nothing else.

A private, pure, shared decoder maps the reply text to the JSON document
text. The Agents' existing `json.loads(..., object_pairs_hook=_unique_object)`
call and every existing validator then run **unchanged**, on that text.

The decoder only recognizes an outer envelope. It never parses JSON, builds
domain values, repairs, searches or retries.

## 6. Accepted representations

Let `T` be the reply with leading and trailing JSON whitespace (space, tab,
LF, CR) removed.

1. **Raw.** `T` does not start with three backticks. The decoder returns the
   reply unchanged. This is today's behavior, byte for byte.
2. **Fenced.** `T` has at least three lines, split on LF (a trailing CR on a
   line is ignored for the fence lines only), and:
   - its **first line** is exactly ` ``` ` or ` ```json `: three backticks,
     then the label `json` or no label, and nothing else (no spaces, no other
     text);
   - its **last line** is exactly ` ``` `;
   - the decoder returns the lines between them, unchanged and joined with LF,
     as the document text.

The document text then goes to the existing parser. `json.loads` requires
exactly one JSON value, surrounded only by JSON whitespace.

## 7. Rejected representations

Everything else stays invalid, with the existing output-invalid status. All
of the following are rejected:

| Reply | Why it is rejected |
| --- | --- |
| Prose before or after the fence | `T` neither starts nor ends with a fence line, so it reaches `json.loads` and fails |
| Fence label other than `json` or none (`JSON`, `jsonc`, `python`, ` ```json5 `), or text after the label | The opening line does not match |
| JSON on the fence line (` ```json {...} `) or a single-line fence | The opening line does not match, or there are fewer than three lines |
| Two fences, or nested fences | The inner fence lines remain in the document text and are not valid JSON |
| Empty fence | The document text is empty |
| Malformed JSON, two JSON documents, or JSON plus trailing text inside a fence | `json.loads` rejects them ("Extra data" or syntax error) |
| Markdown prose containing inline JSON | It is not a fence envelope; no search is performed |
| Duplicate keys, wrong fields, and schema, path, operation, content-limit, decision or semantic violations | Rejected by the **unchanged** parsers and validators, exactly as today |

The fenced form cannot carry a document whose own lines begin with backticks.
JSON strings cannot contain raw newlines, so a valid JSON document never has
such a line. Content containing ` ``` ` inside a JSON string is unaffected.

## 8. Validation order

Per Agent call, unchanged except for step 2:

1. Agent runtime: the `AgentOutputContract` check (nonblank, UTF-8, at most
   `max_bytes`) on the **whole reply**. This is unchanged, so the size bound
   still covers the fence.
2. **New:** the decoder maps the reply to document text (raw passes through
   unchanged).
3. The existing `json.loads` with duplicate-key rejection.
4. The existing exact field, type, array-bound, path, target, operation,
   content, narrative and decision validation, and the domain constructors.

## 9. Ownership and placement

**Owner:** one private module in `legoai-engineering`, for example
`legoai_engineering._json_document` with a function
`json_document(reply: str) -> str`.
- It follows the existing private shared-helper precedent
  (`legoai_engineering._authority`, ADR-018 addendum).
- It is not public API, and it is not exported.

**Why this owner:**
- **Not Core** (`legoai.execution.agent`, `AgentOutputContract`). ADR-017
  keeps the Agent runtime text-only. The consumers are engineering Agents
  only. Moving JSON representation into Core would reverse that decision
  without a non-engineering consumer.
- **Not a provider adapter.** Fencing is a property of the reply text, not
  the transport. Placing it in the Ollama adapter would make the engineering
  contract provider-specific.
- **Not each Agent privately.** Three copies of the same grammar could drift,
  and two Agents already show the failure.
- **All three engineering Agents adopt it**, including the `RepositoryAnalyst`,
  which has no live evidence of its own. One package should have one
  representation contract for one shared instruction ("Return only JSON").
  Leaving one Agent raw-only would make the same reply valid for two Agents
  and invalid for the third.

**Unchanged:**
- the per-Agent `_unique_object`, `_object`, `_array` and `_string` helpers;
- all `_parse` logic;
- consolidating those helpers is not part of this decision.

## 10. Provider independence

- The decoder takes a provider-neutral `str`: the content the Agent runtime
  already validated.
- It reads no provider, model or transport metadata. It has no Ollama branch.
- It behaves identically for any future `ModelPort` adapter.
- No `format` or provider option is added anywhere.

## 11. Security and failure semantics

**Determinism:**
- The decoder is total and pure: same input, same output.
- It needs no I/O and allocates at most one copy of the reply, within the
  existing output bound.

**What it does not do:** it does not repair, search, retry, call a model or
coerce a schema, and it accepts no candidate other than the single enclosed
document.

**Statuses and effects:**
- The decoder adds no new error type or status. Failures surface exactly as
  today, as `OUTPUT_INVALID` or the Analyst's output-invalid result.
- Model effects, `ExecutionResult`, attribution, the Agent runtime and
  ForgeAI's sequencing and fail-closed behavior are untouched.

**Trust:** accepting the fence does not raise trust in the content. The
document is still untrusted model output, and it is validated exactly as a
raw reply is.

## 12. Compatibility

| Reply | Before | After |
| --- | --- | --- |
| Raw valid JSON | accepted | accepted (identical bytes reach the parser) |
| Fenced (`json` or no label) valid JSON, exact envelope | output invalid | **accepted** |
| Everything else | output invalid | output invalid (same status) |

This is a **backward-compatible widening** of the accepted *representation*.
The *schema* and *semantics* are unchanged.

| Item | Change |
| --- | --- |
| **AgentDefinition versions** (`coding-agent`, `independent-reviewer`, repository analyst) | **Unchanged.** Instructions, model requirement and output contract (what the model is told) do not change. Attribution equality checks are unaffected. |
| **Public APIs** | **Unchanged:** `CodingAgent.propose`, `IndependentReviewer.review`, `RepositoryAnalyst.analyze`, all values and statuses. |
| **Behavior** | Changes for consumers that relied on fenced replies being rejected. No known consumer depends on that rejection. It is recorded here and in the Engineering README (package `0.1.0.dev0`; no release exists). |
| **Evaluation** | LQ1 measurements before and after are **not comparable** for `PROPOSAL_INVALID` or `REVIEW_OUTPUT_INVALID`. The LQ1 harness must mirror the new stage (§13). Its report schema moves to `forgeai-lq1-report/3`, because `response_not_json` changes meaning. Historical reports are not rewritten. |

## 13. Testing and qualification plan

Acceptance tests are defined before implementation.

**Decoder unit tests (private module):**
- **Raw:** a raw document is returned unchanged, including leading and
  trailing whitespace.
- **Accepted:** ` ```json `, an unlabeled fence, CRLF line endings, and
  whitespace before or after the envelope.
- **Rejected, returned unchanged so the parser fails as today:**
  - prose before or after the fence;
  - an unknown label, `JSON`, text after the label, or JSON on the fence line;
  - a single-line fence, a missing closing fence, or a closing line with text.
- **Rejected after decoding** (parser or `json.loads` fails):
  - two fences, nested fences, an empty fence;
  - malformed JSON, two documents, JSON plus trailing text.

**Agent suites (M8.1, M8.2 and M8.3, through each public API):**
- Raw valid output stays accepted, with identical results.
- Fenced valid Coding, Reviewer and Analyst output is accepted. The result
  equals the raw case: same proposal, review or analysis values.
- Every rejected form above yields the existing output-invalid status.
- Inside a fence, these are still rejected:
  - duplicate keys and schema-invalid JSON;
  - an invalid path, an untargeted path, a wrong operation;
  - content over its limit;
  - a review whose decision contradicts its blocking findings.
- An output over `max_bytes` is still rejected by the runtime contract,
  whether fenced or raw.
- Model effect and attribution are unchanged, and there are no extra model
  calls (no retry).

**Architecture tests:**
- Update the engineering import allowlist for the new private module.
- The decoder imports only the standard library: no `legoai.reference`, no
  provider names, no Ollama branch.
- Core is not modified.

**Regressions:**
- the full Engineering suite (including the CR-2b/CR-3 validators);
- Core Agent, Model and routing tests;
- ForgeAI-1/2/3 validators;
- `validate_forgeai_lq1.py`, including the LQ1.2 phases.

**LQ1 harness update (evaluation-only, same slice):**
- The classifier mirrors the decoder stage.
- It adds a closed `representation` feature (`raw`, `fenced`, `none`) and a
  `fence_label` feature (`json`, `none`, `other`).
- The report schema moves to 3.
- Every existing agreement, privacy and non-interference test still passes
  against the new runtime. Agreement means no `classifier_disagreement` for
  fenced valid replies.

**Live follow-up** (maintainer, after local qualification):
- Rerun the same `qwen2.5-coder:7b` LQ1 measurement: same fixture revision,
  hidden revision and N = 3.
- Describe the change in failure *shape* only, with no threshold and no
  leaderboard.
- Expect new failure classes (checks, review decisions, rework) to become
  visible. Do not expect general success.

## 14. Non-goals

This decision does not include:
- prompt changes or examples;
- provider-native structured output or Ollama `format`;
- output repair, JSON search or retry;
- a Core or Agent-runtime JSON facility;
- consolidating the per-Agent parsing helpers;
- context-window or output-token settings;
- check-failure rework;
- weaker Ruff, mypy or pytest;
- hidden-test changes;
- target discovery (M8.5), M8.4, Workflow, Team or model routing.

## 15. Consequences

**Benefits:**
- It removes the single observed representation blocker for the Coding and
  Reviewer Agents, without changing what they validate.
- One private grammar replaces three implicit raw-only assumptions.

**Effect on evaluation:** later LQ1 measurements can reach checks, review and
rework, which have barely been measured live. It does **not** imply ForgeAI
will succeed: semantic validity, check quality and review behavior remain
unmeasured.

**New obligations:**
- The engineering package's accepted representation is now a documented
  contract that future engineering Agents must reuse.
- The LQ1 harness must track the decoder.

## 16. Revisit triggers

Revisit this decision if any of these occurs:
- Live diagnostics show a material share of replies in a form this decoder
  rejects: another label, prose around the fence, or JSON inside prose. The
  first response is measurement, not wider tolerance.
- A non-engineering package needs the same representation (a second package
  consumer). That would justify a shared owner outside `legoai-engineering`,
  through its own ADR.
- A provider-native structured-output requirement is proposed for other
  reasons (Option C). It would complement this decoder, not replace the
  validators.
- Fence acceptance is linked to any security or validation regression.
