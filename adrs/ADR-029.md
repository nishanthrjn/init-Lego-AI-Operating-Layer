# ADR-029 — Role-specific model bindings and admission

Status: Proposed

Date: 2026-10-30

Review: LEGOAI-ROLE-MODEL-BINDINGS-DESIGN-REVIEW-1

BASE: `7da850c089df8e1e845a2205fc3309a042695a8f`

## Context

ForgeAI currently composes its coder and reviewer against one governed host
and the same `engineering-reasoning` requirement. The evaluation v2 and v3
results motivate separately qualifying roles, but neither evaluation admits
a model for one role under a retrospective rule. Their final verdicts stand.

Role configuration must not confer execution, disclosure, credential or
Plugin authority. Model outputs remain data. Deterministic approval, mutation,
check and review boundaries remain application-owned.

The verified facts, file-and-symbol change proposals, alternatives and
acceptance criteria are in the
[design review](../planning/LEGOAI-ROLE-MODEL-BINDINGS-DESIGN-REVIEW-1.md).
This ADR proposes a direction; it does not authorize implementation or execution.

## Proposed decision — Option C

Use Option A first: ForgeAI composes one governed host per role, with one
selected binding in each host. Keep the current Engineering requirement
profile initially; the application maps distinct coder and reviewer roles to
their respective hosts. Do not add a compatibility alias, implicit fallback,
per-call provider choice or live reload.

Keep Option B, a multi-binding host, conditional on a second independent
consumer needing the same host semantics or demonstrated costs that justify
changing the host contract. Do not build a speculative shared routing facade
as part of Option A.

### Authority and lifecycle

- Each role host owns its execution contexts, grants, evidence and selected
  model lifecycle. Contexts must never cross host boundaries. Application
  factories create destination-role contexts with explicit correlation.
- ForgeAI retains one workspace guard and one proposal approval/mutation
  story. Reviewer reads use their own authorized boundary. Separate model
  hosts do not create a second mutation authority.
- Preserve aggregate run limits of four model calls, two applies, two check
  batches and two reviews, as well as per-host capacity. Execute sequentially
  on the owning thread and event loop.
- Remote roles require independent credential provisions and per-binding
  disclosure admissions. Show each provider's actual payload classes and
  obtain explicit default-no operator consent before any relevant call.
- Attribute outputs and failures to the role, selected binding, provider,
  model and execution evidence; never report credentials or raw provider text.

### Configuration and admission

Propose one bounded, closed-schema operator configuration for role bindings,
covering supported replay, local and remote adapters. Configuration selects
an existing supported adapter; it never loads arbitrary code or grants authority.

Introduce an application-owned, versioned role-quality admission register
through a later slice. Records bind exact provider/model/role, frozen evidence,
instruction and request settings, review authority, expiry and rule version.
Start with no admissions. A fresh preregistered per-role evaluation and separate
admission review are required; existing v3 results cannot be reclassified into
admissions. Pair-level workflow qualification remains a separate gate.

Unattended remote operation additionally requires a separate purpose-bound
Model credential decision and batch disclosure/admission authority. Define
custody, grant scope, rotation/expiry, revocation, reconciliation and unattended
operator authorization first. No credential store is designed here.

## Alternatives and consequences

Option A preserves the existing host boundary and contains the first change
inside ForgeAI composition, at the cost of duplicated host resources,
credential prompts and cross-host attribution work. It requires an explicit
split of coder/reviewer context creation and read authority, not just opening
a second host.

Option B centralizes captured role selection but expands Core composition,
catalog admission, remote-plane dispatch and embedding semantics. DocuMind,
ForgeAI, evaluation harnesses and shared Generative Media composition paths
need compatibility review. Its extra complexity is unjustified without an
independent consumer requirement. Option C keeps that migration possible
without paying for it now.

Changing Engineering definition profiles later changes pinned source files
and makes v3 verification fail at that new HEAD by design. Historical manifests
must not be rewritten. Record a reproduction commit before such a change.

## Acceptance and follow-up gates

Follow the ordered slices and validator gates in D6 of the design review:
accept the design; implement local/replay role composition; qualify attended
remote composition; add the role-quality register; preregister and run fresh
per-role evaluation; qualify local batches; resolve remote batch authority and
the separate credential decision. Conditional Core work has its own upstream
acceptance gate.

Offline controls must demonstrate foreign-context rejection, role-specific
routing and reads, unchanged aggregate budgets, exact disclosure attribution,
default-no consent, refusal of unadmitted roles and unchanged legacy behavior.
Provider and model execution require separate operator authorization.

Local documentary validation is pending. No production change, model
admission, implementation authorization or independent security sign-off is
claimed by this review.
