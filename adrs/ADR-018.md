# ADR-018 — Repository Analyst composition in Engineering

Status: Proposed; implemented under the maintainer's scoped M8.1 instruction.
M8.1 locally qualified; canonical ADR status remains Proposed. Depends on ADR-002,
ADR-017 and M6.5. Reviewed before M8.2: ownership, optional dependency direction,
authorization before disclosure and trusted composition are durable decisions.
The implementation details illustrate these decisions rather than replace them.

## Decision

Place the repository-specific request, bounded evidence, analysis values and
composition in `legoai_engineering.analyst`. An optional `analyst` extra depends
on the existing `legoai-reference` distribution. The base Engineering install
keeps zero runtime dependencies. Core does not import Engineering. There is no
new distribution, third-party runtime dependency or change to generic Agent or
Model contracts.

Use two deterministic phases. Trusted composition authorizes selected reads and
model disclosure against an explicit M2 workspace and exact path allowlist.
It obtains complete bounded files through RepositoryWorkspacePort. The Analyst
then calls the existing M7 runtime once using `engineering-reasoning`, and validates
a closed JSON analysis schema plus exact evidence-member path references.

The private read composition uses existing Governance evaluation before each
read and before releasing the bundle. It requires a `read-for-model-analysis`
scope and rejects approval-bearing contexts. This is a trusted local read/disclosure
boundary, not a new catalog capability or security boundary against hostile Python.
The operator owns workspace identity, principal, permission and model-destination
association. Separate existing governed Chat authorization remains mandatory.

## Alternatives and consequences

A Core specialization would reverse package ownership. A new distribution adds
release overhead without an independent consumer requirement. Putting all behavior
in an example would not provide a reusable typed specialization. A tool loop adds
authority and termination problems that this explicit-file use case does not need.

M2 stable-workspace assumptions and synchronous I/O limitations remain. Evidence
is not an atomic snapshot or canonical Evidence. Only structured citation membership
is validated; narrative and any paths mentioned inside narrative remain unverified.
Accepted-output limits do not bound provider generation, transport or cost.
No write, Git, execution, memory, retry, fallback, Workflow or Team surface is added.

Qualification requires the affected Engineering suite, Core Agent/Model/routing
regressions, import/dependency checks and fresh wheel installation with and without
Core. No runnable validation was performed internally; see the Engineering README.

## Addendum — CR-3 authorized engineering effects (2026-09-29)

This addendum extends the same authorization decision to the two effects a
governed engineering consumer needs. It does not reopen or change any decision
above, and the ADR status is unchanged.

- **Actions:** two fixed action identifiers join `read-for-model-analysis`:
  - `apply-repository-changes`, for `RepositoryMutationPort.apply`;
  - `run-engineering-check`, for `EngineeringCheckPort.check`.

  Each wrapper hard-codes its action. No action or scope is taken from request,
  task or model data.
- **Resource binding:** identical to reads. The `SecurityContext` operation
  subject must equal the operator's workspace `ConfigurationRef`, and the
  resource scope must equal that reference's `instance`. A context for another
  workspace, action or scope is refused when the wrapper is constructed.
- **Timing:** current Governance is evaluated immediately before every effect,
  with a fresh timestamp. No allow decision is cached. A grant that expires, is
  revoked or loses policy currency after construction is denied on the next call.
- **Denial before effect:** `DENIED` or `UNAVAILABLE` raises
  `EffectAuthorizationError` before the inner adapter is called. Nothing is
  written, and no check process or sandbox is started. Allowed effects keep
  their existing result and error semantics, and there is no retry.
- **Approvals:** approval-bearing contexts are refused, exactly as for reads.
  No approval is consumed or orchestrated.
- **Ownership:** `AuthorizedRepositoryMutation` in
  `legoai_engineering.repository.mutation_authorized` and
  `AuthorizedEngineeringChecks` in `legoai_engineering.checks.authorized`
  decorate the existing Ports, which are unchanged. The inner adapter still
  owns the effect. One private helper, `legoai_engineering._authority`, holds the
  shared check for reads, mutation and checks.
- **Public wiring:** the read composition is public as
  `legoai_engineering.analyst.authorized` and
  `legoai_engineering.coding.authorized`.

Authorization is permission to perform an effect. It is not isolation, result
integrity or evidence of which inputs were checked. No Git wrapper, evidence
wrapper or generic authorization middleware is introduced.
