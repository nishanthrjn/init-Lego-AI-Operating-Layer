## 1. Context and decision question

Configuration already records Secret references, not material. Secret Access owns reference/use governance. ADR-005 supplies current explicit authority; ADR-007 supplies final dispatch ordering; ADR-009 supplies evidence custody. The open choice is how a qualified realization obtains and uses confidential material without creating an ambient credential service or a durable replay source.

How does the reference runtime allow an authorized operation to use Secret material for one explicit purpose without making it ambient, durable, transferable, replayable or broader than the operation's authority?

These are enforcement objectives at the declared trusted boundary, not a promise that bearer bytes become technically uncopyable. A trusted Adapter may need a token string in memory; a malicious component with that memory access can defeat language-level conventions. The first mechanism supports qualified trusted-host operation, not protection from a malicious debugger, host administrator, memory scraper or hostile in-process Plugin. ADR-012 owns expanded Plugin isolation.

No store, credentials, encryption, provider protocol, vault, environment loader, SDK credential class, signing mechanism or implementation is created. The mechanism is optional: a Secret-free deterministic Capability does not need a Secret provider or Secret-provider startup.

## 2. Closed boundaries and distinctions

SecretRef ≠ Secret material; Secret identity ≠ credential value; configuration ≠ Secret store. Permission to invoke a Capability does not grant Secret resolution; permission for a Secret use does not grant arbitrary purpose or export. Availability and possession confer no authority. Secret-use evidence is not the value. Rotation differs from revocation, and revocation cannot erase completed effects or retract bytes already transmitted.

An Agent is not a Secret authority; Plugin ownership does not automatically confer material authority; Model output cannot authorize disclosure. Approval, Permission, Secret use, resource admission and effect success remain independent predicates. A healthy resolver is not a current use decision.

Preserve the existing Secret lifecycle from SPEC: provisioned → active → rotated, expired or revoked; rotation activates a new material revision. This ADR introduces no replacement Secret lifecycle. Acquisition, guarded use, provider acceptance and effect observation are distinct facts, not new Execution or Plugin states.

| Accepted decision | Preserved consequence |
|---|---|
| ADR-003 | Exact non-secret configuration plus reference/selector/purpose semantics; no raw values in snapshots, hashing, comparisons or rollback. |
| ADR-004 | Owner-local durable safe results/history/obligations; neither material nor live credential objects enter ordinary persistence. |
| ADR-005 | Explicit current Principal, requester/acting chain, TenantContext and deputy intersection at each protected boundary. |
| ADR-006 | Finite independently established roots; Plugin inspection/admission and initialization effects remain separate. |
| ADR-007 | All participating invalidators and actual protected acceptance share proven order; no slow network wait under final gate. |
| ADR-008 | Same intended effect retains identity where equivalent; unknown handoff never triggers blind replay or token restoration. |
| ADR-009 | Safe evidence with actual required custody; post-effect evidence failure creates repair without repeating the action. |
| ADR-011 | Secret-bearing support requires accepted mechanism plus implementation/provider qualification and scoped release evidence. |

## 3. Ownership and public contract mapping

The existing **Secret Access** module retains reference, validity/rotation, purpose-bound decision and use-attribution ownership. Material remains authoritative in its Secret-owning system or qualified protected provider; Lego AI need not store the underlying value. A provider realization can be Plugin-owned without acquiring Governance authority, self-admission or ownership of every Secret it serves. No canonical global Secret database is introduced.

Use exactly CONTRACTS §15.5:

| Operation | Public meaning preserved |
|---|---|
| `resolve_secret_reference` | Validates scoped reference/purpose/consumer/revision; returns protected reference and safe material revision/status, never bytes. |
| `authorize_secret_use` | Produces a bounded exact-use decision under current authority/purpose/validity; no general read/export permission. |
| `validate_secret_revision` | Establishes current validity/rotation/revocation for the requested use; historical references do not restore validity. |
| `record_secret_use` | Records immutable actual/unknown use attribution, with safe references and no material. |

Confidential acquisition and conveyance occur only inside an expressly authorized protected realization. The internal ephemeral handle selected below is not a new public result type, transferable canonical capability or `get_secret(name)` API. Generic application controllers, Workflow/Agent code and the Plugin framework do not receive it or raw material.

ADR-002 already allocates Secret contracts to named Secret Access sections of `legoai.governance` and reserves `legoai.reference.secret` for a future reference realization; external implementations live behind their admitted Plugin/Adapter boundaries. Preserve that mapping, separate from Identity, Policy, Evidence and Resources. Do not create a Kernel Secret manager, global singleton or peer implementation imports. No package is created here.

## 4. Alternatives and comparative analysis

### A — Raw Secrets in configuration

Easy for small prototypes and common SDK setup, but ordinary configuration propagates into snapshots, diagnostics, backups, comparisons and checkpoints. It obscures purpose, rotation and disclosure scope. Reject: it violates the accepted reference/value boundary and makes ambient possession too easy. A secured material-source Adapter is a different protected concern, not an exception making raw values ordinary configuration.

### B — Resolve at startup and cache for process lifetime

Reduces resolver calls/latency and can satisfy SDKs expecting long-lived clients. It increases exposure, shares material across unrelated operations and makes rotation/revocation depend on potentially stale caches. Startup success cannot authorize every later use. Reject as the initial mechanism. A later narrowly qualified cache/session may be supported only with explicit scope, lifetime/use count, invalidation/currentness, tenant/account isolation and failure proof; a TTL alone is insufficient.

### C — Just-in-time purpose-bound resolution and guarded use

Resolve safe references first; authorize a narrowly scoped acquisition close to use; hold material privately for one admitted operation; re-establish the complete current set at the actual use boundary; discard on completion or abandonment. This minimizes ambient exposure and aligns with existing owners. It costs resolver availability/latency, explicit gate integration and per-SDK qualification. “Just-in-time” does not itself prove freshness; §8 supplies the actual ordering mechanism and unsupported cases.

### D — Provider-side action/signing without material export

An admitted broker can authenticate/sign/perform a precisely scoped action while keeping a key or credential inside its own boundary. This can reduce host exposure and support non-exportable keys. It adds a trusted external deputy, target/data-transfer constraints, availability and effect-reconciliation obligations, and is unsuitable for some SDKs. Retain as an optional specialized Adapter pattern; not a universal requirement or an automatically safer authorized action.

| Criterion | A — Raw config | B — Startup cache | C — Guarded JIT | D — Mediated use |
|---|---|---|---|---|
| Least privilege / purpose | Ambient, weak binding | Must add per-use enforcement | Exact consumer/action-bound | Broker must enforce exact action |
| Tenant isolation | Copies/config leakage | Cross-operation mixing risk | Explicit scoped acquisition/use | Broker scope and caller binding |
| Rotation | Config/value replacement ambiguity | Cache refresh required | Selector resolved near use | Provider-defined behavior |
| Revocation | Possession survives | Delayed invalidation risk | Ordered current check required | Proven broker order required |
| Exposure lifetime | Durable and widespread | Process lifetime | One bounded admitted use | Material remains at provider |
| Restart | Restores old bytes | Reacquires ambient material | References/history only | Reauthorize broker operations |
| Plugin isolation | Broad exposure | Shared memory/cache | Narrow trusted path; not hostile isolation | Reduced export; host/transport risks persist |
| Agent isolation | Easy prompt/config leakage | Depends on access paths | No material to Agent | No material to Agent |
| Local development | Simple but incompatible | Initially simple | Qualified local source possible | Additional broker may be unnecessary |
| Provider replacement | Embedded formats/paths | Client/cache coupling | Stable references and mappings | Action/protocol capability mapping |
| SDK compatibility | Usually straightforward | Suits persistent clients | Bounded raw-memory bridge where required | Limited for export-requiring SDKs |
| Failure truthfulness | Often silent stale fallback | Stale success temptation | Explicit unavailable/unknown | Separate broker/effect uncertainty |
| Testing burden | Leakage hard to contain | Expiry/cache/race cases | Purpose, race, lifetime and recovery proof | Broker plus external-effect proof |
| Operations | Distributed value copies | Cache invalidation duties | Resolution dependency/cost | Broker availability/qualification |

No numeric scores, vendor promises or empirical security results are asserted. Comparison follows the accepted constraints, not implementation benchmarks.

## 5. Decision

**Select C with no reusable raw Secret cache initially; support D as an explicitly qualified specialized realization.**

The path is: immutable SecretRef semantics → exact purpose/use declaration → current ADR-005 context and owner decisions → governed short-lived acquisition outside long final-gate waits → protected ephemeral handle → ADR-007 current validation and bounded admitted use → prompt disposal → safe ADR-009 attribution and outstanding obligations.

Public resolution never returns material. Only the qualified resolver/protected material bridge and the smallest admitted consumer Adapter that genuinely needs bytes may see them. Where supported, provider-side use avoids export. The mechanism uses separate protected acquisition and use boundaries; success at the first cannot authorize the second. No ordinary durable material retention or cross-operation raw-value cache is selected.

## 6. SecretRef, selectors and configuration

A technology-neutral SecretRef identifies or unambiguously references Secret identity, authoritative owner/domain, owner tenant/scope, class/use requirements, permitted resolver mapping and declared material-version selection rule. It contains no raw value and grants no permission. Names, local paths, environment variable names and provider endpoints are not by themselves canonical identity. No wire format or universal Secret type taxonomy is selected.

The reference itself and even its existence may be sensitive. Resolve it only under current disclosure authority. One explicit verified TenantContext governs the operation; do not infer or correct tenant from the reference. The initial path requires matching admitted tenant scope. A future authorized cross-scope path would need both sides' policies and explicit crossing contracts, never relabeling or ambient sharing.

| Selector | Required interpretation |
|---|---|
| Exact material revision | Use only that version if still authorized/valid; rotation does not silently upgrade it. Missing/incompatible version fails explicitly. |
| Current eligible revision | The declared rule permits choosing the currently eligible revision at use. Record the actual revision privately where allowed; reselect if the ordered current revision changed. |
| Provider-defined alias | Only with explicit owner/versioned mapping and qualification of its selection/currentness behavior; ambiguous latest is rejected. |

Eligibility and preference are distinct. A contract may explicitly permit an already selected still-valid version during a declared rotation overlap. That is a bounded selection rule, not permission to ignore a strict current-at-use selector. When strict current-at-use changes after acquisition, discard/reacquire outside the final gate; no in-gate network chase. Historical evidence records the actual revision/approved mapping, not an unresolved alias.

ADR-003 configuration freezes Secret identity, selector semantics, intended consumer/target/purpose and requiredness, not credential bytes or live authority. Rotation under a permitted current selector need not create a new configuration revision when those meanings remain unchanged. Changing Secret identity, target/account, selector meaning or purpose does; an exact-version config may need a new config/activation treatment to select a different revision. Never include raw values in configuration identity/hashing or rejected-input diagnostics.

Activation may validate references, permitted dependencies, policy and resolver qualification without acquiring material. If initialization itself requires a credential, it is a separate protected effect under §13. Configuration or activation success cannot establish perpetual Secret availability or current use authority.

## 7. Purpose, Principal, tenant and deputy binding

Bind the use declaration to originating requester, actual acting Principal/chain, explicit TenantContext, operation and intended-effect identity, transport/use attempt where relevant, exact capability/Tool/action/input meaning, consumer Plugin/Adapter/version, actual provider/target/account, SecretRef/selector, intended credential function, config/activation, admitted ceiling and applicable Policy/Approval/resource/evidence constraints.

Secret Access verifies current context and governing owner facts; a Plugin-supplied `authorized=true`, provider login success or model rationale is not evidence of entitlement. Invocation, Secret acquisition and use permissions are separate. Apply requester authority ∩ delegated scope ∩ acting/deputy ceiling ∩ applicable Policies, together with Secret owner/purpose restrictions and all other required controls. Broad technical credentials cannot enlarge that intersection.

Resolver technical credentials authenticate the resolver to its provider. They neither impersonate the originating requester nor transfer provider-wide powers to the caller. Independently authorized maintenance remains different recorded work; it cannot be substituted to fulfill a denied request. Approval may be required for acquisition, use or the external action; each binds its exact purpose and remains independent of Secret permission.

Target identity includes the account/organization/resource meaning conveyed by the credential, not just a hostname. Same provider with account A versus B can be a different effect target and deduplication domain. Qualified mappings must verify the returned material is for the requested reference/version/tenant/target; successful byte retrieval is insufficient. Redirects, SDK credential discovery or model-suggested alternate targets must not cause a credential to travel beyond its admitted recipient/purpose.

## 8. Resolution, acquisition and ADR-007 use ordering

### 8.1 Two protected boundaries

Keep slow preparation, Human waits and required evidence production outside final arbitration. Prepare exact action and safe references, perform current preliminary checks, reserve applicable resources and obtain required pre-effect custody. Do not resolve material during arbitrary Plugin discovery, descriptor inspection or general configuration capture.

If acquisition requires a remote call, token exchange, disclosure or other effect, admit **that acquisition** as its own bounded governed step, linked to the parent but with its own identity, current authority, permitted provider target, resources, deadline and required evidence. Its local acceptance follows ADR-007; network response waiting occurs outside the gate. Technical credentials used to acquire material obey the same finite-root/currentness discipline. Public `resolve_secret_reference` remains a reference/status operation, not a disguised raw-value result.

After response validation, material resides only inside the protected resolver holding area, bound to the pending exact use and a declared finite lifetime. A response arriving after cancellation, expiry or invalidation is rejected for use and discarded; an in-flight previously authorized acquisition may still have cost or disclosure effects. Acquiring material does not confer permission to expose it to another consumer or invoke the business action.

### 8.2 Final exact use

1. Enter ADR-007's exclusive live arbitration domain for the intended protected use. Check the invoking effect record; unresolved/completed prior dispatch cannot acquire a second independent slot.
2. Revalidate exact Principal/Tenant/action/consumer/target/configuration and all current governing decisions, Approval/resource/evidence predicates and deadline. Validate SecretRef mapping, actual selected material revision, status/validity and declared selection rule.
3. Establish current Secret authority and material validity from participating authoritative owners, or a qualified equivalent ordering guarantee. All local changes to Secret use permissions, material revision eligibility, alias mapping, rotation/revocation and consumer/provider suitability that can invalidate use must enter the same arbiter before becoming effective.
4. Complete required owner-local consumption and re-establish the final exact set under ADR-007. Persist only safe attempt/decision/claim references and obligations; never material or a replayable handle.
5. Inside the qualified bounded non-reentrant acceptance path, permit the exact consumer to use the ephemeral handle/material for the specified operation. Validate time/expiry at actual use acceptance with ADR-007's qualified bound or equivalent atomic guard.
6. Release the gate without waiting for remote completion. Minimize retained material and close the use scope on the earliest applicable completion, cancellation, expiry or failure; record actual/unknown use and effect observations separately.

If required currentness, material selection or local bounded access is unavailable, do not fetch/wait under the gate. Exit without the external use, dispose of unsuitable material, and perform any permitted reacquisition as a separately governed step outside. Earlier claim consumption remains real. Repeated preparation is bounded by inherited deadline, attempt and resource rules.

### 8.3 What the gate proves, and what it cannot

For a participating revocation M and use U, if M becomes effective first, U sees the restrictive authoritative fact or unavailability and cannot proceed. If U wins actual valid acceptance, it is already in flight when M becomes effective; stop limits and subsequent-use restrictions are recorded. Earlier resolution R is neither U nor authority for U. Raw possession cannot bypass the guard.

A local lock cannot order an independently revoking remote provider. A recent fetch, token expiry, provider health response or local cache does not prove the required joint currentness. Initial supported paths therefore require local authoritative control participation or an external protocol whose qualified behavior actually establishes equivalent order/currentness at the relevant protected boundary. A remote provider lacking that proof is unsupported for the affected guarantee/path; no delayed-observation exception or newly invented distributed lease protocol is introduced.

Provider-side mediation can enforce remote material validity at its own use boundary, but its contract must also preserve the relevant requester/action authority and ordering for the whole claimed path. It cannot automatically inherit the local arbiter's proof. A provider rejecting an invalid token is useful failure behavior, not evidence that an unauthorized credential disclosure never occurred.

An Adapter acceptance must commit responsibility for the exact admitted protected use, not merely enqueue arbitrary future credential use. If work waits before credential disclosure/use or performs later protected sub-actions, those boundaries need current checks. Unbounded SDK callbacks, network waits or subsequent hidden retries cannot run as part of the final gate. If an SDK cannot expose a qualified boundary, that integration is unsupported until a conforming realization exists.

Expiry is independent of acquiring the lock. Include authoritative time basis, uncertainty and remaining check-to-acceptance bound; no universal TTL or hard real-time CPython guarantee is supplied. A timestamp followed by arbitrary scheduling pause is not proof. Unsupported strict time/currentness scope fails closed. A stuck old holder must be terminated/fenced under ADR-007 before replacement; force-unlocking cannot create safe authority.

## 9. Handle, lifetime, SDK bridge and caching

Select an internal non-public, non-serializable guarded use handle over returning raw bytes to ordinary callers. It is bound to the pending use, actual consumer, operation/effect, tenant, target/account, material revision and lifetime. Knowing/copying a reference does not authorize invoking it; each use still passes trusted checks. This is an in-process mechanism under the trusted-host assumptions, not cryptographic capability security or a provider lease.

Default scope is one admitted operation/transport use with one bounded Adapter call and no reusable raw-value cache. A profile must supply finite acquisition/holding/call limits, expiry/currentness rules and cancellation/disposal behavior before enabling its path. Do not hold material through Human review, unbounded queue waits, unrelated preparation or arbitrary background tasks. Failure to demonstrate required bounds blocks support; a configured timeout is not proof of perfect physical erasure.

An SDK that requires a string/token may receive the minimum material inside its admitted Adapter's private call scope after the use guard. The bridge must prevent ordinary serialization, debug/repr dumps, exception embedding, request/body/header logging, telemetry and implicit SDK credential persistence/discovery. Minimize copies and retained references; close/reset qualified client/session state when the use ends. If an SDK retains unbounded global authentication state, the one-use realization does not support it.

Disposal means disabling further authorized access/use, clearing controlled references and releasing the protected scope promptly. Python, garbage collection and ordinary SDK strings do not guarantee cryptographic zeroization or that every physical copy disappears. No perfect erasure claim is made. OS swap, crash/core dumps, debugging and memory inspection remain sensitive exposure surfaces requiring declared host controls; no OS policy or native secure-memory implementation is chosen. Stronger memory guarantees require separately qualified mechanisms.

Later caching or multi-use sessions are optional qualification work, not selected defaults. They must bind permitted operations/consumer, tenant/account, use count or finite session scope, lifetime, rotation/revocation/currentness, concurrency and cleanup/failure behavior. They must not transfer one caller's access to another. Provider-native lease metadata is distinct from a use grant; its name alone establishes neither freshness nor immediate revocation.

## 10. Rotation, revocation, derived credentials and sessions

Rotation creates a new material revision that may become preferred/current. An old revision can remain usable only under explicit provider/owner overlap and selector semantics. Revocation withdraws covered future use under the declared effective order; it is not simply a pointer change. Neither operation rewrites historical attribution or implies old values must be retained for proof.

If rotation occurs before acquisition, follow exact/current/alias rules. If it occurs after acquisition but before use, revalidate at §8: a strict current selector must use the new eligible revision, while exact or explicitly overlap-permitted use may continue only if still valid and authorized. If target/account/purpose semantics changed, do not treat that as a harmless credential refresh; reacquire decisions/new intent as required.

If revocation wins use ordering, an already-resolved handle is unusable and its material is discarded. Record requesting, effective, observed/enforced and in-flight scope separately. If use already won, restrict later actions and request bounded cancellation where supported, but preserve partial/completed/unknown effects, consumed Approval and charges. Do not claim to remove a transmitted credential from provider memory or undo external acceptance.

Tokens minted from another credential, session cookies, refresh tokens, signed assertions and temporary credentials remain Secret material according to their actual power. Bind lineage to source reference/revision, derivation purpose, provider/target/account, consumer and validity. The exchange can be its own governed effect with cost and uncertainty. Secret-bearing derived values stay inside the protected path; their canonical results/history contain safe references, not bearer values.

Source revocation does not necessarily revoke already issued sessions externally. The profile must state actual propagation and residual validity. Locally stop future covered uses of known derived lineage according to the effective restriction and prove any claimed remote invalidation separately. A minted token is not an exemption from current Policy merely because its signature or expiry still looks valid.

Long-lived authenticated connections and pools may retain sensitive session authority even if original bytes are dropped. The initial single-use mechanism does not implicitly qualify them. Any later support must preserve current checks at future protected actions, segregate tenant/purpose/account, bind permitted consumers and concurrency/use limits, and demonstrate revocation/rotation/drain behavior. One startup authentication cannot authorize all later queries or cross-tenant pool reuse.

Single-use tokens and one-time passwords require explicit owner/provider consumption and timing semantics. A one-use host handle is not proof of provider single-use enforcement. Unknown consumption requires status/reconciliation, not a retry with the same token. Private-key signing/use-without-export is a useful D specialization; signing power still cannot exceed application purpose/authority. OAuth, API keys, database credentials and password-based protocols are examples owned by Adapters, not canonical APIs or authentication UX selected here.

## 11. Persistence, restart, retry, cancellation and accounting

Persist only safe SecretRef/selector interpretation, exact purpose, consumer/target mapping, config/activation, operation/effect/use lineage, safe actual revision/status, decisions, resource observations and evidence/repair obligations. Raw material, bearer-derived values, live handles, authenticated client objects and sessions do not enter ordinary Application/Execution state, Workflow checkpoints, owner result ledgers, backups or migrations. Protected material provider storage remains its separately governed boundary, not ordinary owner state.

After restart no live handle/material is restored by the runtime's recovery mechanism. Physical memory/dump erasure is not asserted. Recover safe records, establish ADR-007 exclusive authority, inspect prior effect knowledge and re-establish current permission/validity before any permitted future acquisition/use. Old checkpoints and configuration cannot resurrect revoked versions or sessions. A historical successful resolution result is status evidence, not a replayable credential return; material acquisition for new permitted use requires a fresh governed step.

ADR-008 governs genuine retries versus equivalent retransmission. Preserve original operation meaning/preconditions and intended-effect identity where equivalence is established. A new transport attempt needs current Secret permission, eligible material, transport authority and remaining bounds. It must not replay bytes retained for convenience. Rotation can change authentication material without changing intended business effect only when contract, provider identity/account/target and equivalence permit it. Otherwise reconcile or require explicit new governed intent; never silently reset provider deduplication identity.

If credential use may have produced an effect and acknowledgment is lost, retain unknown effect and liability. Do not repeat the business action to see whether the Secret worked. Use current authorized provider/owner status, qualified equivalent continuation or intervention under ADR-008. Queries can themselves need a distinct Secret purpose and resource admission. Credential validity does not imply provider business acceptance; use in a request does not imply effect completion.

Cancellation after acquisition but before use disables the handle and discards material without business handoff. Resolution cost/evidence or a credential-minting effect may remain. A SecretRef is not automatically consumed merely by lookup; specialized provider use/consumption rules determine actual facts. Cancellation after protected acceptance preserves in-flight uncertainty and stops only the future work it can actually control.

Resource claims cover acquisition/exchange/API requests, network, rate limits, money, use, refresh, cleanup and evidence duties where applicable. No free-resolution assumption, tariff or provider limit is selected. If resource/Approval fails after material acquisition, no external business use occurs, but acquisition effects/costs remain. If use fails after claims were consumed, consumed Approval is not automatically refunded, and incurred/unknown resource liability remains until authorized reconciliation. Independent owner commits do not become a global rollback.

## 12. Plugin, Agent and disclosure boundaries

A Plugin may declare exact Secret class/reference requirements, purposes, consumers, providers, permissions and exposure assumptions. Admission under ADR-006 must assess them before enabling a Secret-bearing path. It cannot choose an arbitrary tenant's reference, authorize its own material use, widen purpose or log values. The Secret provider Plugin itself cannot self-admit or bootstrap trust by returning a credential. Candidate inspection remains data-only; code import/initialization with effects has its governed boundary.

An Agent or Model can propose a permitted reference, target or intended use as untrusted input. Deterministic enforcement derives current context and validates the actual action. Agent messages, prompts, Context, Tool arguments/results visible to the Agent, Skills and Memory do not carry raw material. Prompt injection, a generated admin request or “show me the key” cannot authorize resolution/export. If a qualified Tool requires authentication, its admitted Adapter performs the protected use and returns only a permitted business result.

No global Secret accessor, name enumeration, ambient environment lookup or generic material-returning service is exposed to arbitrary Plugins/callers. Knowing a reference does not grant existence, metadata, use or export access. An operator does not automatically need to view material. Human disclosure, if ever supported, is a distinct exceptional/high-risk purpose requiring actual upstream authority; no break-glass or diagnostic export exception is invented. Once material has legitimately been shown, this architecture cannot prevent a Human copying it; avoid disclosure unless the governed purpose requires it.

## 13. Bootstrap and finite roots

The dependency graph includes identity establishment, Policy/enforcement, resource duties, evidence custody, Secret resolver and any provider technical credential. It must terminate at independently provisioned accountable roots under SEC-054–056 and ADR-006/009. This ADR designates no actual root, authority, credential source or technology.

An acceptable semantic termination is an independently established administrative basis designating bounded host identity/Policy enforcement and bounded local root evidence custody. Where needed, it separately designates a protected technical-credential source whose access does not require the unstarted resolver. That source permits only the resolver's named bootstrap/provider duty; it is not ordinary application Secret access or a universal service account. Exact Principal/Tenant, realization/version, ceiling, validity/revocation, custody, resources, dependencies and recovery authority must be recorded and qualified.

```text
Independently established accountable administrative basis
  → bounded identity / Policy / enforcement / resource roots
  → bounded independent root evidence custody
  → protected provider-credential source, if required
       → admitted Secret resolver duty
            → governed ordinary Secret uses
```

The arrows describe prerequisites/designations, not automatic grants or physical deployment. Credentials for the source itself must also terminate independently. No loop may be hidden by an SDK default, environment variable or recursive `get_secret` call. Source options such as OS/user-protected custody or a secured external handoff require their own proof; none is selected here.

For a credential needed by the ordinary Evidence backend, use an independently qualified bounded root custody path to establish the required pre-use evidence; then authorize backend credential use and preserve linked ordinary custody obligations. Root custody must actually meet the required guarantee and attest its own bounded custody under CTR-061; an ordinary log is not a substitute. If Policy demands that very unavailable backend before its own credential can be used and no permitted independent path satisfies it, the Secret-bearing path is blocked. Do not waive evidence or silently narrow its guarantee to break recursion.

Plugin initialization requiring authentication is a protected operation with its own current purpose, evidence and resources; credentials are not loaded during descriptor inspection. Initializer/provider duties stay within the exact admitted stage and cannot lend inactive contributions general eligibility. Root rotation/replacement uses independently entitled authority, preserves lineage and reassesses dependents. Suspected resolver/root compromise needs recovery authority/evidence outside the compromised basis; otherwise stop affected paths.

## 14. Evidence, errors, diagnostics and retention

Safe Secret-use evidence identifies requester/acting Principal and tenant through permitted references, purpose/consumer, SecretRef/actual revision where allowed, resolver/provider/target mapping, config/activation, operation/effect/use identity, currentness/rotation basis, time/order, acquisition/use observations, success/failure/unknown extent, resources and outstanding duties. Resolution success, actual credential use, provider acceptance and external effect confirmation remain independently attributable.

Do not put raw Secret material into ordinary configuration, Application/Execution state, checkpoints, Plugin declarations, Evidence/Conformance records, logs/traces/metrics, Artifact metadata/content, Messages, Agent prompts/Context or Evaluation datasets. Derived bearer credentials receive the same treatment. General error objects, repr/debug dumps and SDK response bodies must not become indirect export channels. Prevent material entering these paths by construction; redaction regexes alone do not establish safety. Secret fingerprints can enable guessing/linkage and are not inherently safe or required; any retention needs a specific governed basis.

Reference, revision, provider identity, target/account and timing metadata can themselves be sensitive. Public diagnostics may expose only an opaque correlation and canonical category; entitled internal readers can inspect safe details under current ADR-005/009 disclosure authority. Do not leak cross-tenant existence through not-found, validation, status, enumeration, timing claims or echoed attacker-supplied reference details. No elimination of every length/timing/side channel is claimed; qualify the actual threat scope.

| Condition | Canonical handling, with safe detail |
|---|---|
| Malformed or ambiguous selector/purpose | ValidationError; no guessed alias, tenant or target. |
| Missing current use authority / invalid tenant scope | AuthorizationDenied / TenantViolation as established; avoid existence disclosure. |
| Required provider/resolver unavailable | CapabilityUnavailable or DependencyFailure according to actual boundary/cause; no fabricated denial or absence. |
| Unsupported version interpretation | VersionMismatch; a correctly interpreted but unavailable exact version may be CapabilityUnavailable. |
| Revoked/expired use condition | Deny under applicable AuthorizationDenied/PolicyViolation or time-bound DeadlineExceeded; distinguish cause internally without leaking material. |
| Stale decision/revision or conflicting use identity | Conflict; no silent mutation of original operation meaning. |
| Required control/custody unsatisfied | PolicyViolation or applicable dependency failure; no business handoff. |
| External use timeout/business failure | Appropriate invoking-family error, such as ToolFailure, with separate none/partial/completed/unknown effects; credential validity and business outcome remain distinct. |

These are mappings to existing semantics, not new Secret lifecycle/error categories. Authorized not-found does not authorize substitution. Unknown control status is not invented proof of revocation or invalid credentials. Failures retain safe category and references, not sensitive provider responses or credentials in stack diagnostics.

Required pre-effect evidence must meet ADR-009 before protected use. Post-effect evidence failure leaves actual effects and a durable repair/intervention obligation; repair the evidence operation, not the external action. Safe material-revision attribution need not retain obsolete bytes. Deletion of material and retention of permitted reference-use history are separate governed decisions. Q-05 conflicts, privacy, legal hold and permitted disposition remain upstream; no universal retention duration or precedence is invented. If required historical interpretation becomes unavailable, disclose that gap and block dependent claims/retries as applicable.

## 15. Provider qualification, outage, fallback and local development

Before enabling a path, qualify exact owning Plugin/Adapter/provider, reference and material-version identity mappings, tenant/account/consumer/purpose checks, response integrity and source authentication, current access enforcement, selection/rotation overlap, revocation and derived-token behavior, actual protected boundary, timing/currentness proof, transient handling/disposal, SDK defaults/retries/sessions, safe evidence/error behavior, resources and admitted failure assumptions. Marketing claims, successful login and returned bytes are not sufficient proof.

For remote providers include network/trust/authentication, delay/outage, response substitution, independent updates, token exchange and rate-limit/charge behavior. No transport, encryption, TLS configuration or credential protocol is selected. A provider with independently effective revocation requires §8's actual equivalent-order proof; this ADR does not qualify any such provider by assumption. Even a local source must prevent mutation paths bypassing declared authority/currentness guarantees or explicitly remain unsupported for that scope.

Required resolver outage blocks the affected Secret-bearing operation. No fail-open to an old cached token, ambient environment value, default SDK credential, another tenant or same-named Secret in another store. A separately qualified fallback would need explicit policy and preservation of Secret identity, scope, target/account, purpose, selector/revision meaning, currentness and evidence. The initial mechanism supplies no automatic fallback.

A future qualified local developer source is possible without enterprise infrastructure. Its protected provisioning and custody are separate from canonical configuration; local paths and `.env` conventions are not platform semantics. Environment variables are merely a possible future source Adapter, not selected or privileged by process availability. Process-wide scope, inheritance, diagnostic/dump exposure, staleness and SDK ambient reads require explicit qualification. Technical readability never grants use authority.

A Secret-free runtime performs no unnecessary resolver start or material acquisition. It still meets universal authority/evidence obligations. A Secret-bearing optional path can be excluded until its provider and finite roots are qualified; it cannot be activated merely because this ADR is accepted.

## 16. Structural walkthroughs

### W1 — Human/Service external Tool

The caller's verified context and exact Tool target/account/action bind SecretRef and purpose. Action Mediation checks requester/deputy scope and required Approval/resources/evidence. Secret Access validates the safe reference; protected acquisition obtains only the permitted revision inside resolver custody. The final ADR-007 gate validates the complete current set and admits one exact Adapter use. Safe business result and use/effect evidence return; material never returns to the caller. Broad credential powers cannot authorize another API operation or account.

### W2 — Agent-proposed Tool call

A Human's governed work allows an Agent to propose a call. The proposal can mention only permitted reference/target metadata; it cannot change TenantContext, acting chain or grant. Deterministic mediation validates the actual action and §8's path. The Agent receives no raw credential or live handle. A prompt asking to print a Secret is denied without exposing existence-sensitive details.

### W3 — Credential-bearing Plugin initialization

Inspect P's data-only declaration/configuration and qualify Secret requirements under ADR-006. If initialize must authenticate to a target, admit that exact effect with current bounded duties and finite root evidence. Resolve only near that use; admission/import alone does not receive material. Init may complete while offer publication later fails: preserve init/credential-use facts and repair publication rather than repeating authentication/effects. No Secret-provider Plugin self-admits.

### W4 — Equivalent provider retry after rotation

E1 has a qualified ADR-008 continuation, not blanket replay permission. A new transport attempt keeps its intended effect/account/target and deduplication scope, rechecks current authority and resolves the permitted current credential. Rotation to V2 is compatible only if action/account/equivalence remain unchanged. Changed account mapping or expired provider deduplication requires reconciliation/new governed strategy. Neither old bytes nor a new key may be used to manufacture safe retry.

### W5 — Release publication credentials

ADR-011 approves exact artifact set A and scoped publication purpose. That approval is not a general registry credential grant. The publisher binds destination/account, artifact/action, effect identity, current release/publication authority and SecretRef. §8 admits only that protected use; destination change is reassessed for target/purpose. Lost acknowledgment follows ADR-008; repair publication evidence without repeating confirmed upload. A Secret-free runtime artifact can still have this separately Secret-bearing publication path.

### W6 — Evidence backend credential

The ordinary custodian needs authentication. An independently qualified bounded root evidence duty first satisfies required pre-use custody for the backend-credential action. The resolver's technical credential also has independent provisioning, identity/Policy and resource basis. Use proceeds only if the whole graph terminates and meets actual requirements. Unknown/missing root custody does not become a logging fallback. Later custody failure preserves effect/source obligations under ADR-009.

### W7 — Provider-mediated signing and sessions

For a qualified non-exportable key, the admitted broker receives only the exact authorized data/purpose and returns an allowed result; it does not grant arbitrary signing to the application. A signature functioning as a bearer assertion is protected derived material. If the operation creates a session, later actions require that session's qualified tenant/account/use/currentness model, not a permanent startup grant. Pools and provider-side key custody remain specialized support, not defaults.

## 17. Failure and race timelines

### Timeline 1 — Normal Secret-bearing Tool use

1. Current caller/tenant, exact action/account and Secret purpose are admitted with required controls.
2. Governed acquisition returns validated V1 only into protected resolver custody.
3. Final arbiter proves V1/authority/current selection and all claims valid at actual use; Adapter accepts the exact call.
4. Release material promptly; retain safe resolved/use/effect evidence separately and reconcile any unknown charges.

### Timeline 2 — Unauthorized caller knows SecretRef

1. Caller guesses a valid-looking reference and requests resolution/material.
2. Secret Access validates current entitlement before protected existence/metadata disclosure.
3. Refuse with safe canonical error/correlation; no bytes, handle or existence-dependent detail is disclosed.
4. Record permitted denial evidence; reference knowledge never becomes permission.

### Timeline 3 — Wrong tenant

1. Verified context is Tenant B while the supplied reference belongs to A.
2. Scope checks reject the mismatch without changing context or probing/disclosing A's material.
3. No fallback or name-based remapping occurs; safe evidence retains authorized scope only.
4. Explicit future cross-scope support would require independent crossing authority, not this request's assertion.

### Timeline 4 — Rotation before acquisition

1. Preparation pins reference/selector; owner rotates V1 to V2.
2. Exact-V1 request remains V1 and succeeds only if permitted/valid; otherwise fails without substitution.
3. A permitted current selector chooses the eligible revision according to its declared rule.
4. Record actual selected revision/reference where permitted; configuration meaning is preserved.

### Timeline 5 — Rotation after acquisition, before use

1. Protected holding area has V1 for the pending action; rotation changes eligibility/current selection.
2. Final gate observes the ordered owner revision.
3. Strict-current use of V1 is refused; reacquire outside the gate. Explicit valid overlap or exact selection can proceed only under its own conditions.
4. Preserve acquisition cost/evidence and any consumed claims; no raw-value caching workaround.

### Timeline 6 — Revocation before handoff

1. V1 was acquired while permitted; revocation commits effective restriction before U.
2. Final owner guards refuse U and disable/discard the pending material.
3. No new Secret-bearing business handoff is made under V1.
4. Record revocation/use ordering and residual acquisition effects; possession is not later authority.

### Timeline 7 — Revocation after provider acceptance

1. U validly wins ordering and provider receives the credential-bearing request.
2. Revocation later becomes effective; record known in-flight scope and propagation duties.
3. Future covered actions/session uses stop or revalidate; do not claim remote bytes/effects were erased.
4. Completed/partial/unknown effects and charges remain. Provider-session revocation is claimed only to proven extent.

### Timeline 8 — Resolver outage

1. Required provider fails during reference/currentness or acquisition work.
2. Report actual dependency/capability unavailability with safe details; no fabricated not-found.
3. Do not read ambient credentials or resurrect cached V1.
4. Block affected use; any permitted recovery retains deadline/resource/effect lineage and requires fresh controls.

### Timeline 9 — Crash after acquisition, before use

1. Protected custody contains V1, while durable state holds only safe references and obligations.
2. Process crashes; recovery does not deserialize a credential or live handle.
3. Establish exclusive authority and determine whether a handoff may already have occurred; an unresolved attempt is not absence proof.
4. Only a proven safe permitted next step may reauthorize/reacquire. Historical material is never replayed from checkpoint.

### Timeline 10 — Crash after use, acknowledgment unknown

1. Adapter may have caused E1; local acknowledgment/evidence is missing at crash.
2. Recover E1 and safe Secret-use lineage with unknown effect/liability.
3. Do not repeat E1 to test credentials; obtain authorized status/reconciliation or qualified ADR-008 continuation.
4. Any later protected query/transport use has current Secret permission/material and its own resource/evidence scope.

### Timeline 11 — Agent requests raw Secret

1. Agent text or retrieved content requests key output, suggests `authorized=true` or a different target.
2. Deterministic enforcement treats it as untrusted data, retaining original Principal/Tenant bounds.
3. Reject material disclosure; optionally process a genuinely permitted exact Tool action through the protected path.
4. Agent-visible results and diagnostics contain no raw/derived material.

### Timeline 12 — Bootstrap credential cycle

1. Resolver Plugin needs credential S to start; S requires that resolver; mandatory Evidence needs the same unavailable chain.
2. Dependency assessment exposes the cycle before Secret-bearing initialization.
3. Proceed only if independently designated identity/Policy, technical-credential and qualified root custody duties actually terminate the graph.
4. Otherwise declare the path unavailable; no self-admission, ambient credentials or audit waiver breaks the loop.

### Timeline 13 — Derived token survives source revocation

1. Authorized exchange of S yields sensitive session T with safe lineage; provider may retain T beyond S revocation.
2. Source restriction invalidates covered future local uses of T, under current owner rules.
3. Record any remote revocation request/confirmation and residual validity separately; no instantaneous remote-stop claim.
4. Unknown exchange or single-use consumption follows reconciliation, not mint/use replay.

### Timeline 14 — Publication credential and partial claims

1. Exact release publication is approved; required Approval/resource use commits, but Secret validity later fails before handoff.
2. No registry action is sent; consumed Approval and resolution cost remain recorded.
3. New entitlement, settlement and retry require their respective owners; there is no automatic refund.
4. If the upload instead occurred and only audit failed, repair evidence rather than upload again.

### Timeline 15 — Provider/account substitution

1. Original reference maps to account A; fallback resolver returns bytes for same display name in account B.
2. Mapping/target validation rejects mismatch before protected use.
3. Preserve the original effect scope and safe failure; no cross-account deduplication assumption.
4. A deliberate mapping migration needs explicit authority, equivalence review and new candidate/activation treatment where meaning changes.

### Timeline 16 — Expiry, pooling or hostile in-process access

1. A pending handle expires, or an SDK tries to reuse a pooled session outside its qualified scope.
2. Later protected use fails currentness/use-count checks; a timeout cannot extend validity.
3. If hostile same-process code can directly inspect material, the handle cannot enforce isolation against it.
4. Exclude that threat scope pending ADR-012 proof; do not claim Secret confidentiality merely from package boundaries.

## 18. Threat analysis and proof limits

| Threat | Required treatment / residual limit |
|---|---|
| Secret exfiltration | Narrow protected resolver/Adapter boundary and exact recipient/purpose; compromised authorized consumer remains outside unsupported threat guarantees. |
| Prompt leakage | No material in Agent/Model data paths; deterministic enforcement independent of prompt compliance. |
| Log/exception leakage | Prevent values entering generic logging/serialization and provider errors; redaction alone is insufficient. |
| Checkpoint/backup leakage | Safe references/history only; no live credential/client/session serialization. |
| Cross-tenant access | Verified context and owner scope before protected disclosure/use; no reference-based tenant correction. |
| Confused deputy | Requester/delegation/deputy/Policy intersection plus exact target/account and Secret purpose. |
| Plugin escalation | No self-admission/grant, no general material accessor; qualified consumer stage/duty only. |
| Resolver compromise | Independent root recovery/authority and dependent-scope blocking; a compromised resolver cannot prove its own safety. |
| Provider technical credential compromise | Bounded bootstrap purpose, separate caller authority and independent rotation/recovery; revocation residuals remain explicit. |
| Rotation race | Declared exact/current/overlap semantics and final ordered validation; reacquisition outside the gate. |
| Revocation race | All invalidators participate or supply actual equivalent-order proof; remote polling/cache is insufficient. |
| Stale cache / pooled session | No reusable raw cache initially; future retention requires complete currentness/use/tenant proof. |
| Ambient environment access | Technical availability is not entitlement; SDK defaults cannot supply unrecorded credentials. |
| Enumeration | Current disclosure checks and safe errors/correlation; metadata and references may themselves be sensitive. |
| Derived-token leakage | Tokens/assertions/cookies are sensitive by capability, with protected lineage and handling. |
| Retry replay | ADR-008 effect knowledge and qualified continuation; new credential does not reset deduplication. |
| Provider/account substitution | Qualified exact identity/version/target mapping, not same-name equivalence. |
| Bootstrap recursion | Finite independently established roots and adequate root custody, or explicit unavailability. |

No perfect erasure, complete side-channel elimination, protection against unrestricted host administration or instantaneous remote session revocation is claimed. Initial semantics can be correct while malicious in-process code remains outside supported isolation scope. Required stronger protection cannot be waived through trust labels; qualify it under ADR-012 or do not admit that path.

## 19. Solo burdens and consequences

| Burden | Selected mechanism and tradeoff |
|---|---|
| Implementation complexity | Explicit purpose/context, protected handle and two-boundary integration; reuses existing owners rather than adding a vault or Kernel service. |
| Operational complexity | Resolver/root qualification and conservative outage handling; no initial cache invalidation service. |
| Maintenance burden | Preserve reference mappings, selectors, SDK behavior and provider assumptions; audit material escape paths on changes. |
| Testing burden | Scope/deputy, race, lifetime, restart, evidence and provider-currentness cases; real provider proof cannot be replaced by fixtures. |
| Local-development burden | Qualified minimal local source possible; Secret-free paths need no provider. No enterprise infrastructure requirement. |
| Deployment burden | Provision protected roots/provider dependencies and explicit context; no global environment credential convention selected. |
| Learning curve | Distinguish reference, safe resolution, acquisition, permission, guarded use and external effect; explicit records make each inspectable. |

Benefits include no ordinary raw-secret configuration/persistence, shorter exposure lifetime, attributed purpose, provider replaceability, recovery without obsolete bytes and clear Agent/material separation. Costs include repeated resolver latency/calls, reduced outage availability, extra final-boundary checks, SDK adaptation, provider-specific proof and additional partial-failure duties. No-cache operation intentionally trades latency/availability for a simpler initial exposure/currentness model; it is not asserted to be fastest.

Accepted limitations are the declared trusted-host threat scope, residual physical-memory copies, finite qualified provider guarantees and possible intervention for unknown use/effect. Secret Access/integration maintainers own mapping/exposure qualification; Governance owns authority; invoking owners own effects; Resources and Evidence retain their obligations. Missing mandatory proof or policy parameters block support rather than becoming accepted security exceptions.

## 20. Type-2 migration and reconsideration

Backend and resolution workflow can be replaced behind existing Ports because public contracts carry references, safe status and use evidence, not vendor credential objects. Preserve SecretRef identities, owner/tenant/purpose, provider/account mappings, exact/current selector and revision meaning, configuration/activation lineage, safe evidence references, current restrictions and outstanding effect/resource/custody obligations. Verify mappings and supported failure/currentness semantics before new use; same display name across providers is not migration proof.

Quiesce/invalidate old protected handles and account for in-flight/derived sessions under their actual guarantees. Do not roll back revocation, lose unknown effects, reset use counts or replay old publication/business work. Material transfer belongs only to a provider-controlled or separately secured authorized process; ordinary state migration never carries raw values. Historical mappings may remain as permitted safe references. Reversibility of the workflow does not undo leaked values or external effects.

Reconsider when many providers, non-exportable hardware-backed keys, remote signing, multiple services, hostile Plugins, regulated custody, dynamic short-lived credentials, large connection pools or multi-tenant SaaS require expanded scope. These triggers can justify D, stronger isolation or qualified bounded caching; none is prebuilt or appointed here.

## 21. Release, isolation, observation and proof obligations

ADR-011 support for a Secret-bearing capability/bootstrap/publication path requires ADR-010 acceptance **and** actual implementation/provider evidence under its exact release scope. Acceptance alone supplies no runtime assurance. ADR-012 remains unresolved for hostile Plugin isolation; ADR-013 remains unresolved for operational observation integration. Future diagnostics may use safe reference/categories under current disclosure authority but cannot weaken material rules. Neither later ADR is created here.

Before implementation support is enabled, demonstrate: reference/value separation across public/results/state/config/checkpoints/logs/Artifacts; actual scoped authority and consumer/target validation; hostile proposal/tenant/reference rejection; complete local invalidator participation or qualified remote order; exact/current rotation and revocation before/after actual use; bounded acquisition/holding/SDK acceptance and expiry; honest memory/session limitations; finite root/Evidence termination; no ambient fallback; provider identity/response binding; restart and unknown-effect reconciliation; safe use evidence and post-effect repair; resource/Approval conservation; and migration without raw-value state transfer.

Tests should use synthetic or dedicated bounded test credentials, never production values in fixtures, datasets or evidence. Simulation can validate local behavior but cannot establish real provider revocation, timing, single-use, SDK storage or remote deduplication guarantees. Evaluation/Conformance consume safe references and governed evidence under CONF-045/047; their successful execution cannot grant Secret or release authority. This document creates no tests or implementation.

No upstream contradiction was identified. In particular, raw internal acquisition is not exposed by public `resolve_secret_reference`, remote currentness is not inferred from TTL, and protected use remains conditional on ADR-007's actual ordering proof. Q-05 unresolved precedence, Q-06 resource parameters and Q-07 guarantee qualification remain explicit affected-path blockers where applicable. No accepted document or dependency edge is changed.
