# ADR-020 — Personal Image Inputs in Generative Media

Status: Proposed — for review by the LegoAI platform maintainer acting as
Generative Media / Security boundary owner. Not accepted by this document.
Acceptance records the decision only. It does not by itself authorize
implementation beyond the VTO-1 gate in the
[Virtual Try-On assessment](../planning/VIRTUAL-TRY-ON-IMPACT-ASSESSMENT.md).

Scope: optional `packages/legoai-generative-media` capabilities that send
images of identifiable people to a ComfyUI provider (first consumer: Virtual
Try-On). No Core, Kernel or canonical contract change.

## Context

Virtual Try-On is the first capability that takes a photo of a person and
transfers it to an external workflow runtime. The applicable SECURITY clauses:

- SEC-004: sensitive disclosure is a protected use needing current authority.
- SEC-011: a provider crossing means only policy-permitted minimized input;
  incompatible disclosure is refused and uncertainty is retained.
- SEC-039: unknown mandatory provider guarantees (retention, data use,
  transfer) block the call.
- SEC-066/067: unknown classification prevents disclosure; flows are
  minimized; sanitization is not declassification.
- SEC-075: effect uncertainty is tracked per named effect as
  none/partial/completed/unknown.
- SEC-077: logs and audit minimize sensitive payloads; retention and deletion
  must be reconciled, not assumed.

Provider evidence was gathered by read-only inspection (see the assessment,
§12):

- The local OSS ComfyUI upload route stores files with no byte-deleting
  route. Its optional asset API's `DELETE` removes only a database record, and
  content stays servable.
- Comfy API v2 and Comfy Cloud document record-only deletion, unspecified
  physical deletion, and Cloud retention "as long as necessary to operate,
  analyze, and improve the service".

## Decision

1. **Classification.** Person images are privacy-sensitive application
   inputs. LegoAI assigns them no face, identity or biometric semantics and
   performs no such processing. The capability only passes pixels to the
   approved workflow.

2. **Minimization.** Input image bytes and pixels never appear in logs,
   `repr`, exception text, observations, telemetry or evidence lines. Client
   filenames, local paths and user identities are never accepted by the
   request contract and never sent to a provider.

3. **PNG only, with structural metadata stripping.** v1 accepts PNG only.
   Before any transfer, a new PNG is assembled from only the critical chunks
   required to render the pixels: `IHDR`, `PLTE` when the colour type
   requires it, the `IDAT` sequence, and `IEND`. Every other chunk is removed,
   including `tEXt`, `zTXt`, `iTXt`, `eXIf`, `tIME`, `iCCP`, `sRGB`, `gAMA`,
   `cHRM`, `pHYs` and all private or unknown chunks. Pixels are not decoded or
   re-encoded, and CRCs are validated before stripping. Input that cannot be
   parsed exactly (bad CRC, unknown critical chunk, interlaced or out-of-bounds
   geometry, trailing data) is rejected; it is never forwarded unstripped.
   Colour-management chunks are dropped deliberately, so rendering may differ
   slightly. That is accepted over leakage.

4. **Disclosure is its own named effect.** Input transfer is reported as
   `input_disclosure: EffectExtent`, separate from the job `effect`:
   - NONE: nothing sent.
   - PARTIAL: one of two uploads acknowledged.
   - COMPLETED: all acknowledged.
   - UNKNOWN: a lost acknowledgement.

   `EffectExtent` is reused because SEC-075 defines exactly these per-effect
   semantics. It is never merged into the job effect. For example,
   `effect = NONE` with `input_disclosure = UNKNOWN` is a valid, truthful
   state.

5. **Attempts.** Each invocation performs at most two uploads (person, then
   garment) and exactly one generation submission. Nothing is retried.
   Reconciliation never uploads and stays zero-POST.

6. **Provider names.** Uploaded objects are named with fresh random
   identifiers (`<uuid4>.png`) and never derive from user data. A provider
   rename or dedup response that does not match the requested name is a
   failure, with disclosure COMPLETED or UNKNOWN as known.

7. **Retention and deletion.** Retention is stated per provider profile.
   LegoAI never claims deletion without provider evidence that the bytes were
   deleted. A record-deletion acknowledgement, a 204, or an expiry field is
   not that evidence.
   - Legacy local: upload with `type=temp`. This reduces retention to the
     runtime's lifetime, but only when its asset manager is disabled, and it
     is not deletion. The documentation must say so.

8. **Remote disclosure is fail-closed.** Personal-image transfer is permitted
   only to `deployment = "local"` providers. Remote or Cloud transfer is
   refused before any I/O unless all of the following hold:
   - the provider profile verifies upload, retention and deletion semantics;
   - a superseding or amended ADR permits it;
   - operator configuration opts in explicitly (reserved name:
     `allow_personal_images_remote`).

   Today none of these hold. Consent flags never appear in application
   requests (`TryOnRequest`).

9. **Authorization.** Invocations are governed like every other capability:
   Catalog selection, the exact configuration revision, and the reference
   host's explicit operator grant. This does **not** provide multi-user
   consent, legal consent management, IAM or biometric authorization. Those
   remain out of scope and are required before any multi-user deployment.

10. **Observability.** Permitted:
    - operation and correlation IDs, provider profile and API family,
      workflow identity and digest;
    - upload count, disclosure extent, input byte counts;
    - SHA-256 of the **stripped** input only for local diagnostics;
    - provider job ID and effect.

    Forbidden: image bytes or pixels, metadata or EXIF/GPS, raw provider
    payloads, original filenames, prompt text beyond the approved template's
    identity.

11. **Model substitution.** The model family sits behind an approved,
    digest-pinned template selected by configuration. Model files are operator
    profile values validated by preflight. Changing models within a family is
    a configuration change plus a template re-approval. Adding a family is a
    new closed template kind. Neither changes application code or this
    decision.

## Alternatives rejected

- **Decode and re-encode the input to strip metadata.** It needs an imaging
  dependency and a lossy or unbounded decoder, so it was rejected while
  structural stripping suffices for PNG.
- **Keep ancillary colour chunks.** `iCCP` and `pHYs` can carry
  device-identifying profiles, so minimization wins.
- **Fold disclosure into the job effect.** That loses the "no job, but data
  sent" state.
- **Allow Cloud with a warning.** It conflicts with SEC-039: the retention and
  deletion guarantees are unknown.

## Consequences

- VTO-1 can implement bounded PNG input, stripping, local temp upload and
  disclosure tracking against fakes.
- Cloud and remote try-on stay unsupported until the listed evidence exists.
- Retained personal images on a local runtime remain an operator
  responsibility, documented rather than hidden.

## Review triggers

Any of these reopens this decision:

- a provider publishes byte-deletion semantics;
- JPEG or other formats are requested;
- multi-user or tenant deployment is planned;
- identity or face processing is proposed;
- a model family requires additional personal inputs.
