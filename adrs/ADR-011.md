## 1. Context and decision question

The governing documents and accepted ADRs establish behavior and required proof, but do not select a reference release workflow. A green test run does not demonstrate every applicable obligation, establish migration safety or authorize publication. Repeating all expensive assessments for an unrelated change adds cost without repairing those conceptual gaps.

How will the reference runtime determine that a particular release, under a declared configuration and supported scope, has enough valid evidence to make bounded compatibility, support, release-quality and conformance-related claims?

This decision defines the subject, evidence selection and reuse, compatibility relations, assessment record, accountable release gate, exact publication binding and partial-failure behavior. It creates no release implementation, actual evidence manifest, tests, official profile, certification program or new canonical lifecycle. Registry, CI, Git host, build system, automation product, signing technology, deployment platform and version-numbering conventions remain unselected.

## 2. Closed decisions and semantic distinctions

| Accepted boundary | Consequence for this workflow |
|---|---|
| ADR-001/002 | Assess the conventional GIL-enabled CPython 3.14 reference and existing package ownership; do not turn Python types or tooling into canonical compatibility semantics. |
| ADR-003 | Pin exact configuration contracts, materialized effective revisions and activation bindings; no reinterpretation through new defaults or latest selectors. |
| ADR-004 | Stateful assessment/decision records use accountable owner-local guarded commits, history, results and obligations; no global transaction. |
| ADR-005 | Current explicit Principal/Tenant scope and entitled authority govern assessment access, approval and publication. |
| ADR-006 | Built-in Plugins retain declaration, finite bootstrap, admission, initialization, activation and contribution boundaries; package import is not qualification. |
| ADR-007 | Protected handoff and authoritative resource/Approval claims retain current joint validity, bounded acceptance and conservative uncertainty. |
| ADR-008 | Preserve operation/effect identity, equivalence, original preconditions, deduplication coverage and reconciliation; no automatic unknown-effect replay. |
| ADR-009 | Required evidence must have qualified custody and exact interpretation; post-effect custody failure creates repair, not permission to repeat the effect. |

A release identifies published software and its evidence-backed declarations. Deployment is an actual operating instance with configuration, tenant, Principals, active Plugins, Providers, Secrets, resources and infrastructure. A release claim does not prove that every deployment is conformant or secure, and does not activate a Plugin or instantiate a runtime.

Evaluation produces measurements, judgments and uncertainty. Conformance assesses all applicable mandatory obligations for an explicit scope. Compatibility assesses a specified relationship between subjects along a particular dimension. Release approval is a separate Governance decision. Certification would require an independently established authorized scheme; none is created here.

Thus Release ≠ Deployment ≠ runtime instance; Release ≠ Plugin activation, Evaluation, Conformance or Certification. Compatibility ≠ Conformance; passing tests ≠ universal compatibility; evidence present ≠ valid claim; Conformance result ≠ Permission; Evaluation score ≠ release authority; claim ≠ proof ≠ certification. The same maintainer may perform several entitled duties, but each duty and any lack of independence remain visible.

## 3. Alternatives

### A — Full evidence rerun for every release

Run every applicable test, Evaluation and Conformance check anew. This reduces reuse-analysis complexity and can be appropriate for an initial release, a small inexpensive evidence set or changes with uncertain broad impact. It remains necessary to determine applicability, method sufficiency, exact subjects, authority and compatibility. A full rerun of an incomplete suite is still incomplete proof. As the mandatory default it spends resources on unaffected evidence, increases solo-maintainer delay and repeats expensive probabilistic/provider work without guaranteeing better coverage.

### B — Manual maintainer checklist

The maintainer reviews changes, selects evidence and approves. This is locally simple and allows valid Human review where reviewer, criteria, subject, time and limitations are recorded. An informal checklist alone risks omitted transitive obligations, inconsistent rerun choices and undocumented reuse. A structured checklist is retained as a review aid; memory and a checked box are not the authoritative evidence ledger.

### C — Change-impact-driven evidence ledger and release assessment

Freeze an exact candidate; compare an explicit baseline; derive requirements and compatibility relations affected by changes; justify reuse of unaffected evidence; regenerate affected proof; gather separate Evaluation/Conformance findings; record exclusions, decisions and exact publication bindings. This adds an explicit mapping/review burden, but makes omissions inspectable, preserves history and avoids repeated work without weakening the obligations. Ordinary versioned records and references suffice locally.

### D — CI success equals release approval

Pipeline success is easy to automate but gives the pipeline's chosen checks hidden authority. It omits proof outside the pipeline, scope closure, provider freshness, independent governance and missing-test detection. Reject this equivalence. CI may execute declared checks and validate ledger consistency, but its success is an evidence input, not release authority. Moving the same checks to a local runner must preserve the decision semantics.

| Criterion | A — Full rerun | B — Manual checklist alone | C — Impact ledger | D — CI-success gate |
|---|---|---|---|---|
| Semantic fidelity | Requires separate scope/authority rules | Depends on review discipline | Explicit clause/claim mapping | Pipeline can silently define policy |
| Completeness | Only as complete as applicability/suite | Omissions hard to discover | Missing and transitive obligations visible | Unconfigured checks disappear |
| Repeatability | Good with pinned inputs | Weak without durable criteria | Recorded inputs, reasons and decisions | Execution repeatable, decision incomplete |
| Material changes | Conservative broad rerun | Inconsistent | Semantic and transitive impact | Usually limited to configured triggers |
| Reuse and cost | Minimal reuse, highest repeated cost | Ad hoc reuse | Evidence-specific justified reuse | Cache success can hide staleness |
| Compatibility accuracy | Needs explicit relation matrix | Easily reduced to intuition | Scoped relations with exact proof | Passing build is insufficient |
| Security/Conformance | Needs independent gates | Authority confusion possible | Separate owners and mandatory blockers | Green result can obscure violation |
| Failure truthfulness | Requires preserved failures | Depends on retained records | Missing, partial and contradictory facts explicit | Often flattened to job status |
| Local burden | Simple planning, repeated execution | Low initial cost, growing inconsistency | Modest ledger plus targeted execution | Tool/platform configuration burden |
| Automation | Easy execution, expensive reruns | Difficult without structure | Incremental automation of explicit rules | Easy but insufficient decision rule |
| Replaceability | Runners replaceable | Human-memory dependency | Stable records, replaceable execution tooling | Pipeline-specific hidden semantics |
| External Providers | Repeated checks still need time bounds | Freshness easy to forget | Separate qualification and drift triggers | Provider changes may evade pipeline |

No numeric scores are invented. The comparison is architectural analysis of accepted requirements, not measured runtime cost or an empirical release result.

## 4. Decision and selected workflow

**Select C: an exact-candidate, change-impact-driven evidence ledger, bounded compatibility assessment, separate Conformance findings and current governed release approval, followed by exact-artifact publication and verification.**

Use A when broad impact cannot be bounded or no reusable evidence exists, and B as an attributable review aid within C. D remains insufficient. The first workflow is locally executable and needs no enterprise platform, remote certifier, distributed evidence graph or cloud build farm.

1. Identify and freeze the candidate artifact set, source/build provenance, material dependencies and supported scope/configuration assumptions.
2. Pin baseline release/assessment/evidence sets and explicit compatibility targets; record absence of a prior baseline for the first release.
3. Record semantic material-change analysis, including transitive dependencies, environment and external changes.
4. Derive requirement applicability and closure, compatibility relations and proof obligations independently of test inventory.
5. Map each obligation to existing reusable evidence, necessary new evidence or an explicit gap; justify every reuse.
6. Produce affected/new proof through governed local or external work and obtain required ADR-009 custody.
7. Gather exact Evaluation results and Conformance findings; assess compatibility/migration and resolve counterevidence.
8. Establish any genuinely independent narrowed scope as a new finding, retaining the broader failure/gaps.
9. Pin the complete evidence manifest, applicability ledger, support/compatibility statements, exceptions, limitations and proposed decision revision.
10. The currently entitled release authority reviews and commits approval for that exact scope, or records blocking obligations.
11. An independently authorized publication action publishes only the assessed artifacts; it checks current applicability and publication controls.
12. Verify actual destination artifact identities and availability, record publication evidence and reconcile incomplete obligations.

Candidate, assessed release and published release are workflow descriptions, not new canonical states. Approval can be described as approved for stated scope, blocked, or approved with explicit limitations; it does not replace canonical error, finding or lifecycle vocabulary.

## 5. Release subject, build identity and freeze boundary

The release subject is an owner-issued stable reference-runtime release identity/version plus the exact covered distributable artifact set and its material interpretation. It identifies source/build identities and mapping, build environment assumptions and material dependency inventory; canonical SPEC/Contract/Port/Capability versions; reference package/distribution versions; built-in Plugin/Adapter releases and owning contributions; supported CPython/runtime range; configuration contracts/effective revisions or bounded qualified configurations; state/evidence interpretation ranges; claimed migration rules and qualified external targets where relevant.

Source identity and artifact identity are related but different. Rebuilding the same commit may produce different bits or dependencies. Bind the actual assessed artifacts, including each member of a multi-artifact release, and preserve enough provenance to answer what was released, from which inputs, against which contracts, with which evidence and decision. No hash format, signing system, SBOM standard or reproducibility level is selected. Integrity/authenticity must satisfy the governing evidence rule; a mutable filename or tag cannot establish it.

Freeze occurs before evidence is attached to the candidate for decision: record exact artifacts/inputs and scope at an immutable candidate revision. Development elsewhere may continue. A changed artifact set, material dependency or configuration meaning creates a new candidate subject/revision and an impact review. A new assessment of unchanged bits may instead produce a new assessment revision. Neither silently changes the old record. Build-time evidence may be mapped to the frozen artifacts only through adequate provenance establishing its applicability.

Immediately before approval, pin the exact combined evidence set, requirement closure, compatibility targets, policy/exception references and proposed scope. This second binding fixes the assessment inputs, not live authority forever. Subsequent invalidation or policy/revocation changes must be considered at the protected approval/publication boundary; unknown mandatory currentness blocks the action.

Reproducible builds are a separate evidence-backed claim. Inability to reproduce later does not automatically invalidate evidence for exact retained artifacts, but cannot justify replacing them with a different rebuild. Unpinned material dependency drift invalidates equivalence to the assessed subject. No vendoring rule is introduced.

## 6. Baselines, materiality and impact closure

Use an exact previous accepted published release and its assessment/evidence set as the usual comparison baseline. Other declared supported interoperability or upgrade targets may also be baselines. Record exact metric/criteria/case versions for regression comparisons. Never use an unresolved latest/current-production selector. A first release records no prior-release baseline and establishes its own scope evidence; it does not fabricate a no-regression conclusion.

A change is material when it can affect the truth of a claim or the applicability/sufficiency of its evidence. Analyze source/build differences together with contract/metadata changes, configuration semantics, dependencies, declared behavioral changes, environment/runtime changes, external target behavior, security knowledge and threat/failure assumptions. Diff size, file count, patch label and unchanged signatures are not materiality proofs.

Trace changes through affected contracts/owners/guarantees, their transitive dependents and interactions to proof obligations and claims. Include test/evaluator changes themselves: a different oracle, dataset or collector can alter what a passing result establishes. Incomplete impact knowledge expands the required proof scope; if uncertainty cannot be resolved by broader adequate evidence, the claim remains insufficient.

| Workflow analysis category, not canonical status | Evidence consequence |
|---|---|
| Documentation / release-note rendering | Assess claim wording, packaging/publication or privacy effects; reuse runtime proof only if relevant artifacts/behavior/assumptions are unchanged. |
| Internal implementation / API-additive change | Check behavioral, failure, resource and transitive effects before reuse; additive syntax does not establish immateriality. |
| Contract or compatibility-affecting | Reassess affected version relations, consumer behavior, boundaries, extensions and migrations. |
| Security / tenant / authority | Regenerate affected enforcement/adversarial proof, including transitive action boundaries even with unchanged APIs. |
| Persistence / migration | Requalify ADR-004 durability/history/recovery and ADR-008 identities/results/obligations plus migration boundaries. |
| Dispatch / retry / resource / Approval | Reassess ADR-007 acceptance/order and ADR-008 equivalence/provider horizons; conserve liability and consumed uses. |
| Plugin bootstrap / admission / lifecycle | Reassess ADR-006 finite roots, stage boundaries, contribution eligibility and stop/publication interactions. |
| Evidence custody / interpretation | Requalify ADR-009 custody, availability, recovery and privacy; inspect every claim relying on changed custody assumptions. |
| Runtime, dependency or Provider | Reassess relevant environment/guarantee mappings, freshness and replacement behavior; unchanged application source is insufficient. |

Automation may propose impact mappings; accountable review resolves semantic uncertainty. Record the reviewer, criteria, subject, scope, time and limitations. Undocumented maintainer memory is not reusable evidence.

## 7. Requirement applicability and scope reduction

Use the CONF-060/063 clause-level coverage ledger. Each cited canonical requirement keeps its original ID/version, normative strength, applicability predicate and rationale, supported subject/scope, transitive dependencies, proof obligations, expected/forbidden observations, evidence/sufficiency rule, current finding and remaining gaps. A suite inventory is an input, not the authority for the requirement denominator. Expand all relevant clauses before a full-scope claim; do not stop at family-level matrices.

Preserve the Conformance judgments exactly:

| Judgment | Release consumption |
|---|---|
| conformant | Adequate proof of every applicable mandatory obligation for that scope; still not release authority. |
| nonconformant | Known applicable mandatory violation; blocks any claimed conformant scope containing it. |
| not assessed | No conclusion attempted; never a pass. |
| insufficient evidence | Missing, stale, contradictory, uninterpretable, irrelevant or inconclusive proof prevents a supported positive conclusion. |
| not applicable | Applicability predicate demonstrably does not activate; reason retained. |
| unsupported scope | Genuinely excluded feature outside mandatory closure; no satisfaction implied. |

Applicable, excluded-with-reason, assessed, violated, unassessed and insufficiently evidenced are coverage dispositions under CONF-063. “Not implemented” and “blocked” may describe implementation/work gaps but do not create new Conformance judgments. SHOULD recommendations retain their upstream treatment and rationale. An empty applicable set cannot establish implementation behavior.

Define scope before conclusion. If an independent optional feature cannot be supported, retain the original broader finding/failure, create a separately bounded scope/finding, recompute its full mandatory and transitive closure, verify isolation of the excluded path and publish the exclusion. Do not relabel a failed foundational obligation optional or hide a valid counterexample by deleting it from the denominator. A foundational tenant, authority, evidence, effect or resource failure cannot be excluded while still claiming the dependent capability. Code presence alone never establishes supported scope.

## 8. Evidence ledger, reuse and invalidation

Ordinary references represent Claim → Requirement → Proof obligation → Evidence/finding → exact subject/version/configuration/environment → producer/custodian. No graph database is required. Release assessment consumes contract validation, component/integration/race/security tests, Evaluation and Conformance results, compatibility/migration and Plugin/Adapter qualification, static/type/build/package checks, dependency/provenance evidence and manual review as applicable. No category is universally sufficient.

Every relied-on item identifies producer/assessor, exact source and subject versions, method/criteria/interpretation, scope/configuration/environment/dependencies, time and freshness assumptions, coverage, limitations, counterevidence and ADR-009 custody/access guarantees. A report file or evidence identifier alone does not establish qualified custody, retrievability or interpretability. Required pre-decision custody must be established before approval; unknown custody cannot be treated as success.

Reuse requires all relevant subject portions, requirement meanings, interpretation, configuration/contract semantics, implementation, dependencies, environment, threat/failure assumptions and sufficiency to remain unchanged or have an explicit justified equivalence mapping. Custody and current applicability must still hold. For each item record its exact original reference/subject, mapped candidate obligation, unchanged conditions or equivalence proof, change-impact exclusions, review authority and rationale. Reuse references the old item rather than forging a new observation time or copying it as newly produced evidence.

For example: E17 may support candidate C2's dispatch obligation only if the mapped dispatch subject, requirement/version, dependency/clock/storage assumptions and custody remain applicable and the reviewed change closure cannot affect that guarantee. “Patch release,” “file untouched” or “passed last time” is insufficient. A new Conformance finding binds the candidate and combined justified evidence set; an old pass label is not transferred wholesale.

Invalidation records the affected item/obligation/claim, changed condition or evidence gap, time, reason, responsible assessor and required next proof. Old evidence remains historical and is excluded from current proof where invalid. Subject/contract/configuration/dependency changes, unsupported interpretation, threat/failure changes, provider drift, security findings, expiry, loss or unavailable custody can invalidate applicability without altering old content.

Time alone is not a universal freshness rule. Static proof for immutable subjects can remain applicable; mutable provider behavior, vulnerability knowledge or environmental qualification may have declared observation windows, expiry or event triggers. Accountable owners specify actual bounds; no global TTL is invented. A new assessment timestamp cannot refresh old observations. Retain needed evidence for declared support/claim intervals subject to governed disposition; no indefinite retention or legal precedence is created. Where permitted loss/disposition prevents proof, state that limitation and restrict dependent current claims.

## 9. Missing, failed, partial, contradictory and flaky evidence

Mandatory collection failure, unavailable Evaluation, blocked Conformance, missing interpretation, inadequate access or stale evidence blocks the affected positive claim unless an independently valid narrowed scope is assessed. Infrastructure failure is not subject success; distinguish assessment execution failure from a demonstrated behavioral violation. Use canonical errors where operationally appropriate, such as VersionMismatch, DependencyFailure or AuthorizationDenied, with truthful effects and obligations rather than new release error categories.

Partial evidence supports only the observed capability, version, configuration, tenant model, failure mode or provider scope. Do not extrapolate to all environments. Known valid mandatory counterexamples dominate positive averages. Conflicting credible evidence requires attributable investigation and resolution; unresolved uncertainty is insufficient evidence, and established violations remain nonconformant. Preserve the favorable and unfavorable source records.

A fail followed by pass retains both attempts, their inputs, nondeterminism and cause/disposition. A passing rerun does not erase failure. A tooling/environment fault may be resolved as such only with evidence that justifies the inference; unexplained flakiness cannot support a required deterministic guarantee. Fixes create a new candidate if bits/meaning changed, then a new assessment. If only new evidence or corrected interpretation changes, issue a linked assessment revision for the same subject.

Known non-blocking issues may be admitted only under the applicable release policy and must show scope, impact, affected claims, workaround and residual risk. An exception is valid only where the actual upstream rule expressly permits it: record entitled issuer, rule/version, exact scope, basis, evidence, compensating conditions, duration/review and revocation. Risk acceptance does not waive a canonical MUST, erase a failure or invent Q-05 precedence. Mandatory unresolved authority conflicts block the affected claim.

## 10. Evaluation and Conformance integration

Evaluation Management retains ownership of Evaluation attempts/results; Conformance assessors retain their findings. Release consumes exact references. Validate subject/conditions, evaluator method/authority/required independence, dataset relevance/contamination, coverage, integrity/custody, freshness, uncertainty and limitations under EVAL-079. Execution success, good score and model judgment cannot appoint a release authority.

For stochastic assessments retain dataset/case membership and versions, model/provider version, evaluation configuration, sampling/runs, aggregation, uncertainty and the predeclared threshold/stopping rule. No single stochastic run becomes deterministic enforcement proof. No new business-quality threshold, numeric risk tolerance or Q-06 resource limit is selected. Record exact regression baselines; no regression does not imply Conformance, and a measured regression blocks release only under an applicable rule or violated requirement.

Conformance assesses full mandatory closure using sufficient methods, negative/failure cases and component interaction evidence. Component passes do not imply composition conformance. Self-assessment is labeled first-party; independent assessment requires substantiated independence, not merely a different process or signature. No official profile, badge, certifier or certification authority is created. Until governed profiles exist, publish an explicit bounded supported contract set and absence of an official profile reference.

Prior Evaluation or Conformance may contribute through §8's exact applicability mapping, including unchanged cases/criteria/assumptions and preserved counterevidence. A new target's release assessment cannot silently change the prior source finding. Inaccessible restricted evidence counts only through an adequate authorized summary/attestation accepted by the governing proof rule, with what was inspected stated explicitly; otherwise the finding remains insufficient.

## 11. Compatibility dimensions and bounded matrices

Compatibility findings identify subject A, subject B, direction, dimension, contract/version or range, supported operation/path, environment/configuration, result, evidence and limitations. No global `compatible=true` replaces them. A support matrix identifies what this release supports; a compatibility matrix identifies specific relations it can preserve. Include only claimed upgrade/interoperation paths and relevant range boundary cases, not an exhaustive Cartesian product.

| Dimension | Required assessment for a claimed relation |
|---|---|
| Contract / public API | Canonical language-neutral behavior, valid inputs, outputs, errors, authority, tenant, resources/effects and guarantees; source/API compatibility where exposed, not just signature shape. |
| Configuration | Exact prior contracts/materialized revisions, effective meaning, defaults and retained activation bindings; explicit transformations rather than reinterpretation as latest. |
| State | Owner-specific read and mutation compatibility, durable identities/revisions, history, retained results, obligations, liabilities and crash/recovery boundaries. |
| Plugin | Declaration, admission, initialization, activation, contribution versions, configuration and recovery independently; old Plugin/new runtime and reverse only for claimed combinations. |
| Adapter / Provider | Consumer-visible semantics and declared enhancements, actual external targets/versions, failure and retry/effect coverage; no universal provider promise. |
| Runtime | Actual qualified CPython/runtime and material environment/dependency assumptions, storage/time/isolation scope; no invented OS matrix or untested range. |
| Data / Evidence interpretation | Exact historical formats/semantics, protected access, readers/references, integrity, custody and required retention; no latest substitution. |
| Migration | Authorized source-to-target transformation, preconditions, loss, preserved history/effects/accounting, coexistence, validation and recovery/rollback limits. |

Backward compatibility means the named previously supported consumer/state/Plugin/configuration/evidence paths retain their promised behavior, or have a clearly stated required governed migration. A breaking change invalidates such a promised relation without that adaptation; removing required semantics, narrowing inputs or weakening safety can break compatibility with unchanged API syntax. A compatible addition may still be material for security, cost or failure proof.

Forward compatibility with arbitrary future versions is not promised. Unknown mandatory semantics produce explicit VersionMismatch/unavailability as appropriate; optional extensions can be omitted only under their declared safe omission rule. Do not infer support from matching numbers. Preserve SPEC V-02, CTR-064 and PLG-008 semantic major/minor/patch rules, explicit initial 0.x compatibility and prerelease/range rules where they already apply. This ADR does not impose a new SemVer/CalVer convention on reference-runtime release identifiers.

Each support statement names release/artifacts, governing versions, supported concepts/capabilities/operations, Plugin and Adapter versions/ranges, configuration/state/evidence interpretation, qualified environments/topology, failure/security assumptions, external combinations, limitations and known unsupported features. Inapplicable dimensions have reasons. Do not use undefined alpha/beta/GA/production-ready labels or unqualified “Lego AI compliant,” “fully supported,” “secure” or “backward compatible.”

## 12. Migration, configuration, Plugin and effect compatibility

For each claimed N → N+1 upgrade, pin source/target release and owner state/configuration/evidence contracts, permitted transformation, responsible owners, authority/tenant/resources, preconditions, semantic loss/limits, validation and partial-failure behavior. Demonstrate preservation of IDs/revision lineage, prior results, operation/effect equivalence, original preconditions, consumed Approval, charges/unknown liabilities and outstanding evidence/repair obligations. Startup or a fresh-install test cannot establish migration success.

The actual supported sequence includes new release validation/admission/initialization/activation, offer publication, explicit binding changes, disposition of in-flight work and old release stopping/retirement where applicable. Assess coexistence, partial migration and stop failure without inventing a global transaction or new Plugin state. “No migration needed” is itself an evidence-backed compatibility finding.

ADR-003 requires exact old configuration interpretation and retained activation binding semantics. Unknown old contracts are unsupported/unavailable; they do not inherit new defaults. A transformation creates explicit new revisions and lineage. ADR-006 requires all built-in Plugin stage and contribution proof, including restart/recovery; importing P or matching its declaration range does not establish admission or safe activation.

ADR-007/008 changes to acceptance, exclusivity, deadlines, resource accounting, Approval use, effect identity, equivalence, provider retry, retained results or horizons regenerate relevant order/concurrency/crash/reconciliation evidence. Unchanged method signatures do not permit reuse. Old retained evidence and operation descriptors require supported exact interpretation or an explicit unavailable path that blocks dependent recovery guarantees.

Publish only evidenced upgrade paths, for example an assessed immediate predecessor relation or an explicitly required intermediate transformation. Downgrade is a separate directional claim and is unsupported unless qualified. Deployment rollback may switch software but does not undo effects or guarantee that old code understands newer state. An old snapshot cannot restore revoked authority, expired Secret validity, unused Approval or copied resource balances. Irreversibility and intervention obligations remain visible.

## 13. External qualification and freshness

Each external support row binds owning Plugin, exact Adapter version, Provider identity/API version or qualified behavior range, target/account/environment assumptions, supported operations, time/observation scope, failure model, retry/effect guarantee, limits and exact evidence. A fixture/simulator proves only its declared scope; provider marketing, compatible payload shape and mocked timeout tests cannot establish real-provider deduplication or effect truth.

Provider behavior can change without a new local release. Declare freshness triggers and any authority-supplied validity bounds, known mutable dependency assumptions, affected claim owner and reassessment disposition. Before relying on current support, ascertain required applicability; if it is unknown or invalid, the provider-specific claim is insufficient/stale rather than automatically refreshed by an old pass. This does not design continuous production monitoring.

Conditional support is permitted: Adapter X under declared qualification conditions may support guarantee G only when those conditions and evidence remain valid. Do not call an unresolved dependency condition satisfied. If optional Provider proof fails, remove that independent support relation through a new bounded assessment while retaining the broader failure; core support can remain if its closure is independent. Provider replacement also preserves ADR-008 effect history; qualification does not authorize redispatch of unknown work.

## 14. Manifest, outputs and ownership

Select a conceptual **release evidence manifest**: an exact immutable assessment input set of references, not a JSON/YAML schema or runtime Plugin/deployment/configuration manifest. It identifies candidate/artifact identities; source/build/dependency provenance; governing versions; explicit supported scope and absence or exact references of governed profiles; applicability/proof ledger; new/reused Evidence and reuse reasons; Evaluation/Conformance findings; compatibility/support matrices; external qualification; migration paths; known issues/gaps; valid exceptions; decision/reviewer references; freshness/retention limits and publication obligations.

The assessment record binds baseline, materiality analysis, exact manifest revision, compatibility findings and governing gate rule, approved/blocked scope, responsible reviewers and current decision authority. Published decisions/findings are immutable historical facts; correction/supersession is linked new work. An approval outcome's own custody and any post-decision obligations are separately recorded under ADR-009; do not require a circular manifest that must already contain its future approval receipt.

Conceptual outputs are the identified release artifact set, support/scope statement, compatibility/migration findings and notes, evidence manifest/coverage ledger, change/materiality record, Evaluation/Conformance references, known limitations/exclusions, attributable gate decision and publication/verification facts. Human release notes and changelog are projections, not authoritative evidence or compatibility proof. This ADR produces only this decision document, none of those operational artifacts.

Use existing responsibilities: Governance owns release authorization/policy decisions; the bounded reference release workflow coordinates evidence and records its assessment facts through existing Artifact/definition/provenance facilities. Compatibility analysis is part of this workflow and applicable Conformance assessment, with Plugin admission compatibility still owned by Plugin Lifecycle. No new semantic Release subsystem or Kernel owner is introduced. Evaluation owns its results, Conformance its findings, Evidence its custody and Lifecycle/Catalog their Plugin/offer states. Release cannot edit those source facts.

## 15. Release authority and final gate

For the initial reference release, select explicit approval by the accountable Human maintainer acting as a currently entitled release Principal under Governance. This applies to an actual scoped release claim, not every edit or test run. It is first-party release approval, not independent certification. Later automation can execute a separately governed bounded rule, but CI status or Agent output never self-appoints that authority.

Bind acting Principal, requester, tenant/application jurisdiction where applicable, exact candidate/assessment revision, applicable Policy/Grant and required Approval references, decision, limitations, attributable time/order and evidence. Repository membership, ambient OS identity or a maintainer display name is not proof of entitlement. Separation of duties applies when required; a solo maintainer cannot declare independence from themself.

The final gate verifies artifact/input exactness; complete mandatory closure and sufficient current evidence; required ADR-009 custody; valid compatibility/migration claims; resolved mandatory counterevidence; explicit remaining exclusions and allowed exceptions; currently entitled authority and resource/effect constraints. It records blocking obligations if mandatory evidence/authority or compatible state is unavailable. Release policy may add quality conditions but cannot override canonical MUSTs or change Conformance findings.

Agents may collect data, run bounded checks, propose impact mappings and assemble draft manifests. Deterministic validation plus governed accountable review is required before accepting their output. Model judgment can contribute only under its declared evidence method; it cannot establish compatibility, security, Conformance or release approval by assertion. All release work remains resource-governed; no unlimited CI/model/provider spend is assumed.

## 16. Publication, binding and partial failure

Publication is separate governed work against an exact approved artifact set and assessment reference. Before its protected handoff verify current publication authority, decision applicability, required evidence and exact artifact identity under ADR-005/007/008/009. A queued job cannot substitute latest branch/tag output for assessed artifacts. If required validity cannot be maintained at the boundary, refuse publication. Do not hold a global transaction across Evidence, Evaluation, Conformance, release decisions and an external registry.

Approval success does not imply publication success, and published bytes do not prove gate success. Record attributable destination, attempted artifact identities, actual known effects, availability and remaining obligations. After publication verify that destination artifacts match the assessed set. B substituted for assessed A is not the assessed release; its support/Conformance statements do not apply. Record mismatch and authorized correction/withdrawal duties, including supply-chain incident scope, rather than retroactively blessing B.

On known publication failure, the historical assessment survives and the publication obligation remains. Reuse it only if exact subject, scope/evidence applicability and current publication authority still hold. Do not rerun expensive unchanged assessments automatically or rebuild different bytes under the same identity. On unknown delivery/acknowledgment, use ADR-008 status/reconciliation or a demonstrated equivalent retry; do not blindly republish. No exactly-once registry operation claim is made.

Partial multi-artifact publication records which artifacts are verified, missing or unknown; it does not claim complete availability. If publication happened but evidence recording failed, keep the known/unknown publication fact and repair the evidence obligation under ADR-009 without repeating a confirmed effect. Source-owner durable obligations must exist before an external action can create an untracked gap.

Changing destination or adding a mirror may require destination-specific authority, trust, disclosure and publication evidence. It need not rerun unrelated behavioral proof if the exact artifacts and applicable assumptions remain unchanged. Mirrors do not create new compatibility findings. Credential-bearing publication itself triggers the Secret prerequisite even if the runtime being released is Secret-free.

## 17. Reassessment, restriction and historical interpretation

New security findings, compatibility counterexamples, provider/dependency drift, invalidated evidence or changed support rules trigger a linked assessment/advisory. Same bits with new findings create an assessment revision; different bits or configuration meaning create a new candidate. Preserve original inputs, evidence, approvals and publication facts. A newer finding can supersede applicability for future claims without rewriting the old finding.

The authorized claimant/release authority may restrict or withdraw a supported claim with affected release/version/scope, reason, effective time and required publication/notification obligations. An assessor may publish correction/invalidation evidence without pretending to be that claimant. Historical download availability and currently asserted support are different facts. Claim withdrawal neither revokes a Plugin nor undoes deployment effects; operational action needs its separate owner and authority.

A security defect may leave artifacts downloadable while their affected security/support claim is withdrawn. Preserve sufficient historical interpretation, including the original definitions and exact evidence mapping. Later Evidence loss can make current verification unavailable without proving that the release never existed or never behaved as recorded. Public statements must expose material verification limits; do not reinterpret old evidence as latest or silently retain an unprovable current claim.

## 18. Security and privacy analysis

| Threat / failure | Treatment and residual limitation |
|---|---|
| Stale reuse | Exact applicability rationale and transitive impact review; fresh timestamps cannot refresh old observations. Incomplete mapping blocks affected proof. |
| Artifact substitution / tampered manifest | Frozen artifact and manifest revisions, owner guards, current authority and destination identity verification; integrity mechanism must be qualified later. |
| Hidden CI bypass | Explicit gate rule and clause ledger independent of pipeline checks; skipped mandatory proof remains visible. |
| Agent self-approval | Agent proposes only; entitled release decision is separate and attributable. |
| Cross-tenant evidence disclosure | ADR-005/009 current access, purpose and safe references; public projection cannot reveal tenant data, Principals, raw Secrets or protected exploit details. |
| Supply-chain dependency drift | Exact material inputs/provenance, inventory and impact reassessment; same source commit does not prove artifact equality. |
| Provider qualification drift | Separate freshness/assumptions and bounded claim restriction; no universal provider or production-monitoring promise. |
| Waiver abuse | Only expressly permitted exceptions with actual entitlement, scope, expiration/review and controls; non-waivable obligations persist. |
| Flaky evidence cherry-picking | Preserve every material failure/rerun and explain disposition; no favorable-average substitution for a counterexample. |
| Historical evidence loss | Governed retention and explicit availability/interpretation limits; restrict claims that need inaccessible proof. |
| Resource exhaustion / recursive proof | Bounded assessments, finite dependencies and existing ADR-006/009 roots; do not demand an infinite chain of self-certification. |

Internal detailed records may be access-controlled; public reports use safe summaries or permitted attestations and never claim more than internal proof. Redaction cannot convert uninspected evidence into inspected proof or waive mandatory internal custody. No private chain-of-thought, legal signing scheme or unrestricted diagnostic disclosure is required. A clean vulnerability scan establishes only its scoped observation, not a universally secure release.

## 19. Minimal first-release scope and conditional decisions

The first supported slice may be a deterministic direct Capability with a qualified local Adapter/Provider, explicit tenant/Principal enforcement, configuration revisions, owner-local persistence, built-in Plugin bootstrap/admission, Evidence custody, dispatch/resource arbitration and operation deduplication/reconciliation. Qualify its complete universal/conditional closure and interactions. CPython 3.14 follows ADR-001; exact patch/environment support must be demonstrated, not assumed for all OSes or future runtime versions.

It need not support Agent, Model, Team, Workflow, Memory, RAG, distributed deployment or multi-service high availability merely because abstractions exist. Unrelated optional systems are not required test dependencies. Necessary Evaluation and Conformance can use deterministic methods with existing finite admitted roots, without AI. This is a bounded supported set, not a newly named official base profile.

| Conditional feature | Gate without adding canonical ADR-011 dependency edges |
|---|---|
| Secret-bearing Adapter, identity/bootstrap credential or publication path | ADR-010 must be accepted and the path qualified before support/use. Without it, exclude/block the actual Secret-bearing path; a separately authorized Secret-free path may proceed. |
| Hostile/untrusted Plugin execution or claimed effective containment | ADR-012 and its actual isolation proof are required. Trusted-host scope remains assessable with explicit threat limits and mandatory applicable controls. |
| Production observation/operational diagnostic guarantees needing integration | ADR-013 and corresponding evidence are required for that claim; basic mandatory evidence/observation duties remain and cannot be removed by excluding production telemetry. |

ADR-011 canonically depends only on ADR-006/008/009. None of ADR-010/012/013 is created here. Minimal scope is a future qualification target, not a statement that the runtime is already implemented or releasable.

## 20. Structural walkthroughs

### W1 — Direct deterministic Capability

Freeze R and its local built-in Adapter/configuration. Declare explicit tenant, qualified local failure/threat scope and no optional AI. Close requirements for admission, authority, persistence, custody, resource/Approval ordering where applicable and effect/retry semantics. Gather component plus interaction/race/recovery evidence; qualified deterministic Evaluation and Conformance produce their separate findings. The entitled maintainer may approve that exact bounded release once the gate passes. No Agent/Model/Team/Workflow/Memory/RAG proof is manufactured or demanded.

### W2 — Built-in Plugin P and bootstrap change

Bind P's exact release, contributions, owning Provider/Adapter, configuration and host roots. Assess declarations separately from admission, initialization, activation, offer eligibility and restart/recovery. Include finite dependency bootstrap and delayed publication/stop races. If admission/bootstrap code changes, invalidate relevant ADR-006 proof and transitive eligibility assumptions. Qualify only declared combinations; P's success does not promise external-ecosystem compatibility.

### W3 — N to N+1 upgrade

Pin N's state/configuration/evidence families and N+1 artifacts, including old operation outcomes and in-flight unknown effects. Assess reading and mutation separately; execute or otherwise adequately prove the declared migration and partial-failure sequence. Preserve identity lineage, liabilities, consumed uses, historical readers and current authority. A fresh-install pass does not establish N → N+1. Unsupported direct older upgrades and downgrade remain explicit.

### W4 — Optional external Provider

Bind Adapter/API/target/failure/retry scope and real qualification evidence. Keep simulator-only coverage separate. If evidence is stale or Provider behavior changed, block that support relation; assess a new core-only scope if independent. Secret-bearing use additionally requires ADR-010. New Provider support cannot reset ADR-008's prior effect history.

### W5 — Release-note rendering only

Compare exact N/C2 subjects. If renderer change cannot affect runtime artifacts, contract statements, dependencies, privacy or failure assumptions, map prior security/dispatch evidence with explicit unchanged-subject rationale. Assess the changed notes/rendering and publication input relationship. If rebuilt runtime bits differ, establish actual equivalence/material impact; same source is insufficient. Issue a new assessment for the exact combined set.

### W6 — Security boundary change

An authorization implementation changes with identical public signatures. Trace tenant/Principal/Grant enforcement through dispatch, status/result disclosure and publication. Invalidate mapped security and interaction proof, regenerate required adversarial/currentness cases and retain old evidence historically. A happy-path pass cannot discharge those obligations.

### W7 — Persistence realization change

Replace owner storage while contracts stay constant. Requalify ADR-004 conditional commits, durability, history, crash and absence semantics; ADR-008 duplicate results/obligations; migration with outstanding liability and ADR-009 custody dependencies. Unchanged logical schemas and successful startup do not prove failure behavior. Refuse unsupported restore/downgrade relations.

### W8 — Provider retry change

A transport library gains automatic retry or provider retention changes. Trace hidden sends, key/effect mapping, current authority, horizons, resources and lost acknowledgment. Regenerate ADR-008 real-provider qualification and ADR-007 handoff evidence where affected. Preserve earlier failures; disable/exclude unqualified retries rather than broadening the guarantee.

### W9 — Evidence custodian change

Change custody realization or historical interpretation. Identify every dependent release finding, requalify ADR-009 pre/post-effect acknowledgment, loss, recovery, privacy and exact references. Preserve original source evidence and custody history. New storage availability alone does not validate migrated content or make old gaps disappear; required unknown custody blocks approval.

### W10 — Conditional feature expansion

Adding Secret use, hostile Plugins or a production-diagnostics guarantee activates its conditional ADR and proof obligations. Until accepted and qualified, record unsupported scope and prevent that path's activation. A new independently bounded core assessment may still succeed; the broad requested scope's failure remains visible. Excluding a label does not remove a Secret already used by bootstrap or publication.

## 21. Twelve release/failure timelines

### Timeline 1 — Unchanged release evidence reuse

1. N has an exact accepted assessment/evidence set. C2 changes an unrelated presentation area.
2. Impact review establishes unchanged relevant subject/requirements, dependencies, assumptions and custody for E17.
3. Record original E17 and reuse authority/rationale in C2's ledger; assess affected presentation work separately.
4. New C2 finding binds the combined evidence; no old observation is redated or pass label blindly copied.

### Timeline 2 — Material security change

1. Candidate changes an authorization boundary, leaving APIs unchanged.
2. Impact closure invalidates affected security and interaction evidence for the new claim.
3. Required fresh proof and custody are obtained or the claim stays blocked.
4. A new finding references old historical counterevidence and new results; mandatory violation cannot be waived by schedule pressure.

### Timeline 3 — Candidate changes after assessment begins

1. C1 pins artifact A, configuration meaning and dependency set.
2. Source/build/dependency changes produce C2/B while C1 assessment continues.
3. C1 evidence remains bound to A. C2 needs impact/reuse assessment and its own exact binding.
4. Publication of B under C1 approval is refused; unrelated repository development need not stop.

### Timeline 4 — Required evidence unavailable

1. Required Evidence custody/content/interpretation or Evaluation/Conformance result is unavailable.
2. Gate records insufficient evidence or not-assessed scope as appropriate, plus repair/intervention duty.
3. Mandatory affected approval is blocked; an independent narrower scope needs its own closure/finding.
4. Restored access does not automatically refresh old observations or authorize publication.

### Timeline 5 — Contradictory evidence

1. Happy-path A passes; valid failure scenario B violates a mandatory boundary.
2. Retain both; the scope containing B is nonconformant regardless of average score.
3. Fix/reassess or produce an honestly independent narrowed scope with the broad failure retained.
4. If the observations instead remain unresolved/credible conflict, record insufficient evidence; do not cherry-pick A.

### Timeline 6 — Flaky test

1. Initial run fails; a second identical-looking run passes.
2. Record both attempts, environment and uncertainty; investigate tool error versus subject nondeterminism.
3. Governed disposition must justify proof sufficiency or leave the obligation blocked/violated.
4. Neither rerun count nor a favorable aggregate erases a relevant counterexample.

### Timeline 7 — Publication artifact mismatch

1. Gate approves exact A; a destination exposes B under the expected name.
2. Identity verification detects substitution; B is not covered by A's approval or support claim.
3. Record known/unknown publication effects and entitled correction/withdrawal obligations.
4. Independently assess B if intended; never rewrite A's assessment to bless it.

### Timeline 8 — Publication fails after approval

1. Scoped assessment/approval commits; required publication attempt obligation exists.
2. Publication fails or acknowledgment is lost; multiple artifacts may be only partly available.
3. Keep assessment history, exact artifact availability/uncertainty and outstanding duties.
4. Query/reconcile unknown effects; retry only under ADR-008/current authority and still-applicable assessment. Repair post-publication evidence without replaying confirmed publication.

### Timeline 9 — External qualification becomes stale

1. R remains published; its optional provider/API or relevant validity assumption changes.
2. Old observation no longer supports the required current provider claim.
3. Record linked reassessment and restrict/withdraw that claim through the entitled claimant; requalify before restoration.
4. Independent core scope may remain supported; no new local release timestamp cures provider staleness.

### Timeline 10 — Historical state migration fails

1. N+1 fresh installation passes; migration of actual supported N state fails.
2. Record source/target, partial owner changes and preserved effects/liabilities/obligations.
3. Block N → N+1 compatibility; fresh-install evidence cannot substitute. A distinct fresh-only scope needs explicit assessment and exclusions.
4. Repair/migrate under entitled owners; installing N again is not proven downgrade or authority restoration.

### Timeline 11 — Security issue after publication

1. R was published under assessment A1; new finding exposes a mandatory security defect in supported scope.
2. Preserve A1 and produce linked A2/advisory identifying affected releases/claims and counterevidence.
3. Entitled authority restricts/withdraws affected support and records notification/remediation duties.
4. Historical artifacts may remain available; operational Plugin/deployment changes require separate authorization and do not erase past effects.

### Timeline 12 — Optional unsupported feature

1. Core has adequate proof; optional Agent/Secret/hostile-Plugin scope lacks it or its conditional ADR.
2. Retain broad gaps and demonstrate the feature is independent of core mandatory closure.
3. Issue a bounded core finding/manifest with visible exclusions and no claim that package inclusion equals support.
4. Approve only that exact core subject if all gate conditions hold; any hidden dependency on the excluded path instead blocks it.

## 22. Failure model, consequences and solo burdens

This is a local-first workflow over existing owner-local durable records. Candidate freeze failures, missing Evidence, unavailable Evaluation, blocked Conformance, incompatible migration, artifact mismatch and stale external qualification prevent affected approval/publication. Post-approval/publication failures preserve committed facts and obligations. External outages or lost acknowledgment do not receive a new transaction or exactly-once guarantee. Guarantees inherit qualified ADR-004/007/008/009 failure scopes; no stronger storage or distributed profile is claimed.

| Solo-developer burden | Selected mechanism and tradeoff |
|---|---|
| Implementation complexity | Explicit records/refs and deterministic completeness checks; more than a checklist, less than a new release service. Tooling may automate incrementally. |
| Operational complexity | Local execution and visible repair obligations; external qualification/custody still require attention. |
| Maintenance burden | Maintain requirement/impact mappings and interpretation history; reusable evidence avoids repeating unrelated work. |
| Testing burden | Target affected and transitive guarantees, retain failure cases; broad rerun when impact cannot be bounded. |
| Local-development burden | No cloud CI/registry/certifier required; exact environment and artifacts still need recording. |
| Deployment burden | Publish exact approved artifacts through later replaceable tooling; runtime deployment and Plugin activation remain separate. |
| Learning curve | Distinguish subject, proof, finding, approval and publication; tables/refs make that separation inspectable. |

Positive consequences: repeatable scoped claims, traceable reuse, less redundant AI/provider assessment cost, explicit upgrade promises, historical accountability and local operation. Negative consequences: mapping/review work, retained evidence storage, conservative release delays and potentially substantial provider qualification effort. The initial release has little reusable evidence; C does not promise cheap first-time proof.

Accepted operational risks are finite evidence coverage, human impact-analysis fallibility and mutable external services within declared limits. The release maintainer owns the mapping/review risk, subject assessors own proof limitations, Evidence owners custody and qualified Adapter owners provider assumptions. Mitigations are transitive closure, negative/interactions proof, explicit uncertainty, attributable review, trigger-based reassessment and refusing claims exceeding evidence. Mandatory gaps are blockers, not accepted waivers. These risks require review on material changes or contrary evidence; this ADR invents no risk tolerance threshold.

## 23. Type-2 migration and sensitivity

The workflow is Type 2 because canonical contracts and semantic owners remain external, Evidence references remain stable, decisions are bounded records and build/CI/publication tooling remains replaceable. A later local tool or release platform can replace the coordinator without changing what compatibility, authority or Conformance means. Published historical facts themselves are not reversible merely because the workflow is.

Migration must preserve exact release/artifact identities, baseline/impact records, assessment history, compatibility findings, evidence references and interpretation, exclusions, approving authority, freshness/disposition history and pending publication/repair obligations. Validate the new tool's mapping and completeness rules before it issues decisions. Do not replay prior publication effects, lose unknown operations, collapse partial findings or silently reinterpret old assessments. Scope and claim history must remain accessible under the same governed constraints or be explicitly unavailable.

Reconsider when multiple maintainers, a public Plugin ecosystem, many external Providers, larger compatibility matrices, regulated release obligations, an independently authorized certification scheme, a release engineering team, additional SDK languages or multi-service deployment make coordination burdens material. These may justify more automation, independent review or stronger tooling; none is built or assumed here.

## 24. Proof obligations and decision boundary

Before operational use, demonstrate exact candidate/artifact binding; clause-level closure independent of suite inventory; impact/reuse justification including transitive interactions; evidence custody and interpretation checks; current authorized gate/publication; all eight compatibility dimensions; state/configuration/Plugin/effect-history migration; stochastic and flaky evidence handling; provider freshness; partial publication/reconciliation; safe public summaries and linked reassessment/withdrawal. Instantiate §21's twelve timelines against actual storage, runner and publication realizations with qualified failure assumptions.

Future evidence must also demonstrate that support exclusions are independent, self-assessment is labeled honestly, an Agent/CI cannot bypass approval, and the minimal direct Capability needs no optional AI dependency. Test fixtures can prove workflow decision rules but cannot qualify an external Provider or storage implementation merely by simulation.

No upstream contradiction was identified for this mechanism. In particular, existing semantic-version obligations are preserved while reference-runtime release numbering remains unselected. Q-03/04 official authorities/profiles, Q-05 disputed precedence, Q-06 numeric accounting parameters and Q-07 profile guarantees remain open where upstream leaves them open. Missing mandatory inputs block their affected claim rather than being resolved by this ADR.

Only ADR-011 is authored. No accepted source, dependency edge, runtime code, script, test, CI file, schema, operational manifest, package configuration or later ADR is changed/created. The following review checks document coverage, not empirical verification.
