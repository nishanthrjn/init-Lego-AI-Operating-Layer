# ADR-028 — Deterministic approval for bounded ForgeAI batches

Status: Proposed
Date: 2026-10-27
Decision owner: ForgeAI maintainer
Class / priority: C / P2
Reversibility: Type 2; optional operator tool, with retained clone history
Governing requirements: ADR-014 §§3–6; ADR-024 §§6–8;
FORGEAI-4-AND-M8.4-DIRECTION §16;
FORGEAI-V0.2-REPOSITORY-ENGINEER-READINESS-1 §10
Depends on: existing exact approval, context confirmation, authorized mutation,
sandbox checks, independent review and bounded rework
Supersedes: proposed exception to §16's no-commits non-goal only for the dedicated
batch branch; no accepted ADR superseded

## Context

The Developer Preview requires per-proposal interactive approval. A finite
operator-written task list needs a deterministic replacement while preserving
all existing worker gates. The maintainer authorized implementation for review;
this ADR remains Proposed pending a separate acceptance decision.

## Decision question

May an immutable operator-selected policy approve validated proposals in an
isolated batch, with successful candidates committed for later human review?
This does not decide remote disclosure, model quality, planning or merging.

## Decision drivers and constraints

Authority remains deterministic and operator supplied. The original repository's
refs, HEAD, index and working files remain unchanged. Existing package APIs,
current authorization, digest preconditions, strict parsing, check profiles,
independent ACCEPT review and one-rework bound stay intact. A failure stops the
batch and retains partial state. No new dependency, Port or workflow is needed.

## Proposed decision

1. A typed `ApprovalPolicy` loaded from an explicitly selected operator file is
   a valid deterministic approver only in a **disposable standalone clone
   (own .git directory, no remotes) on a dedicated branch** created by the tool.
   Policy is fixed in memory before effects. Selecting the policy is operator
   consent; no cryptographic signature or authentication service is claimed.
2. Pure `policy.py` evaluates exact identity, file count, UTF-8 payload bytes,
   CREATE permission, forbidden names and prefixes. Defaults can only be
   extended. Names/prefixes compare case-insensitively; errors decline. Approval
   carries the exact `ProposalReview.identity`. `require_review_accept` is
   always true; the unchanged SUCCEEDED contract enforces ACCEPT after checks.
3. Automated context confirmation requires READY and exact case-sensitive path
   equality with declared targets/context plus included guidance. Ordering is
   immaterial; missing, additional, case-alias or incomplete paths decline.
   Repository guidance does not grant authority. The operator must review any
   separate check-confirmation requirements before selecting unattended use.
4. Resolve `<base>^{commit}` in the clean operator repository first. Clone with
   `--no-hardlinks --template=`, remove `origin`, create a new
   `forgeai/batch-<UTC timestamp>-<8 hex>` branch at that SHA, then verify HEAD,
   cleanliness and no remotes. Never fetch, create branches or write config in
   the original repository. Use sanitized Git environment, disabled optional
   locks/fsmonitor, argv lists and bounded subprocess timeouts.
5. Commits occur only on this branch, by the operator tool, never ForgeAI package
   code. Only SUCCEEDED task paths from applied evidence may be staged. Every
   commit carries a task id and `ForgeAI-Run` trailer. Verify a single-parent,
   one-commit advance and clean state. Never push, fetch, merge, rebase, reset,
   remove the workspace or delete a branch. Review/import commands are printed.
6. REMOTE bindings are excluded until a separate ADR decides batch-scoped
   admission. Replay and locally operated Ollama are supported. A loopback
   tunnel to remote processing is not local authority. ADR-024 admission
   windows, classes and interactive disclosure remain unchanged.
7. Run at most 20 tasks sequentially; start no new task after the 1–480 minute
   deadline. Do not kill an active task at that scheduling boundary; existing
   model/check timeouts and grant expiry still apply. Record S1 run facts and
   per-proposal policy outcomes, without giving model narrative authority.

The proposed §16 exception covers unattended sequencing and commits only within
this envelope. The human gate moves to policy/task selection and subsequent
branch review; it does not disappear. ADR-014 public composition and per-effect
current authorization remain unchanged.

## Alternatives considered

| Alternative | Disposition and tradeoff |
| --- | --- |
| Interactive approval for every patch | Existing default; simpler authority surface, but cannot meet unattended batch requirements. |
| Model-judged approval | Rejected: probabilistic output cannot grant mutation or Git authority. |
| Linked worktree | Rejected: violates the existing `.git`-file rejection in `LocalGitRepository.inspect`; that boundary is preserved. |
| Standalone clone | Selected proposal: compatible adapters and isolated metadata/objects; costs disk and clone time, with explicit later import. |
| Defer | Existing attended DP remains available if this ADR is not accepted. |

## Evidence

Source baseline: `4413f6bc205322aa0261dd3e112e85aec8746189`.
`forgeai.composition.prepare_run` accepts the required callbacks. `TaskResult`
requires ACCEPT and passed gates for SUCCEEDED. `LocalGitRepository.inspect`
and its linked-worktree test reject gitfiles. `demo.git_environment` supplies
the operator Git pattern. These are source observations, not qualification.

New policy/batch tests cover identity/context, default forbidden names, bounds,
exception declines, operator snapshots, isolated commits, retained failures,
zero-effect refusals and forbidden Git operations. Validation is NOT RUN.

## Consequences and security impact

A deterministic policy can approve defective patches. Checks and model review
are not proof of correctness; the operator owns that residual risk and reviews
before importing or merging. The clone isolates repository effects, not hostile
operator Python or concurrent filesystem tampering. No remote means no configured
push destination, not a prohibition on a human using an explicit URL separately.

`forgeai.policy` is a pure INNER package module. `batch.py` lives beside
`demo.py`, outside the installed package. Architecture tests enforce policy
purity and prohibit package dependencies on the batch tool. Existing module
inventories add only `policy`; canonical logical architecture is unchanged.

## Resource impact and failure behavior

Each batch owns a full clone with no object hardlinks, bounded operator inputs
and a JSONL report. Non-success or an unexpected error stops without rollback.
Commit verification can fail after a commit completed: inspect HEAD rather than
assuming no effects. Interruption may leave an incomplete report or clone.
There is no resume, automatic cleanup or disk reclamation.

## Migration / reversibility

The attended CLI is unchanged. Review with `log`/`diff` against the resolved
base in the clone. The human may run the printed fetch to import the branch and
later merge, then delete the output directory. Disabling the tool requires no
data migration; retained clone history remains inspectable.

## Conformance and follow-up gates

The validator preserves baseline modules/tests and unrelated packages, scripts,
experiments and plans. Replay/FakeSandbox checks do not qualify real Docker,
installation, live models or remote admission. Maintainer validation and ADR
acceptance remain pending. Model quality is UNQUALIFIED; no live execution is
authorized by this record.
