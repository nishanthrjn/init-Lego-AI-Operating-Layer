## Context

Lego AI is deliberately language-neutral, but a first reference implementation needs a concrete substrate for source, interfaces, records, concurrency, packages and developer tools. The repository currently contains accepted architectural documents rather than runtime code; there is no existing codebase migration or established implementation language that overrides this choice. All nine governing documents were reviewed in the required authority order; no higher-level contradiction was identified.

The initial maintainer is one developer. The decision must make a complex contract-driven platform feasible to build, review and maintain without assuming a large operations team. The maintainer's comparative language proficiency is **not established by repository evidence**. Productivity judgments below assume adequate working competence in the shortlisted languages and are architectural inferences, not measurements of this developer's speed. A substantial contrary proficiency constraint is a review input, not silently assumed experience.

Future applications may involve coding/research Agents, software teams, content/video or social-media production, enterprise integration, human participation and non-AI automation. They make eventual AI/data integration relevant, but none becomes a Kernel dependency. The first slice remains tenant-aware even with one tenant, deterministic and directly callable, with no mandatory Model, Agent, Workflow, RAG, vector database, event broker or distributed deployment.

## Decision question

Which programming language and runtime should implement the **first official reference runtime** of Lego AI Operating Layer, while preserving the ability for other conforming implementations, Plugins, Adapters and applications to use other languages?

This ADR chooses the implementation substrate and its initial runtime support policy. It does not choose package layout, a package manager, type checker, validation library, test framework, application framework, storage engine, broker, IAM product, Model provider, observability backend, deployment platform, public protocol or serialization format.

## Decision drivers

The comparison uses ordered judgments, not numerical scores:

1. **Non-negotiable gates:** canonical semantic fidelity, external security enforcement, tenant/resource/effect correctness, independent modules and replaceable Ports. An option that needs a weakened contract is rejected regardless of productivity.
2. **Dominant tradeoff:** sustainable solo-developer delivery across implementation, operations, maintenance, testing, local setup, deployment and learning. This includes the cost of compensating for language weaknesses, not merely concise syntax.
3. **High weight:** maintainable typed boundaries, testability and understandable asynchronous orchestration. Correctness must remain inspectable after the first prototype.
4. **High but secondary weight:** future AI, local-model, evaluation and data ecosystem access without moving SDK types or framework state into core contracts. Hosted API access alone is insufficient to decide the language.
5. **High weight:** replaceability and interoperability, dependency reproducibility and runtime longevity.
6. **Adequacy threshold, then optimization:** realistic performance, memory/startup footprint and growth toward multiple processes or remote adapters. There is no measured throughput or latency requirement that presently justifies maximizing CPU throughput at the cost of development complexity.

Sensitivity: if the reference runtime were primarily a web product with a TypeScript-skilled maintainer and all ML behind remote services, TypeScript/Node would likely win. If compact standalone deployment or sustained CPU-intensive coordination became dominant, Go or Rust could become preferable. These are explicit changes in drivers, not failures of their ability to express Lego AI today.

“Pass” is conditional on designing the required boundary. No language compiler, GIL, event loop, goroutine scheduler, JVM monitor or borrow checker proves joint validity at distributed dispatch, tenant isolation or exactly-once effects.

Canonical identity/version/revision remain separate even if represented by similar language values. Execution states do not become language task states. Exceptions do not determine canonical error/effect categories automatically. Immutability must account for nested values, not just read-only fields. Permission, Approval and resource claims remain current owner-governed facts rather than object possession. Built-in Providers and Adapters retain their owning Plugin/version; a package name does not supply that ownership or admission.

## Realistic reference-runtime workload

The likely coordination path is input validation → context/Principal/tenant checks → Capability resolution → admitted execution → bounded I/O or deterministic action → owner state/resource/evidence updates. Later paths include Model calls, Tool and database I/O, human waits, streaming, small policy computations, serialization and Plugin coordination. Latency is plausibly influenced by external I/O, but **no benchmark establishes its proportion**.

CPU-heavy local inference, media processing, large retrieval/indexing jobs or data transformation may be substantial. They should be assessed as specific capabilities with resource limits; the orchestration substrate need not implement their inner loops. Multi-process workers, native components or remote adapters remain possible later, with explicit failure/context/effect contracts. No such topology is chosen here.

## Alternatives considered

### Python with modern CPython

**Strengths.** Python supports a compact explicit domain model, interactive investigation and a broad integration surface. Its standard library offers task groups, timeout/cancellation facilities and asynchronous context support. `TaskGroup` groups child tasks and propagates failures; swallowing cancellation can interfere with structured control flow. These are useful primitives, not a selected Workflow engine. [Python task documentation](https://docs.python.org/3/library/asyncio-task.html), [context variables](https://docs.python.org/3/library/contextvars.html).

**Typing.** Annotations, Protocols, generics, distinct static identifier types and unions can make Port contracts inspectable. Python does not enforce annotations at runtime, so a strict checker is an additional required development control; runtime input validation remains separate. Broad dynamic values or unchecked third-party stubs can defeat that control. [Python typing documentation](https://docs.python.org/3/library/typing.html). Value-oriented records are feasible, but frozen dataclasses do not make referenced collections deeply immutable or provide a security boundary. [Dataclasses documentation](https://docs.python.org/3/library/dataclasses.html).

**Concurrency/performance.** The selected conventional CPython build retains the GIL: pure-Python CPU work cannot be assumed to scale across threads. Async I/O can overlap waits, while blocking code must not occupy the coordination loop. Free-threaded CPython exists and is supported in the 3.14 series, but some extensions can re-enable the GIL; adopting that build needs separate compatibility and concurrency evidence. It is not the baseline selected here. [Python 3.14 release documentation](https://www.python.org/downloads/release/python-3147/), [free-threading guide](https://docs.python.org/3/howto/free-threading-python.html).

**Cost.** Environment management, dependency resolution, native wheels and static-checker consistency add work. Dynamic introspection/import execution makes trusted-module discipline and isolation especially important. CPU-heavy Python processing and per-object overhead may become bottlenecks. The AI/data advantage is valuable, but is not proof of those workloads being fast or dependencies being compatible with the chosen minor version.

**Disposition:** selected, with the runtime policy and mitigations below. The inference is that its combined orchestration and future local AI/data integration cost is lowest for this project's declared trajectory, provided typing, packaging and boundary discipline are treated as real work.

### TypeScript with modern Node.js

**Strengths.** TypeScript offers productive structural typing, discriminated unions, generic interfaces and strong editor feedback for asynchronous backend work. Structural compatibility helps interchangeable Port implementations, but permits some intentionally unsound assignments; validated identity wrappers and explicit variant handling are still needed. [TypeScript compatibility documentation](https://www.typescriptlang.org/docs/handbook/type-compatibility.html).

**Runtime implications.** Values execute under JavaScript semantics. Types are not runtime validation. Node's native type stripping performs no type checking, so executing `.ts` files does not replace a checker. Module-system and build/package compatibility remain deliberate choices. [Node TypeScript documentation](https://nodejs.org/api/typescript.html). Async-local context and worker threads provide relevant building blocks; CPU work can be moved away from the main event loop, but workers and abort signals do not automatically cancel completed external effects. [Async context](https://nodejs.org/api/async_context.html), [worker threads](https://nodejs.org/api/worker_threads.html).

**Cost and strengths relative to Python.** Strong default static workflow and web/backend ergonomics make this the runner-up. JavaScript numeric semantics require careful representation for exact counters, money and revisions; runtime validation remains necessary. Dependency trees, module formats and package execution have supply-chain/maintenance costs. Direct local ML/data work may introduce another runtime even when remote AI calls work well. Node 24 is an LTS option at the research date; no Node version is selected for Lego AI. [Official Node releases](https://nodejs.org/en/about/previous-releases).

**Disposition:** runner-up, not rejected as architecturally deficient. Prefer it if web/service integration and existing TypeScript expertise dominate, with local ML intentionally externalized. Current sources do not justify calling its AI SDK ecosystem immature.

### Go toolchain and runtime

**Strengths.** A compact language, interfaces, generics, goroutines and integrated tooling make service infrastructure and deployment attractive. Explicit context supports deadlines/cancellation across API calls; it does not force callees to stop or reverse effects. Race detection is useful dynamic evidence, not proof of all schedules. [Go FAQ](https://go.dev/doc/faq), [context package](https://pkg.go.dev/context), [race detector](https://go.dev/doc/articles/race_detector).

**Model implications.** Structs/interfaces express Ports cleanly. A rich closed result/lifecycle vocabulary needs explicit tagged modeling and exhaustive-handling conventions rather than Rust-style enums or Java sealed hierarchies. Error values must be mapped to canonical categories with effects intact; a non-nil error says nothing sufficient about external effect status. Goroutines need bounded ownership, joins, cleanup and backpressure; cheap concurrency is not free resource capacity.

**Plugin implications.** Native Go dynamic plugins have portability and build-compatibility constraints, including no Windows support in the documented mechanism. That does **not** disqualify Go from Lego AI: compiled-in contributions with explicit owning Plugin identities and remote realizations can satisfy the architecture. It weakens the case for treating native dynamic loading as an easy first-reference solution. [Official plugin package warnings](https://pkg.go.dev/plugin).

**Disposition:** not selected for the primary runtime. Its deployment/concurrency benefits are compelling if this becomes predominantly infrastructure with strict operational footprint goals. Current official hosted-AI clients exist; the tradeoff is broader local ML/evaluation integration and richer domain-model ergonomics, not inability to call Models. It remains a plausible remote Plugin or future reference implementation.

### Java with a modern JVM

**Strengths.** Modern Java provides nominal interfaces/generics, records and sealed-type modeling rather than requiring verbose mutable JavaBean designs. Records supply shallowly immutable data carriers; application invariants and referenced mutable objects still need handling. Virtual threads support scalable blocking-style I/O, not faster CPU computation. [Java records](https://docs.oracle.com/en/java/javase/25/language/records.html), [virtual threads](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html).

**Tradeoffs.** The mature integration/tooling ecosystem, refactoring and runtime diagnostics are credible strengths for a serious platform. JVM runtime/dependency/build configuration and deployment tuning add a footprint this first slice has not justified. This is a workload/maintainer judgment, not a claim that Java requires an enterprise framework. Structured-concurrency API status is version-dependent; the choice must not rely on preview APIs as mandatory canonical behavior. Class loaders and reflection are not malicious-Plugin security boundaries, and version coexistence is not automatic admission.

**Disposition:** not selected. It becomes preferable with substantial existing JVM expertise/infrastructure, enterprise integration requirements, or measurements favoring a JVM reference. Hosted-AI ecosystem support is real; Java is not ruled out for being “non-AI.” JVM distribution/vendor and support licensing would need review if selected; this ADR selects none.

### Rust with Cargo and an explicit async-runtime ecosystem

**Strengths.** Enums, traits, `Result`, ownership and borrowing provide strong tools for explicit state/error modeling and resource lifetimes. Safe Rust prevents important memory and data-race errors; logical races, stale authority, deadlocks and distributed duplication remain architectural problems. [Rust concurrency](https://doc.rust-lang.org/book/ch16-00-concurrency.html). Async futures require execution support beyond syntax; executor selection, cancellation safety and shared-state design add decisions. [Rust async chapter](https://doc.rust-lang.org/book/ch17-00-async-await.html).

**Tradeoffs.** Ownership/lifetime constraints across async Port implementations, generic code and extension boundaries increase the expected learning/debugging burden for a solo platform builder. Compile/link iteration and library integration need comparison on actual workloads; no compile-time measurements were run. Native performance and low-level control are attractive when measured demands justify them. FFI and unsafe code shift obligations back to the author and can compromise otherwise safe boundaries. [Unsafe Rust](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html).

**Disposition:** not selected for the primary reference runtime. Prefer it for a demonstrated latency/memory-sensitive component or a maintainer/workload profile that values compile-time memory guarantees above integration iteration speed. Local inference libraries and remote calls remain possible; Rust is not deemed incapable. No Rust executor or application framework is chosen here.

### Multiple core languages from the start, or defer the choice

A Python coordinator plus a second-language Kernel would impose multiple build/release chains, API evolution, cross-boundary debugging and duplicate contract tests before a need is established. It also risks standardizing a public representation too early. **Reject a multi-language core start.** Later specialized components may use another language behind justified boundaries; they are not part of this selection.

Continuing documentation without a substrate is possible, but deferring this decision would leave the accepted P0 dependency unresolved. There is sufficient documentary evidence to select a substrate without an unauthorized prototype. **Do not defer the choice.** Implementation readiness still depends on acceptance and later ADRs, not merely on writing a selection.

## Evidence and external ecosystem findings

**Evidence boundary:** repository documents establish requirements; official external sources establish available mechanisms; this ADR's ranking is architectural inference. Research date is **2026-09-16**. No prototype, benchmark, package installation or execution experiment was authorized or performed. Performance, developer effort and dependency compatibility therefore remain hypotheses to validate during later authorized work. Sources are linked at the relevant claims; documentation support is not proof of this implementation.

### AI and integration evidence

Official OpenAI clients exist for [Python](https://github.com/openai/openai-python), [TypeScript/JavaScript](https://github.com/openai/openai-node), [Go](https://github.com/openai/openai-go), and [Java](https://github.com/openai/openai-java). Anthropic's [official SDK inventory](https://platform.claude.com/docs/en/cli-sdks-libraries/overview) and Google's [Gemini library documentation](https://ai.google.dev/gemini-api/docs/libraries) also cover these language families. This rules out “only Python has serious hosted-Model access” as a decision rationale. Rust can integrate through other clients or remote boundaries, but the reviewed inventories do not establish equal first-party Rust coverage; that is an evidence limitation, not a claim of no Rust ecosystem.

Python's distinctive advantage for this project is direct access to local-model and data/evaluation workflows, illustrated by [PyTorch installation support](https://pytorch.org/get-started/locally/) and [Transformers installation documentation](https://huggingface.co/docs/transformers/en/installation). Inference: keeping future local inference, embeddings and data preparation near the reference language can reduce cross-runtime integration work. It does not require those libraries, imply every wheel supports every interpreter/platform, or justify loading them into the Kernel.

Python and TypeScript have official [Python MCP](https://github.com/modelcontextprotocol/python-sdk) and [TypeScript MCP](https://github.com/modelcontextprotocol/typescript-sdk) SDKs, and maintained Agent/integration framework surfaces such as [LangChain Python](https://docs.langchain.com/oss/python/langchain/overview) and [LangChain JavaScript](https://docs.langchain.com/oss/javascript/langchain/overview). These demonstrate optional Agent, embedding/retrieval and integration paths; they do not select MCP, LangChain, RAG or any vector store. Specific providers/features, retry defaults and version support need review at the Adapter boundary.

For systems integration, all five candidates can use network clients, CLI/process boundaries, background workers and foreign-function/native integration where appropriate. HTTP, database, queue, object-store, identity and telemetry adapters are ordinary ecosystem capabilities, but suitability depends on the chosen library's maintained platform support, cancellation, tenant context and effect semantics. The [gRPC language inventory](https://grpc.io/docs/languages/) illustrates multi-language tooling while also showing why support should be checked per language rather than assumed identical. No HTTP/RPC/message protocol is selected.

### Security and test-tool evidence

Known-vulnerability tooling is available through [PyPA pip-audit](https://github.com/pypa/pip-audit), [npm audit reports](https://docs.npmjs.com/about-audit-reports/), [Go security tooling](https://go.dev/doc/security/), [OWASP Dependency-Check](https://owasp.org/projects/dependency-check), and [RustSec](https://rustsec.org/). Their existence supports maintainability, not a conclusion that an unflagged dependency is safe. [PyPI attestations](https://docs.pypi.org/attestations/) provide provenance mechanisms; provenance does not establish canonical conformance or permission. No scanner/signing system is selected here.

Python's standard [unittest documentation](https://docs.python.org/3/library/unittest.html) includes isolated async test support, demonstrating that async unit tests need no large platform. Across candidates, unit/contract tests, fake Adapters, property testing, fault injection, adversarial checks and integration tests can be implemented without a mandatory distributed test service. Tool selection remains later. Testing burden differs: Python needs explicit dynamic-boundary checks; Rust's compile-time protections reduce some invalid-memory cases but cannot remove retry, tenant, resource or revocation evidence obligations.

## Decision

**The first reference implementation of Lego AI Operating Layer will be implemented in Python on conventional, GIL-enabled CPython, starting with CPython 3.14.**

This is a reference implementation decision only. **Canonical contracts remain language-neutral.** Other Plugins, Adapters, services, SDKs and applications may be implemented in other languages. This ADR selects one primary language/runtime, not a multi-language Kernel, and does not require AI libraries for deterministic use.

The selection includes a commitment to strict static checking of maintained reference code, explicit runtime validation at trust/input boundaries, and value-oriented domain modeling. These are mitigation requirements for this implementation, not a choice of checker, model library or schema. Standard Python async facilities are sufficient to establish feasibility; the actual task ownership, execution driver, dispatch and concurrency mechanisms remain in later ADRs.

### Runtime-version policy

- **Initial minimum and supported minor:** CPython **3.14**, conventional GIL-enabled build. Initially qualify only the 3.14 minor line rather than promise all future Python 3.x versions or backport support to older minors. Other Python implementations and free-threaded builds are not part of this initial support claim.
- **Patch handling:** use the latest security-maintained 3.14 patch that has passed the reference runtime's dependency and conformance checks at release time; record the exact interpreter/build and dependency environment in release evidence. Do not freeze one patch indefinitely. Security fixes receive prompt compatibility review; known material vulnerabilities cannot be ignored merely to preserve a pin.
- **Minor upgrades:** consider a new stable CPython minor after required dependencies, native wheels, static tooling, cancellation/context behavior and supported platforms are qualified. Add a minor through an explicit compatibility/release record; no automatic compatibility claim follows from a successful interpreter launch. Maintain only explicitly tested minors, with a documented migration window when raising the minimum.
- **Support sunset:** plan migration before upstream security support ends; this ADR promises no private indefinite interpreter maintenance. A routine supported-minor update under this policy belongs in release compatibility records; changing language, implementation family, GIL/free-threading baseline or these support principles requires a superseding ADR.

The official [Python version-status table](https://devguide.python.org/versions/) lists 3.14 in bugfix support with scheduled end of life in October 2030 and 3.15 as prerelease at the research date. This supports selecting a current stable baseline without starting on a prerelease. Scheduled dates can change; future releases must verify current status. CPython 3.14 dependency availability is **not assumed universally proven**: incompatible optional AI libraries may remain unsupported or use a later separately authorized Adapter environment instead of silently lowering the core baseline.

## Why the selected option wins for this project

Python meets the mandatory substrate gates without making AI foundational. It combines a manageable deterministic orchestration implementation with direct access to the broader local AI/data/evaluation ecosystem that the stated future applications are likely to exercise. That combination reduces expected integration and language-switching work for one maintainer. The choice would be weaker if the project only needed hosted Model HTTP calls; the SDK inventory explicitly shows strong alternatives there.

Its weaker runtime typing is a significant cost, not ignored evidence. The project already requires boundary validation and behavioral conformance regardless of implementation language. Adding strict static analysis, narrow values and import discipline is a feasible additional burden compared with maintaining a separate local ML language from the start. This tradeoff is an architectural inference; no empirical claim is made that Python is always faster to develop or cheaper to operate.

No accepted requirement currently demands sustained CPU throughput, tiny standalone artifacts, hostile in-process isolation, or a compile-time proof discipline that would favor another primary language enough to outweigh this integration benefit. If later requirements establish such needs, narrow native/remote capabilities can be evaluated before a costly full runtime rewrite.

## Why the runner-up was not selected

**Runner-up: TypeScript on Node.js.** It provides a compelling typed backend workflow, excellent asynchronous I/O ergonomics and credible hosted-AI/Agent integration. It was not selected because this project's future local-model, data-processing and evaluation work would more often introduce a second language/runtime boundary, while Python can serve both orchestration and those optional ecosystems directly.

This is a modest, scope-dependent advantage, not a universal ranking. TypeScript becomes preferable if the maintainer's strongest expertise is TypeScript, the primary product is web/backend integration, local ML is deliberately remote, and its type/tooling benefits materially reduce maintenance. A review establishing those conditions should reconsider this proposed decision before acceptance. Neither JavaScript numeric behavior nor erased typing is a categorical disqualification; both can be handled with explicit models and validation.

## Consequences

### Positive

- One primary reference language across deterministic orchestration and optional AI/data integration.
- Compact domain and Adapter code with interactive diagnosis and a broad maintained tooling ecosystem.
- Standard asynchronous/context facilities make an I/O-oriented foundation feasible without selecting an Agent or Workflow framework.
- Public semantic contracts can remain separate from provider SDK objects and language-specific representations.
- Specialized components remain replaceable through Ports instead of forcing a second core language now.

### Negative

- Type safety depends partly on tool configuration, annotation quality and third-party type information; runtime checks remain necessary.
- Pure-Python CPU cost, object overhead and blocking calls can limit concurrency or raise resource cost.
- Packaging, virtual environments, native dependencies and interpreter minor upgrades need sustained discipline.
- In-process imports/introspection and native extensions cannot provide a hostile-Plugin security boundary.
- Multi-version package coexistence, reproducible builds and clean public package boundaries require explicit design rather than following automatically from language choice.

### Risks accepted

The maintainer accepts these **implementation tradeoff risks**, not waivers of canonical obligations: additional static/runtime validation work; potentially higher CPU/memory cost than a native implementation; Python packaging/native-wheel variance; async misuse and cancellation mistakes; future integration churn; and expensive migration if the substrate later becomes unsuitable. Actual speed, footprint and dependency compatibility are unmeasured. There is no accepted risk allowance for unauthorized effects, tenant leakage, secret exposure, false conformance claims or dropped liabilities.

## Concurrency and type-system implications

### Concurrency is an implementation concern, not a contract shortcut

Task cancellation, timeout expiry and an external effect's completion have different meanings. Cleanup must not silently refund Approval use or resource liability. A child operation may continue outside the process after its local waiter is cancelled; a new retry must not infer none. Context propagation likewise carries attribution but does not refresh a revoked Grant. The runtime must re-establish required current predicates at each protected boundary.

Task groups and bounded I/O are useful implementation directions, but the actual handoff ordering is ADR-007. The GIL is neither an authority lock nor a multi-owner transaction. An `await`, a thread, a native call or a process boundary can expose interleavings; code that appears sequential still needs owner revision/claim arbitration. Backpressure must limit admission/queued work and inherited resources, not merely cap sockets. Process isolation and horizontal scaling remain possible with explicit context/effect/evidence transfer, without requiring them in the first slice.

### Four distinct forms of checking

| Layer | What it establishes | What it cannot establish alone |
|---|---|---|
| Language type facilities | Vocabulary for interfaces, generic values, variants and identifier distinctions | Actual current authority, valid data received from outside, safe effects |
| Static analyzer | Some incompatible calls/returns and variant mistakes before execution | All runtime values, dynamic imports, concurrency correctness or security |
| Runtime validation | Actual shape, bounds, versions and cross-field invariants at a boundary | Entitlement/current Policy unless the appropriate owner is consulted |
| Schema validation, if later authorized | Conformance of a chosen external representation | Full behavioral Port semantics, effects, claims or conformance |

No universal schema or Python interface is defined here. Port types can express canonical records without exposing SDK-specific classes; generic extensions require namespaces/version/requiredness and semantic validation rather than an unrestricted object dictionary. Explicit canonical error categories, recoverability and effect statuses remain independent of exception inheritance. Compile-time-friendly typestate can help local code but cannot prove persisted state is current or an Approval remains usable.

## Security impact

Language selection does not establish identity trust, isolation, permission or audit adequacy. Python module import can execute code, so Plugin discovery/metadata inspection must not import unadmitted candidate behavior just for convenience. Namespaces, virtual environments and private attribute conventions are not hostile-code boundaries. Native extensions and FFI can corrupt process state or bypass Python-level checks; admitting them requires the same threat/permission analysis as other privileged code.

Untrusted object deserialization is particularly hazardous: Python's official [pickle documentation](https://docs.python.org/3/library/pickle.html) warns that malicious data can execute arbitrary code. This ADR does not select pickle or any public format. Canonical records must not become Python object graphs as a hidden interoperability contract; later representation choices need independent review.

Supply-chain scanning/provenance and pinned dependencies reduce specific risks but do not prove safety. Reflection/debuggers/crash dumps may expose sensitive values; no reliable general secure-erasure guarantee is claimed for Python objects. Secret-use mediation, logging discipline and appropriately strong process/host boundaries remain ADR-010/012/013 work. No private chain-of-thought is required for evidence. Current Principal/tenant checks and fail-closed dispatch remain external to probabilistic behavior regardless of implementation convenience.

## Resource impact

Qualitative expectations, not measured results:

- **Runtime memory/startup:** CPython plus imported dependencies creates interpreter and object overhead. Keep the deterministic core free of heavyweight optional ML imports; measure the actual footprint before setting limits.
- **CPU and concurrency:** likely adequate for initial orchestration, but validation, serialization and policy work may dominate at higher rates. Offloading introduces its own process memory, transfer, cancellation and accounting costs.
- **Build and iteration:** ordinary Python source avoids a full native compile cycle; native extensions and binary dependency builds can reverse that advantage on unsupported platforms.
- **Artifact/deployment size:** interpreter, environment and native libraries must be distributed or provisioned reproducibly. No single-static-binary simplicity is claimed.
- **Operations:** patching, dependency review and environment qualification consume maintainer time. AI calls or media workloads may dominate spending, but that has not been measured and does not excuse inefficient core paths.

Budget/Quota/Limit precision, currency and metering policy remain canonical-owner decisions in ADR-007 and its upstream parameter authorities. Integer/decimal representation options in Python do not decide approved units, overrun policy or settlement behavior.

## Interoperability and language-neutrality impact

Python is the first reference substrate, not the canonical ontology. Applications and Plugins do not have to be Python, and an Adapter is not defined as a Python package. A future Rust performance Adapter, Go remote Plugin, Java enterprise service or TypeScript UI/service integration remains possible if it preserves the relevant contract and owning Plugin semantics.

In-process foreign code requires an appropriate FFI/ABI and threat review; arbitrary binaries are not automatically callable or safe. Remote/CLI adapters require explicit context, version, authority, effect and evidence mappings. This ADR selects neither those mechanisms nor HTTP, gRPC, MCP, A2A, JSON, Protobuf or another public format. Cross-language interfaces must be designed when actual consumers require them.

## Migration / reversibility

This is Type 1 because source APIs, dependency tooling, maintainer expertise, operational procedures, Plugin packaging and tests will accumulate around Python. A rewrite entails implementing and requalifying behavior, not transliterating syntax. Optional native components can also add ABI/platform lock-in.

Canonical Ports, exact domain versions, owner boundaries and independent conformance evidence limit the damage: they allow a second implementation to coexist and compete on observable behavior. They do not make migration free. State, operation identities, deduplication history, outstanding effects, resource liabilities, Approval consumption, Secret references and evidence interpretation must survive any transition. Rolling back source code does not roll back real effects or restore authority.

Do not persist arbitrary Python objects or expose Python exception classes as public contract meaning merely for convenience. Storage and wire representations remain undecided. A later language implementation may initially replace one capability behind an Adapter, then expand while consumers remain bound to explicit versions and guarantees. Process/network boundaries introduce new failures and require proof; they are a migration option, not a mandatory architecture today.

## Reconsideration triggers

Reopen through a superseding ADR, not fashion-driven edits, if:

- Representative measurements show required latency, throughput, memory or startup cannot be achieved within acceptable complexity/resource bounds, even after targeted optimization or bounded specialized components.
- The runtime/dependency model cannot substantiate an actual required security or isolation property with a feasible enforcement boundary.
- Packaging, native-wheel availability, upgrade maintenance or supply-chain risk becomes unsustainable for supported deployment platforms.
- The maintainer's demonstrated comparative expertise or product direction materially changes the solo-developer cost balance.
- Critical Model/data/provider ecosystems shift enough to remove the integration advantage, or cross-language adoption requires a second official runtime.
- The reference workload becomes predominantly infrastructure/native computation rather than orchestration plus optional AI/data integration.

These triggers require evidence and a migration analysis. A new language release, popular framework or isolated microbenchmark is not enough.
