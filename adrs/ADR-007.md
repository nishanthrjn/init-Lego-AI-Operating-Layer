## 1. Context and decision question

The current governing sources and accepted ADRs were reviewed. Owner-local durability, explicit current Principal/Tenant authority, exact configuration/activation, finite bootstrap and mandatory evidence custody remain closed. The canonical dependency graph remains ADR-004, ADR-005 and ADR-009; accepted ADR-006 supplies the root/contribution context without a new dependency edge.

Which arbitration mechanism makes authority, Approval, resources, deadline, evidence and trust predicates jointly valid at the protected handoff while conserving parent and child resource bounds?

Separate owners checking “yes” at different times is insufficient. Conversely, a single global transaction merging Governance, Approval, Resources, Lifecycle, Evidence and the external target would contradict accepted ownership and failure semantics. The mechanism must expose partially consumed claims and uncertain handoff while preventing new use of stale authority or copied capacity.

The first supported realization is a trusted local modular monolith with one explicit tenant, one active dispatch-arbitration process for the admitted state domain, and deterministic direct Capability support. Agent/Model/Workflow/Team/Memory are optional. Remote effect targets are possible only through an admitted local Adapter whose handoff, uncertainty and resource guarantees are qualified. Independently changing remote control owners are not automatically covered by the local ordering mechanism.

## 2. Alternatives

### A — Bounded serialized handoff arbiter

A shared local ordering gate admits one final dispatch or participating invalidating mutation at a time. Owners retain their own state and atomically guard their own claims. The invoking plane retains the single effect dispatch obligation. This supplies a straightforward order for local revocation and dispatch without making all owner commits atomic.

Costs are serialized final sections, strict participation by every relevant mutation path, bounded callback requirements and fail-closed recovery. A Python lock alone is not this architecture: ownership exclusivity, durable facts and the no-bypass contract must hold across tasks, administrative paths and restart.

### B — Atomic conditional commit over co-located owner records

A physical transaction can validate and update several owner records together, simplifying a subset of local claim consistency. Logical owners still must validate their own contributions. It does not atomically include an external effect, resolve the crash between commit and handoff, or inherently stop wall-clock expiry between them.

Reject this as the foundational semantic requirement. It makes coordination depend on co-location and broader atomic units, complicates later separate owners and still needs a handoff/currentness boundary. ADR-004 permits separately reviewed co-located optimizations, but this decision must remain correct when they are absent.

### C — Independently arbitrated claims with joint-valid interval/ordering proof

Owners issue bounded claims and the dispatcher obtains a demonstrated common validity interval or equivalent ordering guarantee. This can support distributed owners and higher concurrency, but requires protocol-level fencing, revocation, clock/disconnection and expiration reasoning. Leases or timestamps alone cannot ignore already effective restrictive changes under SEC-028.

Not selected for the first slice: the local scope does not justify distributed coordination complexity, and no qualified remote protocol is available from the accepted ADRs. It remains a future replacement only if it proves the same currentness, partial-failure and conservation semantics.

| Criterion | A — Serialized local gate | B — Cross-owner physical transaction | C — Independent bounded claims |
|---|---|---|---|
| Joint validity | Direct order if all invalidators participate and time is checked at handoff | Strong local snapshot; commit-to-handoff gap remains | Requires qualified common interval/order protocol |
| Logical ownership | Separate owners/commits | Must prevent hidden merged ownership | Separate owners |
| Partial completion | Explicit, including consumed-before-abort | Fewer local partial writes but remote gaps remain | Explicit across participants |
| Revocation | Same gate orders effective mutations and handoff | Transaction order insufficient after commit by itself | Propagation/fencing/disconnection proof needed |
| Local operation | No remote coordinator required | Requires shared transactional realization | Most initial moving parts |
| Failure recovery | Durable owner results and invoking-plane uncertainty | Transaction recovery plus external uncertainty | Distributed state/uncertainty reconciliation |
| Scaling | Conservative throughput, measured bottleneck possible | Store/co-location coupling | Better topology flexibility at higher proof cost |
| Reversibility | Replace scheduling behind owner contracts | More storage coupling | More protocol/claim-version coupling |

## 3. Decision

**Select A: a bounded serialized local handoff arbiter, combined with owner-local conditional claims, a durable single invoking-plane dispatch obligation, and conservative uncertainty recovery.**

The first realization uses one arbitration domain for its admitted local state/tenant scope. This conservatively orders unrelated final sections too; it is a reference implementation scheduling choice, not a canonical global clock or requirement that all deployments share one global transaction.

Every supported mutation that can invalidate a participating authority, constraint, claim or eligibility fact must enter the same domain before becoming effective. Owners still authorize and commit only their own state. Final handoff holds the ordering gate while it establishes the final predicates, completes applicable owner-local consumption and commits the one protected handoff. It does not hold the gate throughout the external effect.

Preparation, expensive validation, human waits, candidate resolution and evidence collection happen outside that final section. All are revalidated for applicability inside it. Gate occupancy and each local participant operation must have a declared finite bound for the realization. An unsupported dependency, time guarantee, reentrant callback or uncertain gate owner blocks dispatch; it is not replaced with stale success.

No resource quantum, currency, tariff, numeric precision, timeout duration, universal clock source, datastore product, lock library, scheduler or queue technology is selected. Q-06 parameters must be supplied by their accountable authority for each supported resource dimension. Missing mandatory parameter scope blocks that claim rather than this document inventing it.

## 4. Responsibility and claim meanings

| Responsibility | Accountable owner |
|---|---|
| Principal/Grant/Policy/tenant validity | Respective Governance owners; Boundary Enforcement composes action decisions |
| Approval bounds and use claims | Approval Management |
| Allocation, Budget/Quota/Limit, reservation, consumption and settlement | Resource Admission and Accounting |
| Delegation work/assignment bounds | Work Coordination; allocated resource capacity remains Resources-owned |
| Plugin activation/health and offer registration | Lifecycle and Catalog respectively |
| Mandatory evidence custody | Evidence and Provenance; sources retain their obligations |
| Deadline propagation | Execution Coordination under inherited bounds |
| Single dispatch obligation and effect identity | Invoking plane; Action Mediation for Tools |
| Ordering gate | Technical arbitration used by owners; no authority or balance ownership of its own |

A claim is an existing contract record, not a general grant. It identifies scoped identity/kind/owner, expected/current revisions, tenant/subject, action/effect equivalence, quantity or bound, validity/time basis, governing references, provenance and accounting/liability. Caller-created claims or copied availability snapshots are not spend authority.

Preserve CTR-018 claim states: creation yields reserved; reserved may become consumed, released, expired or invalid. Consumed does not become reserved again. Expired/invalid bars new use but does not erase consumed use or outstanding liability. Partial consumption identifies disjoint units with conserved totals. Corrections/settlements are linked records, not rewriting original consumption. These are claim states, not new Approval, Plugin or Execution states.

## 5. Arbitration participation and invalidation

The ordering gate must cover **all paths** changing facts relied on by supported dispatch: Principal/credential/issuer acceptance; Grant/Policy and tenant/crossing restrictions; relevant Role/delegation eligibility; Approval revocation/consumption; resource allocation/claim mutation; deadline changes; Plugin stop/retire/health/suitability; Catalog eligibility changes; and evidence status/disposition where current availability or validity is required. Creation of competing claims also uses the relevant ordering participation and owner invariant guards.

Read-only history inspection and unrelated computation need not enter the gate. Mutation planners can work outside, but the authoritative conditional commit that affects participating current facts occurs while holding it. Storage writes by an administrative backdoor, background expirer, another process or direct Port cannot bypass participation. Domain owners enforce that requirement rather than trusting callers to remember a convenience facade.

A pending revocation request is distinct from authoritative effectiveness. The owner must enter the gate, validate current authority and expected revision, then commit its effective restriction and result. Only then may it acknowledge that scope as effective. If handoff already won the order, the owner reports in-flight scope and any remaining propagation/stop duties. It cannot falsely claim that enqueueing a revoke request universally stopped work.

Time expiry does not wait for a background expirer to obtain the gate. Actual handoff validates the authoritative validity interval/time basis under §8, regardless of whether an expired status row has been materialized. Similarly, a hardware/storage outage or independently effective external restriction cannot be delayed merely by holding a local gate. If its current applicability cannot be guaranteed for the handoff, that predicate is unsupported/unavailable and dispatch fails closed.

Initial protected decisions therefore use local authoritative control owners or external facts whose admitted contract supplies a genuine validity/order guarantee covering this boundary. A local cache of an external grant is insufficient. External authorities that can revoke independently without participating in an equivalent proven order are not supported for those protected paths. This is an explicit availability/scope limit, not permission to ignore remote revocation.

The arbiter is not an unrestricted SYSTEM Principal. Its queries/commands have bounded ADR-005 context, and every owner separately enforces current command authority. Its scheduling does not grant claims, change Policy precedence or waive mandatory evidence.

## 6. Dispatch protocol and irreversible boundary

### 6.1 Preparation outside the final gate

1. Bind the exact proposed action, actual target, tenant, requester/acting chain, immutable input/config/activation references, admitted ceiling and intended effect identity under the invoking owner.
2. Resolve requirements and collect applicable decisions, Approval and evidence references. Establish resource dimensions/units, known upper bounds or an explicitly authorized uncertainty policy, inherited allocation and deadline.
3. Persist invoking-plane intent, responsible effect/reconciliation/evidence obligations and required source facts under ADR-004 before an external handoff can create an untracked gap.
4. Obtain owner-issued reservations through governed owner mutations. Preparation may partially succeed; records expose which claims exist. No reservation or feasibility response alone releases the effect.
5. Obtain required pre-effect custody under ADR-009. Validate expensive inputs outside the gate, pinning exact subject/revisions; final applicability checks remain inside.

### 6.2 Final ordered section

1. Acquire the exclusive live arbitration domain and verify the invoking record has no prior unresolved or completed handoff for this effect scope. A repeated request is status/reconciliation, not a second independent dispatcher.
2. Validate the exact frozen action/target/tenant/acting context and all participating current owner facts. Material changes require fresh decisions/Approval, not hidden substitution.
3. Verify every required resource dimension/occupancy, Approval/delegation use, evidence receipt, deadline and isolation/trust/eligibility predicate. Establish completeness of the mandatory set; an omitted owner is not an affirmative result.
4. Commit owner-local bounded consumption/dispatch binding of the applicable claims in a recorded deterministic participant order. Each owner checks its expected revisions and conservation independently. Keep the gate throughout; partial commits remain real if a later one fails. No cross-owner rollback is promised.
5. Re-establish the final exact set after those intentional mutations. A just-consumed Approval use is valid only for its bound operation, not a new reusable allowance. All remaining current conditions and time margins must still hold.
6. Commit the invoking owner's durable exact claim/action/decision set and one **handoff-attempt obligation** before releasing an external action. This record means handoff may follow; it is not proof that handoff happened. Storage delay may invalidate time requirements, so check them again at actual handoff.
7. Commit the protected handoff to the admitted realization at its declared acceptance boundary while holding the gate and satisfying §8's timing requirements. Record the observation/outcome separately as available. Release the gate without waiting for external effect completion.

The handoff-attempt description is not a new canonical claim or Execution state. It is retained invoking-plane operation knowledge under existing effect/obligation contracts. Claim consumption does not assert actual metered usage or successful external effect. A gate release due to abort does not automatically undo any earlier consumption.

### 6.3 Handoff versus queues and external completion

A request merely queued for later delivery has not necessarily crossed protected handoff. The initial Adapter must expose a bounded local acceptance boundary that takes responsibility for the exact admitted operation. It must not treat arbitrary queue insertion as permanent authority for later protected sub-actions. If work waits before that acceptance, reacquire the gate and current checks at actual acceptance. If accepted work later performs another protected sub-action, that sub-action gets its own current boundary.

No arbitrary candidate callback, network response wait, Human decision or reentrant Governance command runs inside the gate. Qualified Adapter acceptance must be bounded and non-reentrant; long-running external execution occurs outside. An interface incapable of providing that boundary/guarantee is unsupported for this mechanism, not made safe by calling its future completion “dispatch.”

The narrow crash window between durable attempt and actual acceptance is intentionally exposed. Recovery must never auto-send an unresolved attempt. It queries/reconciles the realization/effect under ADR-008's eventual contract, or holds for an entitled safe decision. This prevents a second independent handoff caused solely by restart but does not claim exactly-once external delivery/effect. Actual provider retries, transport duplication and cross-provider deduplication remain ADR-008 qualification gates.

## 7. Why the local ordering is sufficient within scope

Let H be the actual governed acceptance/handoff and M a participating mutation capable of invalidating its predicates. Both require exclusive entry into the same live domain. If M commits and releases first, final owner reads/guards for H observe its authoritative revision or return unavailable; H cannot use the superseded positive result. If H reaches valid acceptance first, M cannot become effective through that domain until afterward; that operation is already in flight, and revocation records this limit. An aborted dispatch has no claimed successful H merely because claims were consumed.

Inside the final section, earlier predicates cannot be invalidated by participating owner mutations while later ones are checked. Deliberate consumption changes are known, exact-action-bound and revalidated as a full set before handoff. Thus these are not unrelated stale sequential reads: mutation exclusion plus exact owner guards establishes a common interval, with time/external conditions separately addressed by §8. No interval is inferred if a mandatory participant can change outside the domain or its required current state is unavailable.

Conservation is enforced independently by each claim owner's atomic invariant boundary, not by the arbiter reading balances and subtracting locally. The gate supplies order; ADR-004 commits supply authoritative state/results. Owner failure can leave earlier claims consumed and later claims absent, yet prevents H because the full set is unmet. This is safe partial completion, not an atomic multi-owner transaction.

This is a conditional correctness argument for the selected failure/threat scope. Future implementation must prove participation, exclusivity, time behavior, no bypass/reentrancy and actual acceptance placement. A lock around only the dispatcher while revocation commits elsewhere does **not** implement this decision.

## 8. Deadlines, expiry, time uncertainty and bounded occupancy

Use explicit authoritative time bases/validity intervals and uncertainty bounds supplied by the applicable contracts. No universal clock product or TTL is chosen. The usable common interval must cover actual H, not just reservation or durable attempt creation. For each deadline/expiry, conservatively include clock uncertainty, elapsed preparation/commit time and a demonstrated upper bound for the remaining local acceptance interval. If it cannot be shown that H lies inside every mandatory interval, refuse/hold dispatch.

A final timestamp sample followed by unbounded scheduling pause is insufficient. No-await Python code, the GIL or a short-looking function does not prove a hard bound. The admitted acceptance boundary must enforce the validity guard with a qualified bound on check-to-acceptance delay, or an equivalent demonstrated atomic validity/acceptance mechanism. The default local interpreter is not asserted to supply a real-time guarantee. Strict deadline scopes remain unsupported when the realization cannot establish the required timing bound; a best-effort timeout cannot be advertised as hard handoff validity.

Bound the final section's owner operations and queue wait under the realization's admitted limits. Human waits and slow evidence production occur outside. If a participant hangs, stop new dispatch and surface the affected obligation. Do not forcibly release a lock and let the old holder continue dispatching. Reclaim authority only after confirmed termination/fencing of the previous incarnation under §13. Bounded waiting does not mean time can silently be extended or consumed claims automatically refunded.

Waiting, suspension, retry, nested work and re-resolution keep inherited deadline and resource accounting. Child deadlines cannot exceed the current parent deadline without an explicitly authorized governing parent change. A parent restriction ordered before H invalidates the child's old decision; later new grants cannot silently enlarge an admitted attempt.

## 9. Resource conservation and authoritative quantity semantics

Every quantity identifies dimension, unit and definition version, nonnegative magnitude, accounting scope/window, amount kind (estimate, bound, reservation, actual or correction), precision/rounding and uncertainty or explicit unknown. Signed corrections are separately authorized linked deltas, not negative consumption disguised as a new charge. Different dimensions/currencies cannot be added without explicit conversion/rate/version/uncertainty rules.

For each allocation/dimension/window, committed consumption plus outstanding enforceable reserved liability must remain within effective allocation plus an explicitly approved overdraft bound. Neither this ADR nor a caller supplies a universal overdraft/tolerance. The Resource owner guards the complete shared invariant in one local mutation, including parent/child and relevant windows, rather than checking independent new claim rows against a stale copied balance.

### 9.1 Budget, Quota and Limit remain distinct

| Constraint | Required treatment |
|---|---|
| Budget | Explicit allocation in stated units; reservations and committed/unknown liability reduce spendable capacity |
| Quota | Defined scope/window/reset semantics; reservation and consumption apply to that window; retry does not create a new one |
| Concurrent occupancy Limit | Reserve exclusive or explicitly coordinated capacity until proven release; expiry does not prove work stopped |
| Immutable payload/static Limit | Validation bound to the exact input/revision; not a consumable balance or reusable approval for changed input |
| Multi-dimension bound | Each mandatory dimension must be covered; partial reservations cannot release the action |
| Uncertain externally metered amount | Known upper bound or explicitly authorized uncertainty/overrun policy; otherwise hard-bound admission fails |

`check_resource_feasibility` is observation only. `reserve_resource` conditionally creates authoritative capacity. `consume_resource` records exact operation commitment/usage liability or a scoped report as its contract specifies; actual measurement and settlement remain distinguishable. `release_resource` requires non-use/unencumbered proof or entitled settlement. `reconcile_resource` adds measurements/corrections and preserves earlier uncertainty/history. No currency, tariff, metering precision or billing model is selected.

### 9.2 Parent/child accounting

An exclusive child envelope is one encumbrance against its parent. Child spend draws down the envelope: it must not be added on top of an unchanged full parent reservation. For illustration only, with a parent allocation of 100 compatible units and an exclusive child envelope of 30, the other spendable parent capacity is at most 70. If the child confirms 12 used, the parent's child contribution is 12 consumed plus 18 still encumbered, totaling 30, not 42. Releasing the remaining 18 requires proven non-use and the child's applicable closure/settlement rules.

For shared coordinated allocation, Resource Accounting arbitrates all children against the same authoritative invariant. For an authorized transfer, both source/destination owner facts and any cross-owner partial obligations remain explicit; no double availability during incomplete transfer. Different child operations cannot reserve the same units simply because both read the same remaining-capacity projection.

Nested retries, replacement Providers, Evaluation and Agent loops use linked work/attempt/effect and allocation scope. New attempt identity cannot reset consumption, quota windows or elapsed deadlines. Supplemental resources require an entitled new allocation/parent amendment with evidence, not copying an updated balance into old work.

### 9.3 Unknown liability and settlement

External timeout, cancellation, invalidity, expiry, Plugin replacement or missing usage report never proves zero charge. Retain a conservative outstanding liability under the admitted bound/uncertainty policy until source measurement or authorized accounting settlement establishes disposition. No fresh capacity is manufactured by expiring a claim row.

Usage, release and settlement reports have distinct scoped identities and exact effect/claim meaning. Equivalent duplicate reports return prior accounting outcomes under ADR-004; conflicting reuse is Conflict. Partial actual usage identifies disjoint units; any released remainder must be proven unencumbered. Changed conversion/rate or measurement evidence creates a linked correction with explicit authority and scope. Lost settlement acknowledgment is status/reconciliation, not another debit/refund.

If actual usage exceeds the admitted bound, retain actual facts, expose overrun and block unsafe additional spend; do not clamp the ledger to hide it. Reassess the Provider/measurement guarantee. Only an entitled explicit overdraft/settlement process can disposition the excess; the implementation cannot retroactively claim the original hard-bound promise was met. Q-06 unresolved precision, rounding, measurement or overrun scope blocks affected admission until its authority approves the parameters.

## 10. Approval and independent controls

Approval remains distinct from Permission, Policy, resource reservation and effect success. The request binds exact action/target/material revisions, tenant, requester/performer where relevant, presented evidence, eligible approver, decision rule, conditions, validity and allowed uses. HumanApproval requires authentic eligible Human participation and adequate authorized disclosure of the exact action; a model summary, silence, delivery acknowledgment or elapsed timer is not consent/rejection.

Approval Management conditionally reserves/consumes use under the same participating order and its own revisions. Concurrent requests cannot exceed use bounds. Consumed use remains committed to the exact effect and cannot be retargeted. If downstream resource/evidence/deadline validation fails, a consumed Approval is not automatically refunded or made approved/reserved again. New entitlement is a separate entitled decision inspecting prior consumption, effect uncertainty, duplicate risk and separation-of-duties, with explicit lineage.

Unconsumed reserved Approval use can be released/invalidated only under its owner's rules and known non-use; any terminal Approval status follows its own lifecycle. Resource non-use release does not restore Approval. Approval presence cannot revive a revoked Principal/Grant, make an unsuitable Provider eligible, establish Secret permission or replace required Evidence custody.

ADR-009's pre-effect custody receipt must match the action and current required guarantee inside the final gate. Prepared evidence may remain even if dispatch is aborted; it is not effect confirmation. Post-effect custody failure retains the real effect plus a durable evidence obligation. Repair never consumes another Approval or repeats an external action merely to rebuild the audit trail.

## 11. Partial consumption, errors and cancellation

| Situation | Required truth and safe disposition |
|---|---|
| Approval consumed, second resource dimension refused | No dispatch; consumed Approval remains; release only demonstrably unused resource portions through their owner |
| Resource claim committed, Policy changes before final gate | Current restriction blocks; resource release requires non-use proof, not inferred from a generic failure |
| Final evidence receipt unavailable | No protected handoff requiring it; preserve any already committed consumption and custody uncertainty |
| Durable handoff attempt exists, response missing | Handoff/effect may be unknown; retain all relevant liabilities and reconcile before any potentially duplicate action |
| Cancellation after H | Request permitted stop/later-action prevention; prior external effect can remain partial/completed/unknown |
| Post-effect audit failed | Effect remains real; parent postconditions incomplete with evidence repair obligation |
| Owner unavailable or ordering proof lost | No new dispatch based on cached balances/allow; unaffected qualified scopes only may continue |

Use canonical categories according to cause: Conflict for stale revision/equivalence/use, BudgetExceeded for established resource exhaustion, DeadlineExceeded for deadline, AuthorizationDenied/TenantViolation for authority/scope, PolicyViolation for mandatory unsatisfied controls, DependencyFailure for failed required owners, VersionMismatch for incompatible units/contracts/interpretation where applicable, and ValidationError for malformed required input. Unavailable authority is not fabricated denial and timeout is not none. Preserve exact effect vocabulary and safe diagnostic references.

Cancellation, rejection, failed parent outcome and aborted final section never erase earlier effects/liabilities. A begun Execution cannot become rejected merely because a later boundary loses authority. Reconciliation can complete its investigation with effect still unknown; that does not satisfy an obligation requiring certainty. Compensation is separately authorized work.

## 12. Failure timelines

### Timeline 1 — Revocation before authorization

1. Grant owner commits effective restriction through the domain.
2. New preparation/final check reads current owner state.
3. Revoked scope cannot yield a valid action set; no handoff.

### Timeline 2 — Revocation after authorization, before final entry

1. Preparation obtains allow at G5, then waits.
2. Revocation commits G6 through the gate.
3. Final entry must read G6 and refuse; G5 is historical evidence only.

### Timeline 3 — Revocation after Approval or resource reservation

1. Exact Approval use and some resource dimensions are reserved outside the final section through governed owner operations.
2. A restriction wins the domain order before H.
3. No dispatch. Unconsumed reservations receive only owner-authorized non-use release; any consumed use/liability remains separately recorded.

### Timeline 4 — Revocation immediately competing with handoff

1. Revocation and final dispatch contend for the same domain.
2. If revocation commits first, final validation observes it and no H occurs.
3. If valid H occurs first, subsequent revocation reports that scope in flight; it prevents later applicable sub-actions but does not undo the handoff. Merely requesting revocation is not a false claim of earlier effectiveness.

### Timeline 5 — Revocation during or after effect

1. The realization has accepted the operation and executes outside the gate.
2. Restriction commits; later protected sub-actions recheck, and an allowed stop is requested where supported.
3. Completed/partial/unknown external effects and consumed resources remain. Neither stop nor compensation rewrites history.

### Timeline 6 — Competing capacity and Approval use

1. Two operations both observe one remaining use and insufficient capacity for both.
2. Approval/Resource owners arbitrate the shared invariant using expected revisions and unique scoped operations, participating in domain order.
3. At most valid bounded claims are issued/consumed; loser cannot spend a copied snapshot. A claim in only one required owner is not enough to dispatch.

### Timeline 7 — Partial multi-dimension consumption

1. First dimension/Approval consumption commits; another mandatory owner fails before its commit.
2. The dispatcher cannot establish the full set and does not release H.
3. Persist each owner's actual outcomes; do not roll back all records fictionally or automatically refund Approval. Settle/release proven unused capacity through its owner.

### Timeline 8 — Crash around handoff

1. Invoking owner durably records exact attempt/claim set.
2. Process crashes before or after the real acceptance, before durable confirmation.
3. Restart sees uncertainty, not permission to send. A single recovered dispatcher inspects provider/owner evidence under ADR-008; if no safe proof exists, hold for entitled disposition.
4. Pre-attempt crashes still require checking all earlier owner consumption; lack of H does not erase Approval use or unrelated prior effects.

### Timeline 9 — Deadline expires during final work

1. Preparation had a valid deadline; owner commits/queue delay consume the remaining margin.
2. Actual acceptance cannot be proven inside the common interval with declared uncertainty/delay bound.
3. No H. Record DeadlineExceeded or precise dependency/timing failure; preserve partially committed claims and do not extend parent bounds.

### Timeline 10 — Owner outage and stale cached balance

1. Dispatcher has yesterday's or earlier preparation's positive Resource/Governance evidence.
2. Required owner becomes unavailable or independently effective external validity is unprovable.
3. No new spend/dispatch from that snapshot. Gate possession alone does not make unavailable predicates true.

### Timeline 11 — Unknown charge after expiry

1. Provider may have performed a charge-bearing operation; response is lost.
2. Reservation validity expires or Plugin is replaced.
3. No further use is permitted, but incurred/unknown liability stays outstanding. Capacity is returned only on measurement/non-use proof or entitled explicit settlement, not clock expiry.

### Timeline 12 — Duplicate settlement and nested retry

1. A usage/settlement report commits and its reply is lost.
2. Equivalent retransmission returns the authorized prior result; it does not debit or release twice.
3. A linked new Execution retry retains prior consumption, unknown liability, quota window and parent deadline; it cannot evade constraints by changing attempt/provider identity.

### Timeline 13 — Post-effect custody outage

1. Actual external effect completes after valid H; post-effect Evidence custody fails.
2. Source effect and durable obligation remain; overall postconditions may be incomplete.
3. Repair evidence only. No replay, extra Approval use or new billing action to regenerate proof.

### Timeline 14 — Stale process or stuck gate holder

1. Old dispatcher holds/held domain authority and becomes stalled or unreachable.
2. Another process attempts takeover based only on timeout.
3. Refuse takeover/dispatch until the old incarnation is confirmed terminated or fenced from owner mutations and acceptance. A new lock object or epoch number without enforcement is insufficient.
4. Recover durable attempts and obligations, then admit new work only after exclusive authority is established; unresolved old attempts are not replayed.

## 13. Failure model, exclusivity and recovery

The initial safety model is one trusted local arbitration process using ADR-004 qualified durable owner storage. It covers concurrent tasks, owner-operation failure, process crash/restart, lost local acknowledgment and admitted local machine termination/restart with intact qualified storage. It does not claim highly available multi-process dispatch, network-partition failover, hostile in-process isolation or external exactly-once delivery.

The realization must establish exclusive operating authority over the participating state and dispatch domain, with storage/host enforcement preventing concurrent incompatible writer incarnations. A process lock alone cannot fence a second process or old surviving dispatcher. Initial operation uses fail-stop restart: a replacement is admitted only after the old incarnation cannot mutate participating records or reach the acceptance boundary, and the relevant state has recovered. No automatic timeout-based failover is selected. The concrete local exclusivity primitive must be qualified before use; its mere name is not proof.

If stronger fencing is later introduced, owner writes and actual Adapter acceptance must reject stale authority, not just label log entries with a new epoch. A remote participant outside that enforcement cannot be assumed fenced. If termination/exclusivity is uncertain, affected new dispatch remains unavailable. This is conservative operation under an explicit scope, not a universal availability guarantee.

Recover each owner's claims, revisions, consumed Approval, reservations/usage and outcomes separately. Invoking planes recover exact handoff knowledge and effect/evidence/settlement obligations. Acquire fresh current authority and exclusive domain before new protected work. Missing records or rollback cannot be treated as unspent balances, unused Approval or absence of prior H. Durable attempt without confirmation stays uncertain until legitimate reconciliation; no blind replay loop.

Repair workers use bounded Principal/Tenant/current permissions and exact obligations. They cannot mutate foreign owner balances directly. Queries/status disclosure remain governed even if callers know an effect/claim ID. A denial to disclose retained results does not authorize repeating the effect.

| Risk | Mitigation and limitation |
|---|---|
| Direct mutation bypasses arbiter | Owner-level participation enforcement across admin/worker/Port paths; otherwise mechanism is not qualified |
| Forged claim or copied balance | Validate issuer/owner/scope/revision and exact action; Resource owner alone mutates capacity |
| Approval UI/context deception | Bind actual approved target/revisions/presented evidence and eligible Human; material changes invalidate use |
| Deputy broad credentials | ADR-005 requester/delegation/deputy intersection and exact target/purpose at H |
| Reentrant initializer/Adapter callback | Bounded non-reentrant acceptance; no arbitrary user callbacks under final gate |
| Clock uncertainty/scheduler pause | Qualified actual acceptance timing; refuse unsupported hard-validity scope |
| Untracked remote revocation | Unsupported unless equivalent authoritative order/currentness is demonstrated; no stale-cache exception |
| Double writer/takeover | Verified termination or enforceable fencing before replacement; no timeout-only exclusivity |
| Lost/forged usage report | Exact report identity, entitled source, bounded liability and reconciliation; no automatic refund |
| Evidence/diagnostic leakage | Safe refs, tenant-scoped current access, no raw Secrets/private reasoning |
| Arbiter denial-of-service | Bounded preparation/final work, finite roots, no external waits under gate; fail closed on stuck participant |

Implementation remains in existing invoking/enforcement and Resource/Approval owner responsibilities under ADR-002. Technical shared arbitration cannot become a security manager, balance owner, Kernel service or global Execution state machine. Exact package/API choices for a small internal coordination primitive are deferred; owner contracts must not import peer implementation state. Direct Capability dispatch can use this without AI or Work Coordination, unless its particular action actually requires delegation semantics.

No Q-06 answer is smuggled into arithmetic. Accountable domain Governance/Resource authorities must approve units, precision/rounding, measurement scope, uncertainty, conversion/rate, quota/reset, overrun/overdraft and settlement rules as applicable. Their absence blocks the associated claim. The demonstration with 100/30 units is not a default allocation, billing policy or numerical precision standard.

## 15. Solo burdens, consequences and Type-1 migration

| Burden | A — Selected local gate | B — Co-located atomicity | C — Distributed bounded claims |
|---|---|---|---|
| Implementation complexity | Moderate gate participation/owner guards; narrow failure scope | Cross-owner transaction integration plus external handoff gap | Highest protocol, fencing and interval proof |
| Operational complexity | One live domain, conservative fail-stop recovery | Shared-store coordination | Multiple participant availability/time domains |
| Maintenance burden | Track every invalidating mutation and acceptance boundary | Store/transaction coupling | Protocol and claim-version evolution |
| Testing burden | Interleavings, crash window, bounded timing and bypass cases | Transaction cases plus same external window | Partition, drift, failover and revocation propagation |
| Local-development burden | Minimal infrastructure; explicit owner state/claims | Shared transactional setup | More processes/simulated failures |
| Deployment burden | Exclusive local authority, no automatic failover | Co-location requirement | Qualified distributed services/fencing |
| Learning curve | Order versus ownership/atomicity must remain clear | Easy to overclaim transaction coverage | Most complex currentness/failure reasoning |

Benefits: a comprehensible revocation/handoff order, authoritative bounded use, honest partial consumption and local-first operation. Costs: serialized final sections, strict mutation-path discipline, conservative availability, persistent claim/obligation volume and potential throughput bottlenecks. Accepted limitations include unqualified hard real-time scope, remote invalidation, hostile shared-process code and multi-process availability; these remain unsupported rather than weakened.

Type 1 cost arises from durable effect/claim identities, Approval history, liability, allocation lineage and externally released effects. Replacing arbitration must preserve them and prove the same order at the actual acceptance boundary. Quiesce/fence old dispatch authority, reconcile in-flight/unknown work, transfer exact owner state under ADR-004, qualify the replacement and admit it before resuming. Do not let two arbiters independently spend the same scope during migration. An old snapshot cannot reverse completed effects or consumed uses.

Reconsider on measured contention, large claim volume, independently managed remote owners, required multi-process availability, cross-region deployment, strict real-time requirements or stronger isolation. Partitioning by tenant/resource may become useful only with proof that shared parent allocations, cross-scope controls and one effect's participants retain a common authoritative order. A distributed lease proposal must preserve effective restrictive updates and failure bounds, not merely improve throughput by allowing stale use.

## 16. Proof obligations and downstream decisions

Future evidence must demonstrate: complete arbiter participation; exclusive incarnation and no stale acceptance; simultaneous over-capacity claims; parent/child conservation; all revocation race positions in timelines 1–5; exact Approval context and no automatic refund; partial dimensions; wall-clock/uncertainty expiry at actual H; missing owner/evidence failures; durable-attempt crash window; unknown charge after expiry; duplicate usage/release/settlement; nested retries; stop/publication races; repair disclosure authority; and deterministic direct Capability independence.

Ordering reasoning in §7 is not a substitute for implementation experiments validating the actual storage, clock, Adapter acceptance and failure behavior. No tests, benchmark, fault injection, runtime code, schemas or backend choices are created here. A Python lock or successful happy-path request is not a conformance proof. Guarantees must name actual failure domain, scope and evidence; no unqualified exactly-once claim is permitted.

ADR-008 inherits one invoking-plane dispatch obligation, exact action/claim set, retained owner outcomes and the explicit uncertain handoff window. It still decides concrete effect identity/equivalence, deduplication horizons, provider retry and reconciliation machinery before corresponding effects are enabled. ADR-010 supplies purpose-bound Secret use; any required Secret validity must participate in a proven protected boundary. ADR-011 qualifies release evidence; ADR-012/013 retain isolation/observation choices. No later ADR is written here.
