# ADR-024 — Remote Model Disclosure Admission (REMOTE-MODEL-DISCLOSURE-1)

**Status:** ACCEPTED — 2026-10-09, by explicit maintainer decision, as
drafted. History: proposed 2026-10-09 as the REMOTE-MODEL-DISCLOSURE-1
decision following ADR-023's acceptance; accepted the same day without
change. Acceptance authorizes **the disclosure architecture only** and the
planning of the §17 slices. It does not:
- implement or qualify any REMOTE provider;
- enable REMOTE runtime behavior (the implemented runtime still refuses
  `REMOTE` at open);
- authorize disclosure of repository, task or any other content;
- authorize KISSKI calls.

Each §17 slice requires separate explicit authorization.

**Date:** 2026-10-09

**Decision class:** C — required before any model-visible content leaves the
local trust boundary

**Reversibility:** Type 2

**Decision owner:** Security / Governance (information flow) with the Model
invocation plane maintainer

**Depends on:** ADR-003 (configuration revisions), ADR-005 (authority),
ADR-009 (evidence custody), ADR-014 §14.5–14.6 and §14.18, ADR-020 (media
precedent), ADR-023 (credential profile; independent gate).

**Drivers:**
- SEC-039: enforce declared provider data-use, retention, training-use,
  residency, external-transfer and confidentiality constraints before
  disclosure; unknown mandatory guarantees block the call.
- SEC-066: a small, versioned classification vocabulary with an assigning
  authority; unknown required classification prevents disclosure.
- SEC-067: flows are authorized by source, destination, purpose, recipient
  and classification; derived content keeps its restrictions; sanitization is
  not declassification.
- SEC-025: changes to data-handling configuration are revisioned and
  attributable.

## 1. Context and form

ADR-014 §14.6 reserves REMOTE-MODEL-DISCLOSURE-1 as "a later slice … under a
maintainer decision". It requires declared data-use conditions, retention,
training use, residency where required, and explicit operator admission
before real content is sent to any remote model endpoint. Unknown or
undeclared conditions fail closed. ADR-023 (accepted 2026-10-09) made
credentialed remote transport architecturally admissible but left disclosure
to this decision.

**Why a new ADR rather than another ADR-014 addendum.** ADR-014 decides the
public host composition and the provider-settings union. This decision
introduces governance concepts that ADR-014 does not own:
- a versioned disclosure vocabulary (SEC-066);
- provider-condition declarations with evidence bases;
- operator admissions;
- an invocation-time information-flow gate;
- disclosure evidence.

The concepts must apply to every remote Model provider (OpenAI-compatible,
Ollama, trusted contributions) and later to other remote processors. ADR-020
set the precedent of a separate disclosure decision for media. ADR-014 keeps
only a pointer (§14.6 note).

**First intended consumer:** ForgeAI Coding Agent and Independent Reviewer
on a remote OpenAI-compatible endpoint (first endpoint: KISSKI). KISSKI is
the motivating consumer, not the contract.

## 2. Decision question

What exact provider data-use facts and operator admissions must be known
before model-visible content may leave the local trust boundary for a
`REMOTE` model endpoint?

## 3. Decision summary

A `REMOTE` model invocation may send content only when all of the following
hold, evaluated by the governed Model invocation plane before transport, at
every invocation:
1. A **disclosure declaration** states the content classes of this
   invocation (§4). It is assigned by trusted composition and never derived
   from model output or content.
2. A current, unexpired **operator disclosure admission** (§6) binds this
   binding, provider, endpoint origin, model, consumer and those classes.
3. The admission pins a **processor declaration** revision (§5) whose
   facts satisfy every condition that the admission requires for those
   classes. Mandatory facts are known.
4. The mechanically checkable endpoint properties match (§5.1).
5. If the binding is credentialed, ADR-023 SRCP-1 passes independently
   (§10).

Otherwise the invocation refuses before transport, with nothing sent. Content
is never downgraded, redacted or rewritten to make a refused call acceptable.
`LOCAL` bindings are unaffected.

## 4. Disclosure classes: vocabulary `model-disclosure/1`

A closed, versioned vocabulary, kept deliberately small. It describes
**provenance**, which trusted code knows reliably, not semantic sensitivity,
which nothing in v1 can determine reliably.

| Class | Meaning | Lineage rule |
| --- | --- | --- |
| `SYNTHETIC` | Operator-authored text, declared non-sensitive, derived from no repository, application, user or third-party data. | Combining it with any other class makes the invocation that other class. |
| `PLATFORM_INSTRUCTION` | Fixed instructions authored in source by LegoAI or the application: Agent definitions, output contracts. No task, user or repository data. | — |
| `TASK_TEXT` | Operator-supplied task text: objective and constraints. | — |
| `REPOSITORY_CONTENT` | Text or metadata read from an operator-identified repository: file contents, paths, candidate contents. | Scoped to a **repository identity** (§6). |
| `DERIVED_DIAGNOSTIC` | Content derived from repository content by tools or agents: check-output excerpts, review findings, proposal renderings. | Keeps its source restrictions (SEC-067). It is admissible only where `REPOSITORY_CONTENT` is admitted for the same repository identity. |

- **Assigning authority.** The trusted component that assembles the
  model-visible input (an Agent implementation or the application's
  composition) declares the class set for each invocation, from how it built
  the input. Model output, repository content, provider responses and Agent
  messages cannot assign or change classes.
- **Unknown.** An invocation with no declaration is `UNCLASSIFIED`.
  `UNCLASSIFIED` never goes to `REMOTE`.
- **Combination.** An invocation's classes are a set. Every member must be
  admitted. Restrictions combine without weakening.
- **Extension.** New classes, for example media classes, require a new
  vocabulary revision through a decision. Existing admissions never cover
  classes added later.
- **Not a DLP system.** No content inspection, secret scanning or automatic
  classification is selected. Absent a separately authorized transformation
  capability, a classifier's verdict could not declassify anyway (SEC-067).

**Carrier.** The declaration travels as a typed value on the existing
governed invocation path from the request assembler to the Model invocation
plane. It is never inside message text. ModelPort's signature and the
provider wire format do not change. The exact carrier type and module are an
implementation decision under ADR-002.

## 5. Processor declaration: provider conditions with explicit evidence basis

An operator-authored, versioned record describing one remote processor. Every
fact carries a **basis**:
- `VERIFIED` — mechanically checked by LegoAI at each invocation;
- `PROVIDER_DECLARED` — taken from the provider's own published terms, with
  the source reference (document title or URL) and the date retrieved;
- `OPERATOR_ATTESTED` — stated by the operator on their own authority (for
  example from a contract or institutional agreement);
- `UNKNOWN`.

A policy URL is a source reference, not automatic trust. LegoAI never fetches
or interprets it.

### 5.1 Mechanically verified properties (always mandatory)

| Property | Check |
| --- | --- |
| Endpoint origin and API root | Exact match of the scheme, host, port and versioned API root of the binding against the admission. No redirects. |
| Transport | `https` with certificate and hostname verification. Plaintext and tunnel-attested transports are not admitted in `model-disclosure/1`. A loopback tunnel to remote processing stays `REMOTE` (ADR-014 §14.5) and cannot satisfy this check. |
| Model identity | The configured model id is in the admission. The provider's returned model id must equal it; the existing adapters already reject a mismatch. |
| Deployment | `REMOTE` declared on the binding (ADR-014 §14.5). Never inferred. |

### 5.2 Declared or attested facts

| Fact | Values | Mandatory for |
| --- | --- | --- |
| Provider identity | Legal or service name of the processor and operator of the endpoint. | All classes. |
| Processing location / residency | Jurisdiction or region set, or `UNKNOWN`. | All non-`SYNTHETIC` classes. |
| Retention of inputs and outputs | `NONE`, `BOUNDED` (a stated maximum duration), `UNBOUNDED`, or `UNKNOWN`. Includes provider-side logging of content. | All non-`SYNTHETIC` classes. |
| Training or model-improvement use | `NO`, `NO_BY_CONFIGURATION` (an opt-out the operator attests is in effect), `YES`, or `UNKNOWN`. | All non-`SYNTHETIC` classes. |
| Human access to content | `NONE`, `RESTRICTED` (for example abuse handling or support, as declared), `YES`, or `UNKNOWN`. | All non-`SYNTHETIC` classes. |
| Subprocessors | A declared list, `NOT_MATERIAL` (operator attestation), or `UNKNOWN`. | `REPOSITORY_CONTENT` and `DERIVED_DIAGNOSTIC`. |

`SYNTHETIC` content is non-sensitive by its own definition. For it, the
location, retention, training, human-access and subprocessor facts may remain
`UNKNOWN`. They are recorded as unknown and never asserted. The §5.1
properties and provider identity remain mandatory.

The declaration has a revision identity. Any change creates a new revision.
An admission pins exactly one revision, so a changed declaration invalidates
its admissions until they are re-admitted.

## 6. Operator disclosure admission

An explicit, operator-controlled configuration record. It lives in the host's
revisioned operator configuration (ADR-003; SEC-025). It is never in a
provider setting, request, repository file or model-visible content.

| Field | Rule |
| --- | --- |
| Admission id and revision | Attributable to the operator principal. Any change is a new revision. |
| Binding id(s) | The exact `ModelBindingConfig` names it covers. |
| Provider identity, endpoint origin and API root | Must equal the binding and the pinned declaration. |
| Deployment | `REMOTE` only. |
| Model id(s) | An explicit list. No wildcard. |
| Consumer / application | For example `forgeai`. Purposes: `CHAT`, `EMBEDDING`. |
| Pinned processor declaration revision | Exactly one. |
| Permitted classes | A subset of `model-disclosure/1`. |
| Condition requirements | Per permitted class, the acceptable values. For example: retention ∈ {`NONE`, `BOUNDED` ≤ D}; training ∈ {`NO`, `NO_BY_CONFIGURATION`}; location ∈ {set}; human access ∈ {…}. The operator may only tighten the §5.2 mandatory set, never loosen it. |
| Repository identities | Required if `REPOSITORY_CONTENT` or `DERIVED_DIAGNOSTIC` is permitted. These are operator-declared identities of the repositories whose content may be sent. |
| `not_before` / `not_after` | Both required, with no default. The review period is the operator's choice; the implementation may impose a maximum. |

Rules:
- **Only an operator grants admission.** No model, repository content,
  provider response, Agent message or configuration default can create,
  extend or widen one.
- **Existence is not authority.** An endpoint existing, a credential
  existing or a model being available grants nothing.
- **Re-checked at every invocation.** Admission is evaluated at host open (to
  refuse an inadmissible REMOTE binding early) and **again at every
  invocation**. Expiry, a revision change or revocation takes effect for the
  next invocation. A request already handed to transport is not recalled;
  its disclosure effect is recorded truthfully (§9).

## 7. Fail-closed rules: refuse before transport

The invocation refuses, with nothing sent and a safe refusal category
recorded, when any of the following holds:
1. no admission covers the binding, or the admission is not yet valid,
   expired or revoked;
2. provider identity, endpoint origin, API root or deployment differs from
   the admission or the pinned declaration;
3. the transport is not `https` with a verified certificate;
4. the model id is not admitted;
5. the consumer or purpose is not admitted;
6. the invocation is `UNCLASSIFIED`, or any declared class is not admitted;
7. `REPOSITORY_CONTENT` or `DERIVED_DIAGNOSTIC` has no admitted repository
   identity, or a different one;
8. a fact that is mandatory for a declared class is `UNKNOWN`, or it fails
   the admission's condition requirements (for example residency unmet or
   unknown, training use unacceptable or unknown, retention unacceptable or
   unknown);
9. the pinned declaration revision is no longer current;
10. for a credentialed binding, SRCP-1 refuses (ADR-023; independent).

Never permitted:
- silently dropping, truncating, redacting or rewriting content to fit an
  admission;
- falling back to another binding or provider;
- reclassifying to a weaker class.

A future transformation capability (for example redaction with entitled
declassification) would need its own decision.

The refusal maps to an existing Model failure category (preflight / NONE).
No new effect vocabulary is introduced.

## 8. ForgeAI as first consumer

**Write authority and disclosure authority are separate.** A file being an
editable target, or operator-selected read-only context, says nothing about
whether it may be sent to a remote processor.

**ForgeAI model-visible material, by class:**

| Material | Class |
| --- | --- |
| Agent definitions (system prompts, output contracts) | `PLATFORM_INSTRUCTION` |
| Task objective and constraints | `TASK_TEXT` |
| Target paths and current text, read-only context, candidate contents on rework | `REPOSITORY_CONTENT` |
| Bounded check feedback, review findings in rework constraints, the rendered proposal and check material given to the Reviewer | `DERIVED_DIAGNOSTIC` |

Never disclosed (and still not): Git state, Docker sandbox internals, and
files outside the operator's targets and context.

**v0.1 rule: explicit operator admission, no autonomous classification.**
- ForgeAI declares the fixed class set {`PLATFORM_INSTRUCTION`, `TASK_TEXT`,
  `REPOSITORY_CONTENT`, `DERIVED_DIAGNOSTIC`} for every remote Coding Agent
  and Reviewer invocation, with the run's repository identity. The admission
  must cover all four.
- **Per-run confirmation, in addition to the standing admission.** Before the
  first remote model call, the startup summary shows:
  - the remote processor (provider, origin, model);
  - the admission id and its expiry;
  - the declared classes;
  - the exact repository paths whose content will be disclosed: every target
    and every `--context` file.

  The operator must answer an explicit `y` to disclosure (default No; EOF or
  a non-interactive terminal declines). Declining calls no model and writes
  nothing.
- Rework and review disclose only material derived from the same confirmed
  files. Feedback cannot add files (unchanged ForgeAI rule).
- The checks stay local in the Docker sandbox. Nothing about them is
  disclosed beyond the bounded derived excerpts above.

## 9. Disclosure evidence: safe facts only

For each REMOTE invocation, the Model invocation plane records the following,
under ADR-009 custody:
- admission id and revision, and the pinned declaration revision;
- binding, provider identity, endpoint origin and model id;
- the declared classes and repository identity, if any;
- operation / attempt id and timestamp;
- the disposition: `REFUSED` with a safe category, or a **disclosure effect**
  of `NONE`, `PARTIAL`, `COMPLETED` or `UNKNOWN` (the ADR-020 pattern: a
  named effect separate from the Model result).

Not required, and not retained merely to prove disclosure: prompts, source
code, responses, credentials or headers. Whether any content is kept is a
separate custody policy, outside this decision.

## 10. Relationship to ADR-023 (SRCP-1)

The two gates are independent, and both must pass:
- **Disclosure admission** answers: may this content go to this remote
  processor?
- **SRCP-1** answers: may this credential be used for this exact remote
  invocation?

Neither implies the other.
- A future **credential-free** remote provider still requires disclosure
  admission.
- A **credentialed LOCAL** endpoint is not made admissible by this decision.
  ADR-014 §14.18 keeps it unsupported.

**Recommended order of checks within one invocation:** disclosure admission
first (no material is realized for a call that may not be made), then the
SRCP-1 gate and handoff. Both are rechecked at every invocation.

## 11. Synthetic compatibility probe

The future first compatibility call (for example to KISSKI) needs only a
minimal admission:
- binding: the probe binding only;
- endpoint origin and API root: exact;
- model: one explicit model id;
- consumer: an operator probe tool;
- classes: `SYNTHETIC` only;
- `not_after`: short, chosen by the operator;
- processor declaration: provider identity known; all §5.2 facts may be
  `UNKNOWN` and are recorded as unknown.

The probe sends only a fixed operator-authored string, for example
`Return exactly the word READY.`, declared `SYNTHETIC`. It expects a short
text reply, with no schema. A model-list request (`GET …/models`) carries no
model-visible content. It still requires the probe admission and, if
credentialed, SRCP-1. No such operation exists in the adapter today, so it is
part of a future probe slice. *(Amended 2026-10-09 by §22: the model-list
request is a provider-control operation under its own operator admission,
not a disclosure admission; its method follows the verified provider
documentation.)*

This admission grants **nothing** for repository content, task text or any
ForgeAI run. The probe is not performed by this decision.

## 12. Facts for the first endpoint: TO BE VERIFIED BEFORE ADMISSION

This decision asserts **no** KISSKI facts. Before any KISSKI admission beyond
`SYNTHETIC`, the operator populates a processor declaration from
authoritative sources:

| Fact | Status |
| --- | --- |
| Provider identity and operating entity | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Endpoint origin and versioned API root | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Model ids offered | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Processing location / residency | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Retention and logging of prompts and outputs | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Training / model-improvement use | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Human access to content | TO BE VERIFIED BEFORE KISSKI ADMISSION |
| Subprocessors | TO BE VERIFIED BEFORE KISSKI ADMISSION |

## 13. Other providers

- **Remote Ollama.** `OllamaSettings` gains the required `deployment` field
  that ADR-014 §14.5 already foresaw. That needs a migration note for
  existing configurations; classification is still never inferred. Remote
  Ollama is then subject to this same gate. The recorded existing gap (any
  http/https host accepted without a check) closes when that slice is
  implemented.
- **TrustedModelContribution.** These are trusted in-process code, and the
  host cannot observe where they process content. Until a contribution
  declares a deployment fact, using one to reach remote processing is a
  recorded gap, not a supported mode. A follow-up decision may require the
  declaration.

## 14. Future remote generative media

The model is reusable: processor declaration, operator admission, versioned
classes, a gate before transport, and safe disclosure evidence. Media
disclosure involves prompts, source images, masks, embeddings and generated
artifacts. Those need **media-specific classes and conditions** in a later
vocabulary revision. ADR-020 continues to govern person images, and remote
Virtual Try-On and personal-image transfer **remain prohibited**. This
decision authorizes no image upload and no media disclosure.

## 15. Options considered

| Option | Assessment |
| --- | --- |
| A per-binding "remote allowed" flag | Rejected. No provider conditions, no classes, no expiry; it fails SEC-039 and SEC-066. |
| **Standing operator admission + class vocabulary + processor declaration (chosen)** | Meets SEC-039, SEC-066 and SEC-067 with the smallest vocabulary. The facts' bases stay honest. Reusable by other processors. |
| Human approval of every invocation only | Rejected as the sole mechanism: approval fatigue, and no record of provider conditions. Kept as ForgeAI's per-run confirmation layered on the admission (§8). |
| Automatic content classification / DLP | Rejected for v1: unreliable, and a verdict cannot declassify (SEC-067). |
| Trusting provider policy URLs automatically | Rejected. A URL is a source reference; facts keep their basis. |

## 16. Consequences

**Positive:** remote use becomes possible with explicit, attributable,
expiring operator decisions. The same model serves every remote processor.
The probe is possible without exposing repositories.

**Negative:** operators must research and record provider facts. Admissions
expire and need review. ForgeAI adds a disclosure confirmation per run. A
small governance store and invocation gate must be built and qualified.

**Neutral:** LOCAL behavior is unchanged. ModelPort, `ChatRequest` content
and the adapter wire format are unchanged.

## 17. Implementation gates (each needs explicit authorization)

1. ADR-024 accepted. The ADR-014 §14.6 pointer becomes a reference to the
   accepted decision.
2. Governance values, revisioned host configuration and validation at open
   for the vocabulary, processor declarations and admissions.
3. The invocation-time gate in the governed Model invocation plane, before
   any adapter call, plus refusal mapping and disclosure evidence.
4. The declaration carrier on the governed request path, and declarations by
   the Engineering Agents or ForgeAI composition.
5. ForgeAI per-run disclosure confirmation.
6. The `OllamaSettings` `deployment` field migration.
7. Only then: REMOTE enablement (ADR-014 §14.18 item 2), together with the
   ADR-023 slices for credentialed bindings.

## 18. Qualification gates (offline)

- **Fail-closed matrix.** Every §7 rule refuses with zero bytes sent,
  verified with a synthetic HTTPS server that counts connections.
- **LOCAL regression.** LOCAL bindings are unaffected, with no declaration
  required.
- **No widening.** Model output, repository text and provider responses that
  attempt to add classes, models or repositories cause no change.
- **Expiry.** The admission expires between invocations, and the next
  invocation refuses.
- **Revision pinning.** A changed declaration revision invalidates the
  admission.
- **Evidence.** It contains only §9 facts. Canary content and prompts are
  absent.
- **ForgeAI.** The confirmation lists exactly targets plus context. Declining
  makes no model call and writes nothing. Rework and review disclose only
  derived material.
- **Probe admission.** It permits only `SYNTHETIC`. A `TASK_TEXT` or
  `REPOSITORY_CONTENT` declaration under it refuses.

## 19. Non-goals

- Implementation of any of the above.
- Any KISSKI fact or call.
- Credential handling (ADR-023).
- Content custody or retention by LegoAI.
- Media disclosure.
- Multi-tenant, hosted or unattended use.
- Redaction or declassification.
- Automatic provider selection.

## 20. Revisit triggers

- A need for semantic sensitivity classes beyond provenance.
- Multiple operators or tenants.
- Unattended use.
- A provider offering machine-readable, verifiable data-use attestations.
- Media disclosure.
- Any disclosure observed without a matching admission.

## 21. Decision

Requested at proposal: **ACCEPT** ADR-024 as drafted, authorizing only the
ADR-014 §14.6 pointer update and planning of the §17 slices, each still
separately authorized; **or REJECT** it, leaving REMOTE refused.

**Recorded 2026-10-09: ACCEPTED** by explicit maintainer decision, as
drafted. Done under this acceptance:
- the ADR-014 §14.6 pointer was updated;
- the §17 slices were planned in the roadmap.

No implementation, no REMOTE enablement and no provider call was authorized.

## 22. Addendum — provider-control model discovery (PROVIDER-MODEL-DISCOVERY-1), 2026-10-09

**Status:** ACCEPTED 2026-10-09 by explicit maintainer decision (authorization
of PROVIDER-MODEL-DISCOVERY-1). §§1–21 are unchanged; the §11 sentence on the
model-list request is marked as amended. This addendum adds no disclosure
class and changes no rule for model-visible content.

1. `model-disclosure/1` governs the remote disclosure of model-visible
   application content. Every rule in §§3–9 continues to apply to it,
   unchanged.
2. A credentialed provider-control operation discloses no such content.
   The only one admitted is an explicitly operator-initiated model-catalog
   query (`{api_root}/models`). It is outside that vocabulary: it carries no
   disclosure declaration, and no class (including `SYNTHETIC`) is assigned
   to it.
3. Such an operation still requires all of the following, each checked
   before transport:
   - its own explicit, typed, time-bounded operator admission, bound to the
     exact provider, https origin, API root, operation, consumer and
     credential revision;
   - exact recipient binding with no redirect;
   - durable external-attempt custody (INTENDED before the handoff);
   - current Secret authority under a distinct Secret-use purpose;
   - ADR-023 SRCP-1 transport.

   One request is made, with no retry or fallback.
4. The two authorities are structurally distinct. A provider-control
   admission grants no authority to disclose model-visible content and
   cannot be converted into a disclosure admission. A disclosure admission
   grants no authority for a provider-control operation.
5. A returned model list is an observation at that moment. It is not policy,
   configuration, routing authority or evidence of long-term availability.
   It never changes a binding or an admission.
6. The request method follows the provider's verified documentation; for the
   first endpoint that is `POST` with an empty body. §11's `GET` was
   illustrative.
