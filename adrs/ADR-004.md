## 2. Decision question and initial scope

What consistency, commit, acknowledgment, persistence and recovery boundary will the first reference runtime use for authoritative owner-local state while preserving revisions, tenant scope, history, effects and liabilities without global atomicity?

The initial slice is a local modular monolith, one explicitly bound tenant and a deterministic direct Capability. It does not require Agent, Model, Team, Workflow, RAG, persistent Memory, a broker or distributed deployment. It still needs scoped authority, revision-safe owner mutations, mandatory evidence prerequisites, truthful effect tracking and recoverable obligations for the features it admits.

Persistence here recovers owner records and the knowledge needed to make safe next decisions. It does not promise continuation of a Python stack, transparent replay of a Tool invocation, durable Workflow execution or reconstruction of arbitrary external state. Later checkpoint support must declare a compatible captured revision set, driver-owned state meaning and effect boundary; it cannot infer those from a recovered Execution row.

## 3. Decision

**Select durable owner-local transactional records with conditional expected-revision commit, necessary immutable history, and durable operation/result/obligation facts.**

The behavioral architecture is:

1. Each owner receives an explicitly scoped operation and validates its domain rules, original expected revision/absence, current authority prerequisites and applicable evidence requirements.
2. One owner-local transaction conditionally establishes the new state, new revision, required immutable facts, operation result and outstanding obligations together. It cannot expose a partially committed set.
3. A successful mutation acknowledgment is issued only after that set is durably committed under §4's failure model. Receipt and queued acceptance are distinct acknowledgments.
4. Cross-owner handoffs use explicit operation and exact record references. Their outcomes are separately committed. Missing responses preserve uncertainty; failed downstream work leaves completed upstream facts intact.
5. After restart, each owner verifies and recovers its current state, retained interpretation records, retained operation outcomes and unresolved obligations. Guarded work waits for the state and current controls it needs. Recovery never silently substitutes current configuration or repeats uncertain external work.

Use **one local persistence realization initially**, with separate owner scope and mutation boundaries. Its technology/product, concrete layout, serialization and integration APIs remain undecided. Separate physical stores are permitted later where justified. Neither co-location nor separation changes logical authority.

This is Alternative B with the history and obligation records that correct current-state mutation already requires. It is not full event sourcing: authoritative current state is committed directly, and recovering it does not require replaying every domain event. It does not require a universal append journal, generic event store, transaction framework, repository facade, universal persistence Port or Saga framework.

## 4. Declared failure model and durability scope

### 4.1 Intended guarantee

For each supported stateful owner, successfully acknowledged commits and their required owner-local facts must survive process termination and runtime restart, normal storage-process restart if one exists, and local machine termination/restart **with the storage medium intact and honoring the qualified durable-write contract**. Sudden shutdown requires the realization to demonstrate the necessary persistence/flush behavior; a process-memory cache or an unverified storage acknowledgment is insufficient.

The scope recovered is **current authoritative owner state plus exact retained history needed for interpretation, retained operation results within declared coverage, and unresolved obligations/liabilities**. These are descriptive limits, not new canonical profile names. Retention and stronger evidence requirements remain governed by the relevant policies and contracts. A capability requiring a stronger failure guarantee cannot be admitted on this minimum alone.

This is a required realization target, not a claim that a not-yet-selected store has passed crash tests. Before any corresponding runtime guarantee is advertised, the implementation must qualify the actual storage stack, configuration, failure coverage and acknowledgment behavior. It may not silently downgrade this selected scope to volatile operation when storage is unavailable.

| Failure or condition | Required interpretation and response |
|---|---|
| Runtime/process killed, including abrupt termination | Recover committed owner sets; discard uncommitted storage work; no inference that a remote effect did not happen |
| Normal storage-process restart | Same durable commits survive; runtime may be unavailable until authoritative reads and commit status are established |
| Local machine termination/restart with intact qualified storage | Acknowledged durable sets survive; qualify the actual stack, including abrupt shutdown, before claiming this |
| Lost response or deadline expiry | Caller lacks outcome knowledge until authoritative status establishes it; timeout is not evidence of no effect |
| Owner/store dependency unavailable | Return truthful unavailability/uncertainty; preserve known references and gate dependent work; do not start an empty replacement owner |
| Adapter unavailable after restart | Recover the Execution/effect/obligation records, but dependent continuation or reconciliation may remain unavailable |
| Corrupt, incompatible or incomplete authoritative records | Fail the affected scope closed; retain safe diagnostic/obligation references; no reset to defaults |
| Backup restore or rollback to an earlier image | Separate recovery procedure; cannot be treated as normal latest-state restart or proof of current authority |
| Storage device loss, lost volume, catastrophic filesystem loss, regional/datacenter disaster | No survival promise selected; report loss/unavailability honestly and invoke separately governed recovery if available |
| Malicious storage administrator, Byzantine store, undetectable coordinated rollback | No resistance proof claimed by a transaction alone; protection/freshness evidence must match the admitted threat scope, otherwise affected use stays unsupported |

Normal process crash recovery assumes the original persistence domain has not been replaced or rolled back. That assumption must be checked to the degree required by the threat model; a locally self-consistent database cannot prove its own freshness against an attacker who rolls back every local witness.

### 4.2 Volatile data that remains legitimate

Uncommitted candidates, disposable caches, in-memory scheduling hints and rebuildable read views may be volatile. They cannot be the only copy of an acknowledged authoritative fact, an unresolved liability, or a required recovery obligation. Optional telemetry may have explicitly weaker guarantees. Calling an authoritative record a cache does not exempt it from this decision.

## 5. Owner state model and categories

| Category | Logical owner and retained meaning | Mutation/recovery boundary |
|---|---|---|
| Effective configuration and mutable selection | Application Composition: immutable effective revision, exact contract/source meaning; independently revisioned selection/head | Preserve R1/R2 and exact bindings; conditionally change selection, never rewrite R1 |
| Plugin admission, configuration binding and lifecycle | Plugin Lifecycle: release/config/dependency references, permitted transition, activation identity, history, cleanup obligations | Commit current lifecycle revision and required transition facts together; recovering active history is not proof a live Plugin is initialized/healthy |
| Catalog registrations and offers | Catalog owns registration/offer state; its observations of Plugin eligibility are references/projections of foreign facts | Persist authoritative registrations; rebuild only declared derived views; stale eligibility cannot supersede Plugin authority |
| Resolution records | Resolution owns exact candidate/config/rule evidence and result references where required | Preserve historical selection meaning; a recovered resolution is not fresh authorization or dispatch permission |
| Execution records | Execution Coordination: immutable attempt identity, current canonical state, effects, context/config/activation references and causal results | Atomic legal transition with retained prior facts; driver state remains with its owner, if that driver is supported |
| Protected invocation/effect observations | Invoking plane; Tool Action Mediation for Tool effects | Preserve dispatch knowledge, effect identity/references, liabilities and reconciliation facts; no claim that storing them atomically controls the external target |
| Identity, tenant, authorization, Policy and Approval records | Respective Governance owners, not one configuration or generic security repository | Tenant-scoped authoritative mutations and retained consumption/revocation facts; current eligibility still evaluated |
| Resource claims/accounting | Resource Admission and Accounting | Atomic owner invariant across all affected local allocation/claim records; recover outstanding consumption and uncertainty, not reset balances |
| Evidence records and custody | Evidence owner under its declared guarantees; source owners retain their own mutation/obligation facts | Owner commit does not automatically establish separate evidence custody acknowledgment |
| Operation outcomes and obligations | Owner of the mutation; responsible coordinator records its own cross-owner relationships | Scope/result/coverage and unresolved obligations discoverable after restart without an in-memory queue |

This is a reusable consistency boundary, not a requirement to implement all categories now or to impose identical record layouts on every owner. Shared definitions may retain their explicit publication scope/custodian under S-10; operational records always carry the effective tenant where required.

### 5.1 Persistence unit

The unit is an **owner-local transaction for one declared domain mutation**. It may change one or several records of that logical owner in a compatible tenant/authority scope. It must include every local record or predicate necessary to preserve that mutation's invariant, including required history and result/obligation records. It is neither automatically one row nor automatically every record the owner has.

For example, two claims against one allocation cannot protect separate claim rows while both rely on an unchanged balance read. The mutation must guard the shared allocation or equivalent invariant boundary and commit the affected claim/accounting records together. Merely checking the expected revision of each newly created claim would allow write skew. This specifies the substrate, not ADR-007's arbitration or settlement rule.

An owner-specific adapter/implementation wraps any common technical primitive. A `GenericRepository[T]` that hides transitions, tenant checks or cross-owner writes is not an acceptable semantic boundary. No generic state-machine engine owns all lifecycles.

## 6. Alternatives and comparison

### A — Bounded volatile owner state

This is credible for a deliberately bounded, disposable, non-recoverable session: owner-local guards and retained in-process outcomes can prevent concurrent corruption while the process exists. It minimizes infrastructure and setup. It is not inherently nonconforming for every possible scope; ADR-003 explicitly allows unavailable historical content when guarantees do not require its retention.

It is rejected for the selected first reference scope. A crash erases the only record of consumed resources, uncertain effects, pending evidence/publication/cleanup work and committed results needed for safe status inquiries. Simply refusing historical retrieval does not preserve an outstanding liability or establish whether an old mutation committed. Mandatory evidence may demand recoverable custody before effect; a volatile owner alone cannot supply it. Adding a durable external evidence/result/obligation facility would abandon the purely volatile alternative and still require consistency between owner facts and that facility. Configuration stability alone does not force durability, but the selected combined recovery and obligation scope does.

### B — Durable owner-local current records with atomic revision updates

Directly commit authoritative current records, original-operation outcome and the immutable interpretation/history/obligation facts required by the domain. Guard expected revisions and uniqueness at the same boundary. Recovery reads committed state and outstanding work; no replay-derived state is necessary. This is the simplest sufficient selected mechanism, provided multi-record invariants and crash durability are actually qualified.

Its costs are persistent storage from the first stateful slice, migrations, retention controls, result coverage, handling legitimate orphan records and explicit recovery gating. It does not solve distributed dispatch, anti-rollback trust or evidence custody merely by writing a transaction.

### C — Append-only owner facts with materialized state

An authoritative ordered owner fact stream can preserve history and derive a current view. It is credible for extensive historical reconstruction or domains whose fact model naturally defines all state. It must still condition append on expected stream/record revision, reject duplicate logical operations, durably retain required facts and establish projection position/compatibility before using derived current state.

This alternative is not selected initially. It adds authoritative event interpretation, projection catch-up, rebuild, duplicate handling, schema/event evolution and replay correctness to every relevant owner. Security checks and external effects must not execute merely because a fact is replayed. The need for Events or a few immutable facts does not justify this cost. It remains possible behind an owner boundary if later measured needs justify it and outward revision/result semantics remain intact.

### D — Durable records plus a universal append-only mutation journal

A journal for every owner mutation could aid diagnostics or repair, but it duplicates authoritative interpretation unless its purpose and consistency are explicit. A journal committed independently creates a new dual-write failure; one committed locally still adds representation and retention burden. Reject a universal journal as a requirement. Selected B already retains necessary domain facts and results atomically, without recording every intermediate internal step or inventing a second state authority. Storage-engine internals are not selected by this distinction.

### 6.1 Comparative criteria

These are architectural judgments, not measured scores.

| Criterion | A — Volatile | B — Durable records, selected | C — Facts and materialized state |
|---|---|---|---|
| Semantic fidelity | Adequate only for narrower session guarantees | Direct domain records with required facts | Strong if fact interpretation covers every invariant |
| Owner isolation | Possible with discipline; shared dicts are a risk | Explicit owner mutation scope | Explicit streams/projections still need owner scope |
| Revision correctness | Possible until process loss | Atomic conditional update and record identity | Conditional append plus valid projection position |
| Crash recovery | Loses authoritative session state | Recovers committed sets directly | Recovers facts, then verifies/catches up state |
| Lost acknowledgment | Reconciliable only while result survives | Same result and revision recoverable within coverage | Same result/fact recoverable with duplicate protection |
| Partial facts | Lost at crash without another durable authority | Required facts committed locally | Preserved if appended before they are acknowledged |
| Historical interpretation | Unavailable after loss | Exact required retained records | Rich history; interpreter evolution risk |
| Effect/liability preservation | Insufficient across restart | Durable knowledge and outstanding obligations | Possible, but replay must not repeat effects |
| Configuration recovery | Cannot promise retained R1 | Exact R1 and selection recover | Needs retained snapshot or exact fact reconstruction |
| Plugin lifecycle recovery | History lost | Current state plus required transition history | Rebuild from versioned lifecycle facts |
| Evidence obligations | Cannot alone meet durable prerequisites | Suitable substrate; custody still separate | Suitable substrate; stream alone is not custody |
| Solo-developer burden | Smallest code, hardest lost-state disposition | Moderate and bounded | Largest initial semantic/rebuild surface |
| Operational complexity | Minimal infrastructure, limited guarantees | One local persistence realization and recovery gate | Persistence plus projection and rebuild operation |
| Testability | Simple in-session tests; cannot prove selected restart scope | Finite concurrency/commit/crash boundaries | Adds replay, lag and interpreter evolution cases |
| Migration complexity | Little data to move, lost continuity cannot be repaired | Explicit records/history/coverage migration | Stream and old interpreter/projection migration |

| Future scaling | Requires replacing foundational storage boundary | Can move conditional mutation to another store/service | Can support append-heavy needs; not automatically distributed consistency |

D retains B's core guarantees only when journal writes share the owner commit; it adds C-like history volume/evolution costs without requiring full state derivation. No demonstrated first-slice need outweighs that cost.

## 7. Atomic mutation and commit semantics

### 7.1 Conceptual mutation boundary

A request identifies the owner/record scope, original expected revision or expected absence, operation identity and semantic equivalence, requested change/transition, verified Principal/TenantContext, pinned inputs and applicable cause/evidence references. These are behavioral requirements, not a new Python signature or serialization schema.

The owner must:

1. Establish authorized access and operation scope without leaking another tenant's existence.
2. Recognize a retained equivalent operation outcome, if present, under CTR-014–016. A duplicate of a committed request returns its currently permitted prior outcome; it is not re-evaluated as a fresh stale mutation.
3. For new intent, validate contract/version, required inputs, permitted transition and all applicable current authority/resource/evidence prerequisites. Preparatory validation does not reserve a revision or freeze a grant.
4. At the authoritative commit boundary, enforce operation-identity uniqueness/equivalence and every expected-revision/absence or local invariant guard. A preliminary read followed by unconditional write is forbidden.
5. Atomically commit new current state, fresh revision, necessary immutable historical facts, enough operation outcome/equivalence evidence for safe status/retransmission, and required owner-local obligations. If any required part cannot commit, none of this new owner set commits.
6. Acknowledge the exact committed outcome after durable completion. If completion cannot be established, return uncertainty/unavailability rather than a false negative or positive acknowledgment.

**Committed** means the complete owner-local set crossed its qualified durable atomic boundary and is authoritative, even if no caller received the response. It does not mean that another owner committed, an Event was published, a remote Tool acted, or mandatory evidence custody elsewhere was acknowledged.

Creation uses expected absence of the complete scoped identity and unique operation meaning. Conflicting creation cannot overwrite or impersonate an existing/disposed identity. Correcting an immutable fact produces a linked new fact; it does not update the old meaning in place.

### 7.2 Foreign authority and effect limits

A transaction can guard local state; it cannot make a previously read foreign grant, Approval or Resource claim current merely by storing that reference. ADR-005/007 must establish the required owner-current decisions and ordering at protected boundaries. Unproven current predicates block the protected mutation/handoff. This decision does not suggest that checking several owners sequentially closes a revocation race.

Do not execute external work inside a purportedly rollbackable state mutation and imply that database rollback reverses it. Persist the required handoff intent/obligation before the handoff as described in §12, then record observed completion separately. Cancellation, migration and cleanup may themselves have effects and require the same treatment.

### 7.3 Partial owner-local work

There is no partially committed **single atomic mutation** in the selected supported storage model. A larger owner operation may have several declared stages, each independently committed, with explicit incomplete postconditions. Earlier stage facts remain true if a later stage fails. If corruption prevents determining whether a complete commit survived, mark the affected scope unavailable/unknown; do not bless a torn set as valid partial completion. This distinction avoids both false all-or-nothing orchestration and weak local atomicity.

## 8. Revision, ordering and read semantics

| Identity/version | Valid meaning and comparison |
|---|---|
| Owner state revision | Version of one authoritative mutable record/head; equality and successor order apply only within that scoped record's uninterrupted identity/history |
| Immutable content/history revision | Exact fixed meaning; equality/reference lookup, not a mutable-head concurrency counter |
| Configuration revision | ADR-003's immutable owner-issued effective record; distinct from configuration selection-head revision |
| Plugin release/contract version | Published semantics and compatibility; not mutation or commit order |
| Operation identity | Which equivalent requested mutation is being reported/repeated; not which state version is current |
| Event/delivery sequence | Ordering under its producer/delivery contract, if any; no implied owner-state revision or global clock |

**Select per-record monotonic successor ordering, with exact scoped revision equality for conflict detection.** Monotonic means a committed successor never moves back to an earlier logical revision of that same record; it does not require consecutive integers, a wall clock, a particular encoding or a store-wide sequence. No revision is reused for changed state, including after value A changes to B and later back to A. Record identity/incarnation must prevent deletion/recreation from presenting an old concurrency token as current.

An owner-local compound mutation may advance several affected record revisions together. If several records share an invariant, use a guard covering that invariant or atomic checks over the full read/write/predicate set; unrelated records need no common order. There is no total order across an owner's unrelated records or across owners. An operation result identifies the exact revised records, not a fictional whole-runtime revision.

Two new operations expecting the same R5 cannot both replace that guarded record: one commits the successor, the other gets Conflict with no requested mutation. Conflict diagnostics disclose the current revision only under current access. No automatic reload/latest merge is provided. A deliberate new owner/caller operation may read current state and choose new intent under domain rules; a retransmission keeps the original expected revision.

### 8.1 Reads

Authoritative current reads must present a coherent committed owner state for the declared read scope, ordered with completed mutations in that scope: a read begun after a successful commit cannot return an earlier revision as current. It may return a later committed revision, or explicit unavailability. A requested exact retained revision must be returned with its pinned interpretation, or reported unavailable; never replaced by a later value. A result/status query must be able to establish the original committed outcome within declared retention coverage even if the head has since advanced.

Where one operation needs several local records as one invariant view, the read/check must use a coherent owner-local view and commit guards; independently fresh reads are not proof that the combined predicate held. A cross-owner read is a set of separately attributed revisions/freshness observations, not a globally simultaneous snapshot. A lagging replica/cache must either satisfy the required authoritative read behavior or declare itself a projection; it cannot silently serve stale current authority.

## 9. Acknowledgment and retained operation results

The following labels describe knowledge and acknowledgment stages; they do not add canonical lifecycle states or effect values.

| Observation | What may truthfully be concluded |
|---|---|
| Not attempted, with authoritative handoff knowledge | No requested target mutation attempted at this boundary; earlier parent effects may still exist |
| Rejected before mutation | Requested mutation did not commit; access/evidence costs and earlier effects are separate facts |
| Received/accepted for processing | Receipt only; no durable owner commit or external completion implied |
| Committed and acknowledged | Exact owner-local set durably committed under §4; subsequent owners/effects have separate outcomes |
| Committed, acknowledgment lost | Owner truth is committed; caller initially cannot know it; retained result must support reconciliation |
| Failed with authoritative proof of no state change | This attempted atomic mutation did not commit; does not erase previous stages or external effects |
| Multi-stage operation partly completed | Identify each committed stage, failed/not-attempted/unknown stage and outstanding postconditions |
| Timeout/unavailable commit status | Caller cannot infer commit or absence; preserve uncertainty and status-query path |

Canonical effect status remains exactly **none, partial, completed, unknown**, scoped to the operation/effect being described. A successful local state mutation can coexist with an unknown external action. Failed, cancelled and timed out are never shorthand for none. No new error family is introduced: use the relevant canonical category (for example Conflict, ValidationError, VersionMismatch, AuthorizationDenied, TenantViolation, DependencyFailure or DeadlineExceeded) alongside truthful result/effect/obligation information.

### 9.1 Minimum result retention and lost acknowledgment

Within the operation's declared coverage, the owner must durably retain enough to recognize the original scope/equivalence including expected revision, establish whether it committed, recover its exact outcome/revision references and effects/obligations, and answer `get_operation_status` or the already permitted equivalent family query. The successful mutation's result evidence is part of the same atomic set; it cannot be a best-effort log written after the state commit.

Concurrent repeats must be protected at that commit boundary as well as during an initial lookup. If two requests see no result and race, uniqueness/equivalence plus the atomic result write still permits only the valid original commit. Different meaning with the same identity yields Conflict. Current disclosure authority is checked before returning retained data; denying access after revocation neither erases the old commit nor permits its repetition.

ADR-008 selects concrete identity/equivalence handling, validity horizon, external-provider deduplication and reconciliation machinery. This ADR creates no duration or global exactly-once promise. Before implementation advertises a retry guarantee, its coverage and retention must be explicitly decided and realizable. Result retention must cover that declared guarantee and any longer applicable unresolved-obligation/evidence duty. Expiration, missing result data or unavailable owner status is not permission to retry as new intent. Authoritative absence must be established for the relevant interval; otherwise reconcile or hold for an authorized safe decision under CTR-016.

## 10. Immutable history, current heads, disposition and obligations

Immutable revision records plus mutable owner-local heads are selected where historical meaning matters: configuration, published definitions/bindings, recorded lifecycle/effect observations and material mutations. This does not require every internal field update to produce a full historical copy. Each owner retains the facts needed to satisfy its contracts, including the original governing versions and links for corrections.

| Record class | Preservation/disposition rule |
|---|---|
| Current authoritative state | Remains recoverable while its supported owner responsibility exists; status changes use guarded revisions |
| Historical interpretation | Retain exact required semantic content or supported interpretation representation and its version/references for the applicable guarantee |
| Required evidence | Evidence policy governs custody, access, integrity and retention; a local source history record is not automatically enough |
| Outstanding obligations/liabilities | Durable and discoverable while unresolved under their governed disposition; never silently dropped because a parent failed or restarted |
| Expired/disposed content | Governed deletion is explicit; report unavailable content/interpretation rather than redirecting its identity |
| Tombstones/minimal references | Retain permitted minimal identity/disposition information needed to prevent substitution, reuse and resurrection, under policy |

No infinite history or indefinite retention is selected. Retention conflicts go to the existing policy authority with bounded governed disposition, not automatic permanent retention. Where policy forbids retaining even a tombstone, identity issuance/non-reuse and lookup behavior must still prevent an old reference from resolving to new meaning; a storage key becoming free is not permission to reuse a canonical identity. Safe absence/coverage metadata must itself respect tenant disclosure and retention rules.

Each owner retains required obligation records under CONTRACTS §28: identity, owner, responsible requester/Principal, tenant, parent operation/effect, required action/target revision, due/retention bound, required guarantee, canonical obligation state, last evidence/error, next safe action and reconciliation authority. The pending/satisfied/failed/requires-intervention descriptors remain obligation states, not Execution or Plugin states. Updating disposition uses expected revision and preserves linked facts; cleanup cannot delete the failure it is addressing.

The producer's own mutation must atomically establish any required publication/evidence/settlement/cleanup obligation with the fact that creates the duty. A responsible coordinator may reference that obligation and keep its own orchestration facts; it cannot take ownership of the producer's state. Discoverability cannot depend solely on a queue or a projection successfully receiving an Event. Enumerating owner-local unresolved records is required; scheduling/retry tooling is not selected.

## 11. Crash-point analysis of alternatives

Assume no prior external work unless the cell states otherwise. For every alternative, earlier effects remain real. A validated request is not a committed mutation. C is evaluated as a correctly designed durable conditional append model, not an unfair weak implementation.

| Crash boundary | A — Bounded volatile | B — Selected durable records | C — Durable facts/current projection |
|---|---|---|---|
| Before validation | No new mutation; all earlier session state may be lost | No new set; previous committed sets recover | No new fact; previous durable facts recover |
| After validation, before commit | Validation does not survive unless recorded; no new mutation | No new committed set; revalidate any deliberate new processing | No accepted append; preliminary validation is not authority |
| During mutation | In-process partial staging must not be exposed; crash loses session | Storage recovery yields whole old or whole new set according to durable commit, never torn accepted state | Conditional append is absent or committed; materialized state may lag and must be rebuilt/verified |
| After durable commit, before acknowledgment | No durable commit exists in A; in-memory success may vanish | New state, revision, result and obligations recover; caller queries same operation | Committed fact/result recover; query/catch-up must establish exact outcome |
| After acknowledgment | A's bounded session acknowledgment makes no restart guarantee | Acknowledged set survives declared failure model | Acknowledged durable facts survive; current view must reach proven position |
| During restart/recovery | Cannot recreate lost history; prior identity must not be silently initialized as new | Partial recovery never opens unsafe work; repeat inspection, verify versions and obligations | Incomplete rebuild stays unavailable; replay must neither reinterpret history nor re-execute effects |

If the store is inaccessible, the caller may temporarily not know which atomic outcome occurred. In the qualified intact-storage failure model, recovery must resolve the owner set as committed or not committed; uncertainty is not a third valid partially written transaction. Independent external effects may remain unknown even after that local determination. If storage is lost/corrupt beyond qualification, the owner cannot manufacture commit certainty.

## 12. Cross-owner partial completion and external handoff gaps

Owner A, Owner B and Owner C commit independently. Each owner updates only its own state, even if one physical transaction engine could touch all their records. A parent operation exposes sub-operation identities, exact acknowledgments/results, effects, incomplete postconditions and obligations. Parent success depends on its declared postconditions, not the count of received responses.

For a handoff with required completion/reconciliation, the responsible owner/coordinator must first durably record enough intended operation identity, target/input references and obligation to discover unfinished work after a crash. The recipient records its own outcome. The sender then records the observation in a separate local mutation. This requirement closes the gap in which a process sends an effectful request and crashes before there is any durable record that reconciliation is needed. It does not select an outbox, queue, delivery system or deduplication algorithm.

If the process crashes between recording intent and sending, recovery may not know whether transmission occurred. A pending intent is not proof of dispatch or proof of no dispatch. Inspect recipient status or apply the later declared equivalent safe handoff guarantee; do not blindly send again. If a response arrives but the sender cannot store it, the recipient's committed facts and sender's prior obligation still allow reconciliation. Recording evidence of a real effect cannot be postponed until after another external effect with no recoverable trace.

| Partial situation | Preserved truth and next safe work |
|---|---|
| Configuration R2 committed, Plugin binding fails | R2 exists and may be unused; repair/request binding only if still authorized and compatible, or dispose under policy |
| Plugin active committed, Catalog publication fails | Plugin activation happened; Catalog offer is stale/missing; retain publication obligation, reconcile current eligibility and publish through Catalog's own mutation |
| External action may have completed, response lost | Preserve unknown effect and resource liability; inspect/reconcile or authorized safe disposition; no database rollback claim |
| Resource reservation committed, downstream work fails | Claim remains accounted for; release/settlement occurs only through Resource owner rules under ADR-007 |
| Protected mutation committed, post-effect evidence write fails | Effect and owner fact remain real; durable custody obligation persists; repair evidence without repeating the protected action |
| Required pre-effect evidence unavailable | Do not perform the protected effect; an obligation to write evidence later cannot satisfy a mandatory prior guarantee |
| Execution exists, Adapter unavailable | Keep attempt/effect history; block dependent continuation, expose outstanding reconciliation/intervention |

Orphaned records can be legitimate partial states, not garbage by default. Compensation is new authorized work with its own costs/failures. Cancellation can stop future work but cannot erase committed claims, evidence or effects. Recovery discovers truth and obligations; it is neither automatic retry nor compensation.

### 12.1 Co-located transaction optimization

No cross-owner atomic optimization is required or selected for the first realization. A later realization may use a physically shared transaction only as a separately reviewed optimization when each owner still validates and controls its contribution, necessary invariants and disclosure boundaries are proven, and outward contracts remain valid for separately committed implementations. It cannot create hidden semantic dependencies on all-or-nothing cross-owner commit, bypass owner Ports, turn partial results into impossible states, or imply external effects are included. No distributed 2PC foundation is introduced.

## 13. Restart, startup gating and recovery order

Each owner recovers its own state. Orchestration then reconciles relationships; no owner edits another owner's recovered state to make them agree.

1. Establish the expected runtime/owner persistence identity and authorized recovery context. Distinguish a genuinely new empty runtime from missing state for an existing identity. A missing file/store is not first-run proof.
2. Recover the physical transaction boundary; verify authoritative record identity, tenant scope, integrity/provenance required by the threat model, supported representation version and commit completeness. Detect evidence of restore, rollback or incompatible incarnation.
3. Load coherent current heads and required exact historical records. Verify runtime/contract/Plugin release/configuration interpretation and owner state representation compatibility. Retained content may be readable for history even when not resumable.
4. Surface retained operations with incomplete or unknown outcome and all unresolved obligations/liabilities. Do not mark unknown effects none or expired claims automatically free.
5. Reconcile cross-owner references and dependencies with current authorized owners. A reference proves neither availability nor present authority. Verify evidence prerequisites and current policy, grants, Secret validity, resource/deadline and Plugin conditions required for the intended work.
6. Rebuild only declared non-authoritative projections from authoritative records/facts, retaining version/freshness and publication gaps. Projection readiness does not establish authority readiness.
7. Permit only work whose required state and controls are sufficiently recovered and validated. Further repair is explicit governed work. Startup and repair ordering must terminate at already trusted finite roots under ADR-006/009; this ADR does not authorize a store or Plugin to admit itself.

Recovery interruption is safe: repeat verification/inspection against committed facts. A recovery step that mutates domain state must itself use an owner operation with expected revision and retained outcome. Automatic state replay that executes external work is outside this mechanism. No new canonical recovering, blocked or intervention Execution state is added.

Plugin history may say active after process death; that remains a historical owner fact, not evidence of a running initialized instance. ADR-006 must use existing lifecycle operations and valid recovery/reinitialization treatment with fresh checks. A stopped Plugin requires a new validated activation record before the permitted initialization path, even if it uses the same configuration R1. Existing Execution attempts retain their state and effects until an authorized permitted transition; a begun Execution never becomes rejected because restart admission fails.

Partial availability is by capability/owner dependency closure. An unrelated unavailable owner need not stop a direct Capability that demonstrably does not depend on it. Conversely, a shared physical store outage may actually affect every stateful dependency; logical isolation does not imply physical fault isolation. No operation is admitted by pretending a required failed owner is healthy.

### 13.1 Missing history and unsupported recovery

Distinguish: the record existed; its reference is known; its exact content is accessible; its interpretation is supported; it is currently usable. These are separate propositions. If R1 or its interpretation is unavailable, retain safe references/disposition evidence as permitted and block dependent resumption. Do not recreate R1 from current environment, assign new revisions to conceal loss, substitute R2, or treat unreadable bytes as a valid empty owner. A separate newly initialized runtime/composition cannot claim the old history or resume old work.

## 14. Projections, Events, logs and evidence

Catalog/status/search views may lag their source. Derived records must identify source owner/revision, scope and freshness/coverage; they cannot mutate or authorize on behalf of that source. A source current-read or protected-boundary check must establish the necessary current truth before action. Historical snapshots embedded where a contract requires them are labeled historical evidence, never a second mutable source of authority.

Catalog is still the authority for registrations/offers it owns. Only its derived Plugin eligibility observations or other expressly derived views are projections. Rebuilding them must not invent previously unregistered offers, re-enable stopped/retired activations or erase authoritative Catalog disposition.

A committed material change and its publication obligation are recorded together by the source owner. Event publication/delivery and consumer effect are separate facts. Repeated publication must preserve fact identity and go through the eventual declared duplicate/consumer rules; a materialized view's lag does not roll back the producer. A failed publication remains an explicit obligation until the required guarantee is met or failure/disposition recorded. Events do not require event sourcing.

Logs, metrics and traces are not authoritative recovery state by default. Reconstruction from them is not a fallback for missing owner records unless a separately qualified mechanism explicitly satisfies the exact state/evidence guarantees. Owner-local history supports evidence production, but mandatory evidence custody still needs its own owner, acknowledgment class, retention and recovery guarantees under ADR-009. Physical co-location alone supplies none of these semantic attestations.

## 15. Persistence capabilities and package boundary

The later storage realization must demonstrate these minimum behaviors without a mandated SQL isolation-level name or product:

| Capability | Required behavior |
|---|---|
| Conditional owner mutation | Atomic expected-revision and expected-absence checks; no lost update, stale success or automatic last-writer-wins |
| Compound atomicity | All owner records/facts/results/obligations required by the mutation commit together or none do |
| Local invariant protection | Concurrent predicate/read-write changes cannot bypass shared owner constraints or uniqueness |
| Durable commit and crash recovery | Acknowledgment matches §4; recovery distinguishes committed/uncommitted complete sets |
| Scoped identity/equivalence protection | Prevent conflicting record creation and repeated operation mutation within declared coverage, including concurrent duplicates |
| Exact reference lookup | Resolve retained record/revision and interpretation without following latest; disclose only under current scope/access |
| Authoritative reads | Coherent committed read scope, read-after-commit behavior and exact outcome inquiry under §8 |
| Immutable fact insertion | Preserve required historic meaning; corrections linked, not overwritten; policy-governed disposition remains possible |
| Outstanding-work discovery | Authorized enumeration/status of unresolved obligations and incomplete operations after restart without volatile-only indexes |
| Scope and integrity validation | Owner/tenant binding, provenance/integrity evidence required by the admitted threat model and corruption handling |
| Versioned representation and migration | Explicit compatible readers/writers, guarded migration progress and recoverable interruption |
| Retention and coverage | Governed disposal/tombstones, query coverage and safe unavailability; no expiration-based replay permission |

These may be implemented using different storage technologies. Public contracts retain domain semantics; an owner may define its own internal state adapter needs. This ADR defines no universal persistence API and no Python signatures, repositories, schema, transaction code or exact directory additions.

Existing owner implementations remain under ADR-002's `legoai.reference.application`, `.catalog`, `.resolution`, `.execution`, `.tools`, `.identity`, `.tenant`, `.authorization`, `.resources`, `.plugins`, `.evidence` and other already allocated owner locations. Their logical public contracts stay in their assigned packages. Kernel retains identity/reference/version anchors; it owns no database, mutable global context or state manager. The private runtime composition root wires technical dependencies without becoming a domain owner. Shared technical storage primitives, if useful later, must not introduce peer-implementation imports or broaden ADR-002's dependency matrix.

One local backing realization minimizes separately deployed storage components and recovery tooling initially. Requiring one physical store per logical owner would multiply connection/configuration, backup, maintenance and failure surfaces without by itself proving tenant or owner security. Shared infrastructure has a larger common failure and privilege domain; hostile co-tenancy or stronger isolation requirements may require physical/process separation later. No claim that namespaces alone isolate malicious in-process Plugins is made.

Python object identity, mutable dictionary sharing, GIL behavior, one event loop, async locks and thread/process locks do not establish durable atomicity or cross-process authority. Locks can coordinate local implementation work but the qualified persistence boundary must independently enforce correctness. Serialization remains replaceable: no pickle, JSON, MessagePack, Protobuf or ORM representation is selected. Deserialization must not execute untrusted code; recovery data crosses a trust boundary, and a convenient executable Python object format cannot be assumed safe.

## 16. Tenant and security implications

Every authoritative operational record, result lookup, obligation, index/query and diagnostic retains explicit applicable tenant and owner scope. Single-tenant deployment does not infer tenant from process, connection or filesystem location. No default/wildcard tenant is introduced. Legitimate cross-tenant references require current explicit grants and both policies; they do not relabel foreign records or let one owner copy mutable foreign authority into its own tables.

| Threat | Required boundary and remaining proof |
|---|---|
| Unauthorized owner writes or cross-tenant query/index leakage | Domain operation authorization, complete scope checks on reads/writes/uniqueness/status, protected existence metadata and diagnostics; actual enforcement proof in ADR-005/realization |
| Stale authorization cache | Current required owner decisions at protected boundaries; persisted allow decision is historical evidence, not enduring entitlement |
| State substitution or identity confusion | Verify owner, tenant, record identity, exact revision, contract/representation and applicable provenance; path/row existence alone is insufficient |
| Tampering/corrupt state | Validate integrity/authenticity appropriate to the supported threat model; fail affected scope closed on unverifiable state, preserve safe evidence, never auto-reset |
| Rollback/resurrection | Restore gate under §17; no automatic resurrection of revoked grants, consumed Approvals, resource balances, retired activations or revoked Secrets |
| Unsafe deserialization | Data-only validated interpretation across trust boundaries; no executable recovery payload assumption |
| Sensitive history/results | Least disclosure, governed retention/disposition, protected backups and current access on duplicate/status responses; no raw Secret or private reasoning capture |
| Forged repair/migration | Current entitled actor, expected revisions, exact target/evidence, immutable linked progress; migration is not a privileged bypass |
| Malicious shared infrastructure | Owner-local transaction is not an isolation/security product; unsupported threat scope requires stronger realization or refuses use |

Secret recovery persists safe references and permitted metadata under ADR-003, never raw Secret material as ordinary owner-state convenience. A historical logical reference may resolve current authorized material only under its declared rotation rule; a pinned material reference cannot silently follow latest. Restoring records does not restore Secret validity. ADR-010 retains protected material/resolution choices. Encryption, database IAM, cryptographic integrity/freshness mechanisms and backup products are not selected here.

## 17. Backup restore, schema evolution and reversal

### 17.1 Restore is not ordinary restart

An older internally consistent backup can be missing committed revocations, consumed Approvals, external effects and liabilities. Even a backup containing all owners at one timestamp does not rewind the external world. Different owner restore points can additionally leave dangling or mismatched config, activation, effect and evidence references.

Restored affected scopes therefore remain gated until their identities/coverage are established, relationships reconciled and current authority/consumption/lifecycle/Secret state can be verified through trustworthy evidence adequate to the deployment threat model. A current check against the same unverified rolled-back image is not independent freshness proof. If no trustworthy basis can recover missing consumption or validity, preserve uncertainty, deny dependent use and require governed intervention; do not release capacity, reissue entitlement or repeat the original work. No anti-rollback oracle, external witness or global backup algorithm is assumed selected.

Recovery must surface partial owner coverage and references to unavailable facts. No owner rewrites a peer's recovered state to align timestamps. Additional reconciliation observations, corrections and compensation follow existing contracts and remain attributable. Backup operation and restoration must respect confidentiality, retention and non-reuse; an old backup cannot undo an authorized disposal by silently resurrecting accessible data.

### 17.2 State representation evolution

Persisted representation versions are explicit implementation metadata distinct from canonical contract versions. Compatibility checks cover runtime, state representation, governing contract, Plugin release and configuration interpretation as relevant. Old readable data need not be mutable/resumable: preserve a supported read-only historical interpretation when possible; otherwise report interpretation unavailable.

Migration is explicit, owner-controlled and authorized. It preserves prior meaning, exact externally referenced identities/revisions, tenant scope, lifecycle/effect history, results/coverage and obligations. Changes to semantic content create linked new versions; representation translation alone does not invent a new historical configuration meaning. No automatic fallback decoder or silent field/default reinterpretation is allowed.

Migration units may be per-record or a compound owner-local transaction. Each unit atomically records transformed state and durable progress under its original guards. Completed units remain true when later units fail. Mixed representation support must be declared; if unavailable, keep that owner's dependent work gated until required units complete. Whole-runtime migration is not globally atomic. Compatible read-only history may remain available while mutation is blocked.

### 17.3 Type-1 migration/reversal path

1. Inventory each owner's current records, required history, result coverage, obligations, interpretation versions and cross-owner references; authorize a migration plan with a safe cutover boundary.
2. Quiesce affected mutations initially, or separately prove a later coordinated transfer mechanism. Prevent two old/new writers from concurrently claiming authority; a process convention alone is insufficient.
3. Transfer and verify complete owner sets and reference meaning. Preserve externally meaningful identifiers/revisions; compare contents, effects, unresolved work and coverage, not merely row counts.
4. Reconcile foreign references and migration progress before guarded use. Activate the new realization only with proven exclusive authority/current security and supported interpretation.
5. Retain permitted old history and transfer evidence according to policy. If the destination has accepted new work, reverting is another reconciled migration; loading the old backup would lose new facts and is unsafe.

Another local datastore changes adapters and data transfer; an external database adds connectivity/latency/failure qualification; multiple processes require storage-enforced guards and exclusive authority/cutover; a remote owner service moves the same owner contract and adds explicit network acknowledgment uncertainty. None requires rewriting canonical owner, revision, effect or tenant semantics. Each needs fresh realization evidence.

If internal concurrency token representation must change, use a verified translation tied to exact owner/record/history, reject stale outstanding expectations or resolve retained equivalent requests, and prevent token collisions. Externally referenced immutable revisions remain stable or resolve through an explicit permanent-meaning mapping governed by retention; they are never casually renumbered. A migrated head must not make an old R5 expectation valid against different state.

This is Type 1 because production identities, retained operation results, external effects, cross-owner references and accumulated history are expensive to move or reconstruct. Quiescence, reconciliation, compatibility readers and proof are real costs. A neutral adapter interface alone does not make data reversal cheap, and lost historical facts cannot be fabricated after migration.

## 18. Mandatory failure timelines

### Timeline 1 — Concurrent stale writers

1. The authoritative record is R5. Independent operations A and B both validate against expected R5.
2. A conditionally commits state R6, required facts and result in one owner-local transaction.
3. B attempts its commit with the original expected R5. The authoritative guard fails.
4. B receives Conflict and does not overwrite R6. If authorized it may inspect R6 and deliberately submit different intent; its original retransmission cannot silently change expectation.

### Timeline 2 — Commit succeeds, acknowledgment lost

1. Caller submits O1 with original expected R7 and exact scope/input meaning.
2. Owner atomically commits R8, O1's outcome/equivalence evidence and required obligations.
3. Response is lost. Caller observes a timeout; it cannot infer none.
4. Caller queries or retransmits the same O1. Owner checks current disclosure and retained equivalence, then returns permitted R8 outcome, even though the current head may now be R9.
5. O1 does not execute again and is not incorrectly rejected solely because R7 is no longer current. Outside coverage or while state is unavailable, reconcile/hold; do not manufacture O2 as a safe substitute. ADR-008 decides machinery and horizon.

### Timeline 3 — Cross-owner partial completion

1. The responsible coordinator records operation targets and required handoff obligations.
2. A commits its own fact/result. B then definitively fails before its requested commit. C is not attempted.
3. Parent records A committed, B not committed and C not attempted, exact results and incomplete postconditions. If B's response is merely lost, its outcome is unknown instead of not committed.
4. Recovery asks each owner for its own truth and performs authorized repair. It does not erase A, let A mutate B, or report the entire sequence had no effect.

### Timeline 4 — Runtime crash and restart

1. Owner commit and acknowledgment complete; its state, result and obligations share the durable boundary.
2. Runtime crashes. The original qualified persistence domain remains intact.
3. Restart verifies commit completeness, identity/scope/versions, loads the current head, exact retained config/history and outstanding operations/obligations.
4. Current required authority, resources, evidence and lifecycle dependencies are checked before affected work. Missing R1 blocks R1-dependent resumption; current environment R2 is not substituted.
5. Non-authoritative views can rebuild. Recovered records alone do not initialize a Plugin or resume effectful code.

### Timeline 5 — Crash during mutation

1. Owner validates and begins the local atomic set for O1.
2. Crash **before durable commit**: qualified storage recovery establishes no O1 set committed; prior state remains. The requested local mutation has not happened. Any earlier external/parent effect is assessed separately.
3. Alternatively, crash **after durable commit**: the complete O1 state/revision/result/obligations survive, even before acknowledgment.
4. A crash at the commit boundary requires storage recovery to determine which of these occurred. While that determination is inaccessible, caller knowledge is unknown; no partial local commit is accepted and no automatic external retry follows.

### Timeline 6 — Projection lag

1. Plugin Lifecycle commits a permitted transition with the required publication obligation.
2. Catalog eligibility publication fails; its view remains stale or missing.
3. Plugin's fact is not rolled back, and the stale view cannot authorize contrary to current Plugin state.
4. Authorized repair verifies current source state, updates Catalog through its own operation and records obligation disposition. Repair of an active publication after a later stop must reflect the stop; it cannot publish obsolete eligibility blindly.

### Timeline 7 — Interrupted migration

1. Owner mutation traffic is quiesced at a known revision; source/target representation and migration operation are recorded.
2. Unit U1 transforms its records and progress atomically. U2 has not committed when the process crashes.
3. Restart sees U1 complete and U2 incomplete, with exact old/new interpretation boundaries.
4. It validates U1, resumes/reconciles U2 under its original guards and retains failed-unit evidence. Unsupported mixed-state use remains gated.
5. Other owners are independently inspected; no whole-runtime completion is claimed. Returning to the old store after new target commits requires a separate reconciled transfer, not rollback of history.

## 19. Additional structural walkthroughs

| Scenario | Required behavior |
|---|---|
| Configuration selection race | R1 exists and head H1 selects it. Authorized writers issue immutable R2/R3, then both expect H1. One changes the head; the other receives Conflict. Both issued revisions may remain as valid unused records subject to policy. Neither edits R1 |
| Configuration change versus activation binding | Binding names exact R1 and expected binding revision. A separate selection moving to R2 does not reinterpret that request. If the operation additionally requires a particular current selection, establish that explicit precondition through the owning contract; no cross-owner snapshot is invented |
| Plugin stop versus degrade | Activation revision L7 is active. Stop and degrade each expect L7. Only one permitted transition commits. The loser cannot overwrite stopping/degraded state; any later request must use the current permitted transition and new intent |
| Writer versus retirement | A stale update cannot clear a committed retirement/stop by retaining old expected revision; current lifecycle and authority checks apply even when payload values look compatible |
| Completion versus cancellation | Execution is running at E4. Both operations expect E4; only one applicable transition commits. The loser re-inspects. A committed cancellation request does not prove no completed Tool effect, and a later completion observation is retained through permitted reconciliation/state treatment. No new Execution states or automatic rejected status |
| Competing Resource claims | Both depend on one guarded allocation revision. The full local invariant guard allows only valid committed claims; loser cannot overdraw via a distinct claim row. Consumption/unknown liability persists after downstream failure; ADR-007 decides arbitration/settlement |
| Post-effect evidence failure | Owner effect/fact and custody obligation survive. Query/reconcile evidence acknowledgment by its identity; write/recover evidence without repeating original action |
| Secret reference on restart | Recover safe reference/purpose/consumer metadata, then obtain current authorized use through Secret owner. Never store/reload raw material in ordinary recovery records or revive a revoked reference |

### 19.1 Deterministic direct Capability independence

A verified Principal and explicit TenantContext invoke an admitted deterministic Capability using exact config/activation references. Application Composition, Catalog/Resolution, Plugin Lifecycle, Execution and the applicable Governance/Resources/Evidence and invoking owner boundaries retain their own state. Owner-local commits can record admission, invocation knowledge and outcome without a Team, Goal, Agent, Model, Workflow, RAG or persistent Memory. Technical composition wires the necessary contracts; persistence is general runtime infrastructure, not an AI subsystem.

If the Capability has no external side effect, its result still has scoped authority/evidence/resource semantics. If it has an external effect, the same attempt/handoff/uncertainty rules apply and ADR-007/008 prerequisites must be met. This is a structural independence argument, not a runtime test or permission to implement before the remaining ADR gates.

D adds universal journal maintenance, retention volume and diagnostic interpretation to B without removing these burdens. These are selected architecture counts, not measured setup time or cost. Actual development hours, throughput, footprint, recovery duration and contention thresholds need later experiments.

### Positive consequences

- Logical state authority remains explicit and aligned with ADR-002.
- Stale writers cannot silently overwrite current state; the same original operation can be recovered after acknowledgment loss.
- Configuration, lifecycle and effect history survive the declared interruption scope with honest unavailability outside it.
- Resources, retry/reconciliation and mandatory evidence gain a shared behavioral foundation without acquiring a global transaction dependency.
- One local realization limits initial operations, and owner contracts permit later technology replacement.

### Negative consequences and accepted risks

- Persistent state is required early; record/result/history/obligation volume and migration operations cost implementation and maintenance effort.
- Recovery gating may reduce availability while a necessary owner, reference, current security decision or interpretation is unavailable.
- Cross-owner partial records and orphaned revisions are expected and need governed disposition; transactions do not remove that work.
- Shared physical storage creates a common failure/privilege domain, despite separate logical ownership.
- Qualification may reveal that a proposed storage stack cannot meet abrupt-termination or invariant requirements; it must be replaced or corrected before claiming support.
- No disaster recovery, malicious-store freshness guarantee, transparent execution resumption or full cross-owner exactly-once effect guarantee is established.
- Retention/authority conflicts and external effect uncertainty may require authorized intervention. Storage cannot resolve them by inventing history.

### Mitigations

Keep the initial consistency unit owner-local and explicit; qualify conditional multi-record mutation and durable acknowledgment; retain only history required by interpretation/policy/obligations; expose authorized status and obligation inspection; gate unavailable/rolled-back state; use versioned migration with verified exclusive cutover; separate current checks from historical records; qualify new topology/threat/failure scope before enabling it. Remaining dispatch, deduplication, evidence and trust mechanisms stay blocked behind their respective ADR decisions.
