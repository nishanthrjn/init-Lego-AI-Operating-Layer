## 1. Context, governing review and closed decisions

The thirteen governing documents were reviewed in authority order. ADR-001 through ADR-004 are recorded as Accepted. Their semantics remain closed: conventional GIL-enabled CPython 3.14; ADR-002's one initial distribution and strict logical package boundaries; ADR-003's immutable effective configuration and exact activation binding; ADR-004's durable owner-local conditional commits, retained history/results/obligations and no global transaction assumption.

ADR-005's canonical dependency remains ADR-003. ADR-004 is a relevant accepted substrate, not a silently added dependency edge. The earlier ADR-INDEX status-summary discrepancy has been corrected in the current accepted source. No substantive upstream contradiction was identified; all governing files remain unchanged by this task.

The reference runtime needs trustworthy identity and authority for an embedded direct Capability as much as for an Agent calling a Tool. An HTTP gateway, Python object constructor, localhost connection or successful Plugin admission cannot supply this trust by implication. At the same time, a solo developer should not need enterprise IAM infrastructure for the initial explicitly single-tenant local slice.

The grouped `legoai.governance` package does not create a single semantic owner. Identity/Principal, Tenant Governance, Authorization, Policy Decision, Boundary Enforcement, Approval and Secret responsibilities remain separate. Resources, Work Coordination, Plugin Lifecycle and Evidence retain their own responsibilities. Kernel holds shared anchors, not an IAM engine or mutable security database.

## 2. Decision question and scope

How will the first runtime verify identity evidence, bind a canonical Principal and TenantContext, establish acting authority, evaluate Grant/Policy requirements, propagate trusted operation context, and enforce current authority without tying applications to a security vendor or protocol?

Select a concrete local-first behavioral mechanism, including trust provenance, delegation bounds, enforcement placement, cache/currentness rules and failure behavior. Do not select credentials, token formats, authentication protocols, Policy DSLs, storage products, IAM providers, cryptographic libraries or API signatures. Security-context terminology in this ADR describes an integration value using accepted contracts, not a new canonical entity, lifecycle or public schema.

The initial ordinary path is one explicitly provisioned tenant, a separately established administrative Principal, a direct human/service request and deterministic Governance realizations. Agent, Model, Team, Workflow, RAG and Memory are optional. Expanded multi-tenant operation, arbitrary delegation chains, remote federation and hostile in-process Plugin isolation require additional realization qualification; their canonical constraints are preserved here.

## 3. Trust distinctions and accountable ownership

| Concept | Meaning and boundary |
|---|---|
| Claimed identity/evidence | Untrusted input to verification; text, credential transport and claimed issuer do not establish authority |
| Verified Identity | Evidence accepted for a subject/issuer/scope under a named verifier, assurance, validity and revocation assumptions; not a Grant |
| Authentication | Establishes that the requester may act as that subject in the present context under the accepted verification method |
| Principal | Canonical security subject recognized by Identity/Principal Governance, bound to verified Identity, scope, kind/status and restrictions; an action selects exactly one acting Principal |
| Requester/originating Principal | Source of the requested work and its accountable authority; retained when a deputy acts |
| Actor | Human, Service, Agent or other accepted performer; its valid Principal association is explicit, not inferred from its name/type |
| Application | Composition/intent identity; does not automatically authenticate or grant an Actor authority |
| Role/RoleAssignment | Organizational/Team responsibility and participation; may be explicit eligibility input, never independent Permission |
| Permission/Grant | Authorization meaning and attributable bounded issuance under an entitled issuer; no canonical string syntax selected |
| Policy | Applicable governing rules, restrictions, obligations and authorized exception/combination basis; distinct from Grant eligibility |
| Approval | Separate scoped decision/use entitlement by an eligible approver; cannot replace Permission, Policy or resource admission |
| Resource admission | Independent authoritative reservation/accounting/limits; an allow decision does not allocate resources |
| Security context | Immutable, attributable operation interpretation and references; not an eternal authorization token |

For example, Principal `user-123` is a security subject while Team Role `Architect` describes responsibility. An explicit Grant/Policy may use a validated RoleAssignment as an eligibility condition; the title alone grants nothing. Similarly, Agent A has an Actor identity and must use an explicitly established Principal association/acting authority. **Agents receive no standalone Principal automatically.** A separately administered service/Agent-associated Principal is possible only through ordinary establishment and bounded grant rules.

One Human or Service may have multiple scoped Principal associations; one Principal may have several explicitly mapped credentials. Each action chooses exactly one valid acting Principal and records origin/deputy associations separately. A list of provenance Principals is not multiple simultaneous acting identities. Ownership, creator status, membership, access to a management API, deployment identity and technical credential reach confer no implied administrator power.

## 4. Threat model, assumptions and trust boundaries

Untrusted inputs include caller strings, payload tenant fields, raw assertions, Plugin claims, model output, retrieved content and Agent messages. Identity/authorization/Policy decisions must be made by admitted deterministic Governance realizations under independently established authority. A model-assisted Guardrail can supply evidence within its declared coverage; it cannot be the sole authority for identity, Grant validity, tenant scope or required claims.

For the initial shared-process realization, runtime enforcement and admitted executable Governance/Adapter code must be sufficiently trusted under the declared deployment scope. Logical package boundaries and private constructors do not sandbox malicious arbitrary Python code in the same process. Ordinary consumers cannot gain authority by constructing context fields through the supported interfaces; hostile memory access or monkey-patching the verifier is outside the initial isolation claim and requires ADR-012 or refusal to host that code. Agent/model decisions remain untrusted even when their runtime implementation is trusted.

| Boundary | Input/trust change | Required enforcement |
|---|---|---|
| User/Application → ingress | Raw evidence and requested scope arrive as claims | Protected handling, trusted initiator attribution, approved verifier; no caller-selected Principal |
| Ingress → Identity/Principal | Verification evidence becomes an attributable binding | Accepted issuer/verifier, exact mapping and permitted kind/scope/status |
| Principal binding → Tenant Governance | Requested tenant becomes verified operation scope | Explicit relationship/crossing basis and tenant decision; membership alone is insufficient |
| Runtime → Governance decisions | Exact action/target/acting chain enters evaluation | Complete applicable Grant/Policy/constraint inputs; no caller policy subset |
| Runtime → Agent/Actor | Actor receives minimum necessary work/security references | No permission to mutate or mint trusted context; child derivation governed |
| Domain owner / Tool boundary | Proposed work reaches disclosure, commit or handoff | Action-specific current authority and all applicable controls at this boundary |
| Adapter → external system | Technical credentials can release real effects | Bind exact permitted target/purpose/input; credential breadth cannot widen requester scope |
| State/evidence → caller/diagnostics | Historical/current security information is disclosed | Current access, least disclosure, safe errors; retained result is not public by possession |

Compromised roots/verifiers, stolen valid credentials, forged contexts, revoked authority, outages, stale caches, malicious deputies and Policy conflict are explicitly considered. This ADR states controls and required proof; it does not claim credential theft or a compromised trusted host is solved by context propagation.

## 5. Alternatives considered

### A — Local identity and authorization only

Locally provisioned Principals, a local verifier and local Grant/Policy owners can satisfy a small supported scope and offer simple offline development. Its credential lifecycle, trust-root protection, status/revocation, administration and recovery still require real security. A is credible, not a security-free strawman.

Reject **local-only as the architectural ceiling**: encoding local identity/evaluator assumptions into consumers would make later enterprise mapping and currentness guarantees harder to replace. The local realization itself is selected as C's first implementation. If A already has the same provider-neutral verification/decision/owner boundaries as C, it is that initial realization rather than a meaningfully different architecture.

### B — Mandatory external identity and authorization dependency

External identity and policy systems can centralize lifecycle and support established enterprise controls. They still require independent issuer trust, canonical Principal mapping, tenant enforcement, exact decisions and safe dependency failures. Using them does not transfer accountability to a provider response.

Reject an external-only requirement initially. The direct local slice does not require federation; mandatory remote systems add availability, configuration, credential, bootstrap, integration and semantic-adapter burden. External-only is viable for a future deployment with an actual corporate requirement, through the selected boundaries, not a canonical prerequisite.

### C — Provider-neutral verification and canonical Governance boundary

Use a replaceable identity-evidence verifier, explicit local canonical Principal association, Tenant Governance binding, bounded acting authority and Governance-owned Grant/Policy decisions, carried in an immutable operation context and enforced by protected owners. Supply deterministic local realizations initially. External verifiers, Policy and other Governance backends can later replace those realizations without changing canonical identities or Permission semantics.

**Select C.** It adds a small number of explicit handoffs needed by the accepted contracts anyway. It does not require a networked IAM service, universal security manager, policy language, token-centric runtime or federation implementation. It keeps local setup bounded while preventing local evidence representation from becoming canonical authority.

### 5.1 Comparative analysis

| Criterion | A — Local-only | B — External-only | C — Selected local-first boundaries |
|---|---|---|---|
| Canonical semantic fidelity | Good if distinctions stay explicit | Requires careful provider translation | Explicit shared semantics, provider translation confined |
| Independent trust establishment | Local protected root required | External roots plus runtime binding root required | Bounded independent local root; future roots governed |
| Principal/tenant attribution | Straightforward locally | External subjects/tenants need mapping | Stable canonical references across providers |
| Least authority/deputy protection | Must implement locally | Provider identity alone does not solve it | Owner enforcement and exact acting-chain bounds |
| Revocation/currentness | Local current owner checks | Network/freshness/partition guarantees matter | Same required behavior for both; no fail-open substitution |
| Policy conflict | Must preserve Q-05 | Provider precedence cannot override Q-05 | Mandatory conflict/unavailability blocks explicitly |
| Local development | Lowest infrastructure | Highest setup/service dependency | One local realization, no required external IAM |
| Credential lifecycle | Local administration burden | Often externally administered; runtime trust still needed | Local initially, replaceable without changing consumer semantics |
| Availability | Local failures remain | Adds remote dependency failures | Local first; qualified external failure scopes later |
| Replaceability | Weak if local assumptions leak | Weak if provider semantics leak | Explicit mapping and owner Ports |
| Solo implementation burden | Lowest narrow scope | Adapter/setup burden | Moderate integration; avoids federation prematurely |
| Testing | Local threat/concurrency cases | Adds provider/protocol/failure translation | Shared contract cases plus realization-specific proof |
| Migration cost | Larger if identities are local labels | Larger if IDs/roles mirror provider | Still Type 1: stable mappings/history need governed transfer |

These judgments are not measured security assurance scores or development-time estimates.

### 5.2 Decision placement alternatives

| Placement | Assessment |
|---|---|
| One central authorization service owns everything | Can provide a decision point, but cannot absorb tenant, Policy, Approval, Resources, Secrets, Plugin or domain-state ownership; external deployment unnecessary initially |
| Each domain owner invents authentication/authorization rules | Keeps enforcement close, but duplicates token interpretation, issuer trust, Policy combination and Grant meaning; rejected |
| Shared Governance decision contracts plus domain-owner enforcement | Selected: Identity/Authorization/Policy own their facts/decisions; each protected owner/invoker enforces applicable decisions and its domain invariants |

An API facade may coordinate these calls. It does not become their semantic owner or the sole enforcement point. Direct Port consumers, workers, embedded calls and CLI uses face the same contracts.

## Decision

1. **Identity evidence:** Handle raw credentials/assertions only at the protected verification boundary. Preserve safe evidence references, accepted issuer/subject binding and assurance/currentness facts.
2. **Verifier:** Use an independently trusted, replaceable verifier behind the existing identity contract. Claimed issuer names never configure their own trust.
3. **Principal binding:** Resolve verified issuer/subject/scope through explicitly administered, revisioned mappings to canonical owner-issued Principal references; no automatic display-name mapping or implicit Principal creation.
4. **Tenant:** Require one explicit verified TenantContext for each tenant-scoped operation and exactly one for each Execution. Requested tenant, relationship and action permission remain separate.
5. **Acting/delegation:** Record exactly one acting Principal, actual Actor association, originating requester and applicable bounded chain. Initial support is direct self-authority or one explicit non-redelegable authority grant to a designated deputy; arbitrary redelegation is unsupported.
6. **Grant/Permission:** Authorization evaluates current eligible grants/denials, source issuing authority, delegated scope and admitted ceiling for the exact action/target. Grant management is itself protected.
7. **Policy:** A deterministic local Policy Decision realization evaluates complete attributable applicable inputs through the replaceable Policy contract. Unknown applicability or mandatory unresolved conflict blocks, with governed disposition; no universal precedence rule is invented.
8. **Context:** Trusted Governance/boundary composition issues an immutable operation context referencing verified facts and bounded decisions. Owner-issued provenance and scope are validated at use; field shape, object type or reference possession is insufficient.
9. **Enforcement:** Domain owners and invoking planes enforce at protected reads, commits, disclosures and effect boundaries. Earlier admission/verification is supporting evidence, not permanent permission.
10. **Currentness:** Prove action applicability at each required boundary; initial decisions use current authoritative owner facts. A sequential lookup is not a race-closing mechanism. Final joint dispatch ordering remains ADR-007.
11. **Caching:** No cross-operation positive or negative authorization-decision cache initially. Immutable versioned definitions and safe verification/mapping records may be reused only under explicit scope and still-valid currentness guarantees; stale allows never replace required current authority.
12. **Root:** Require independent, explicitly bounded local identity/administrative root designation by the accountable environment authority. No unrestricted SYSTEM, ambient developer admin, self-trusting Plugin or generic break-glass bypass.
13. **First realization:** One explicit tenant and administrative Principal, a protected local verifier and deterministic local owner realizations, using ADR-004 state behavior. No enterprise IAM service required; no credentials/users/policy files are created by this ADR.
14. **Replacement:** Change verifiers/evaluators/backends through qualified adapters and explicit mapping/trust/history migration, preserving Principal/Tenant/Grant/Policy meaning and currentness.

## 6. Identity evidence verification and Principal binding

### 6.1 Narrow verification boundary

Protected ingress receives a candidate identity/issuer and protected evidence references using `verify_identity` under an already established ingress responsibility. It selects only an allowed verifier and independently provisioned trust basis appropriate to that evidence. Local bootstrap credentials, external assertions, workload identities, certificates, sessions or future methods are possible realizations, not selected formats.

Verification must establish subject/issuer/scope binding, intended relying context/recipient and purpose where applicable, validity, revocation semantics, assurance and method/environment assumptions. It must check the actual verification requirements rather than accept a parsed token or `verified=true`. Failed/uninterpretable evidence never becomes Principal authority. Invalid requests get receiver-attributed rejection evidence under CTR-006; unverified claimed tenant/Principal are labeled claims, not copied into authoritative attribution.

Only the identity boundary interprets raw credential/provider structures. Downstream owners use safe evidence and canonical references, not independently parse tokens. A verifier result reports verification, not Permission, membership, Policy compliance or a caller-chosen Principal. Human and service evidence methods may differ while preserving the same canonical binding meaning.

### 6.2 Governed mappings

An entitled identity-establishment authority explicitly establishes the Principal association through `establish_principal` using expected absence/revision. Mapping identifies accepted issuer/verifier and subject-binding reference, scope, permitted Principal kind, applicable validity/status/assurance restrictions and provenance. Provider-neutral Principal and Tenant references are not provider subject strings, usernames, email-like labels or a prescribed UUID encoding.

Ordinary requests resolve a previously authorized mapping; they do not create a privileged user on first sight. Multiple evidence identities may intentionally map to one Principal only through explicit protected association. One evidence identity mapping ambiguously to several Principals is rejected or routed to an explicitly governed disambiguation/binding operation; there is no first-match, email-match or highest-privilege selection. The chosen acting Principal's scope must match the operation.

Principal removal/anonymization follows canonical lifecycle and ADR-004 retention/non-reuse. A safe old reference never silently identifies a new person/service. This ADR adds no Principal lifecycle states. Credential invalidation, issuer distrust and Principal status changes are distinct owner facts; a historically verified identity remains interpretable even when it cannot currently authenticate.

### 6.3 Mapping concurrency and administrative identity changes

Identity associations, trust acceptance and Principal status use conditional owner-local commit with required history, retained outcome and obligations. An expected-absence check covers the complete scoped mapping identity; competing creation cannot overwrite it. Competing remaps against M4 cannot both succeed: one produces its valid successor and the other returns Conflict. A legitimate remap records new association/history and current revalidation requirements, never rewrites past attribution.

Uniqueness applies at the semantic mapping/invariant boundary, not just at different newly created row IDs. A reused operation identity with different mapping intent is Conflict; equivalent committed retransmission returns the prior currently disclosable outcome under ADR-004. New evidence does not permit renaming old externally referenced Principal identity casually.

## 7. TenantContext establishment and crossing

The request supplies its intended tenant explicitly, including local CLI/embedded use. Tenant Governance uses `bind_tenant_context` with verified Principal scope, candidate tenant, relationship/source evidence and trusted ingress attribution. It then validates exact target/resource scope with `validate_tenant_scope`. An identity assertion naming a tenant is evidence to check, not authority to select it.

Authenticated Principal plus missing tenant for a tenant-scoped operation fails safely as TenantViolation. There is no current process tenant, first tenant, connection-derived tenant, environment-derived entitlement or implicit fallback. Local configuration may explicitly identify a requested tenant, but Governance must still verify it. Membership/relationship permits neither every action nor all data access in that tenant.

Each Execution pins exactly one effective TenantContext. Child work retains that tenant unless it is a separately authorized crossing with the required distinct destination use/Execution. A caller payload naming Tenant B cannot overwrite a verified Tenant A binding. Scope propagates to state, config, effects, resources, messages, evidence, caches and errors according to ownership.

Cross-tenant access requires the explicit exact-resource/action/purpose grant and both applicable policy contexts through `authorize_cross_tenant_access`. Original scope/lineage is retained; destination copies/use and destination Execution are distinct and causally linked under CTR-039. No relabeling, multi-tenant Execution or co-ownership is introduced. The first single-tenant realization need not offer a crossing feature; it refuses unsupported crossings. A later qualified crossing must satisfy this same contract, not broaden a local default.

Tenant/resource/Grant/Plugin/Secret existence is itself protected information. Public denial need not reveal whether Tenant B or its resource exists. Authorized investigations can receive safe evidence references under their own current disclosure permission; absence of disclosed detail must not become a fabricated claim of nonexistence.

## 8. Acting authority, delegation and deputy limits

Each request-driven operation carries originating requester/Principal, exactly one acting Principal, actual Actor association, purpose where required and source authority/chain references. An Application, Agent or Service can perform work without becoming or impersonating the originating Human. Technical host/Adapter association is attributable, not hidden ambient authority.

Effective work stays within the admitted ceiling, requester's applicable authority, authorized delegable/accepted scope, acting recipient/deputy eligibility and ceiling, tenant, current restrictive Policy and applicable Approval/resource/deadline/realization constraints (SEC-019/035–037). These are jointly required constraints, not a generic union of grants or a newly invented Policy ranking. A later broader Grant cannot silently expand a begun attempt; expansion requires the explicit amendment/new attempt permitted by E-03.

### 8.1 Initial bounded delegation choice

The first security integration accepts direct authority or **one explicit authority-delegation edge to a named recipient Principal/Actor association**, with no further delegation permission. Actions, targets/revisions, tenant, purpose, validity/currentness, recipient, issuer/issuing authority, inherited ceiling, applicable policies and evidence must be established. Unsupported mandatory chain semantics fail rather than being truncated. Direct human/service work requires no Delegation entity.

This is a support bound, not a new canonical delegation model. Where work is expressed as the canonical **Delegation** entity, Work Coordination owns it and must use CTR-032, including exactly one Task or Goal revision, recipient acceptance, result/resource/deadline and reporting obligations. Authorization validates its authority chain; it does not invent a lighter substitute owned by a security context or move Work Coordination state into Governance. A bounded on-behalf-of Grant/association for a service request is also governed by its existing authorization contract and cannot impersonate canonical Task/Goal Delegation. The optional work-delegation feature does not force Team/Goal onto the direct Capability slice.

Any later multi-hop support must explicitly permit redelegation within every source bound, record each issuer/recipient/accepted scope and current validity, reject cycles/ambiguous chains and enforce a declared finite supported depth. It is not implemented or required here. Transport through several modules is not itself delegation; a change of accountable performer/recipient requires its own valid association/authority and cannot be hidden as transport to evade the one-edge limit.

### 8.2 Confused deputy and service credentials

If P may read File A and Service S's technical credential can read A–Z, P's request for Z is denied before external disclosure. S's broad credential does not augment P's authority. Enforce the verified exact target, tenant, action, input and purpose, including any target transformation performed by an Adapter. A path/display name alone is not a sufficient resource identity; target substitution or a changed effective target requires validation and current authorization for the actual resource.

Secret use must remain purpose/consumer/target-bound under ADR-010. An independently authorized service maintenance job may have different scope, but it needs its own explicit authority/causal record and cannot be substituted for P's denied request. An Agent cannot switch to the Adapter's service Principal merely because its Tool call failed authorization.

### 8.3 Parent, child and multi-Agent work

A child receives a governed derived/narrowed context with new operation identity and parent lineage. It retains tenant/origin/admitted bounds and only the minimum needed references. Changed action, target, purpose, performer, tenant or effect boundary requires the corresponding new checks; a parent allow is not inherited as a blanket permission. Scope widening is a separately authorized operation, never a context edit.

For P → Supervisor Agent → Worker Agent, an attempted new delegation by the Supervisor is unsupported initially and cannot widen read into write. A permitted initial alternative is for P's entitled authority to directly authorize the Worker as a separate bounded recipient and admit linked work; the Supervisor's message remains a request/data, not the issuing authority. This is a new explicit authorization/operation, not rewriting the existing Supervisor delegation. Future multi-hop realization must prove attenuation and attribution at every hop. No Worker gains the Supervisor's maximum technical access.

## 9. Grant, Permission, Policy and administration integration

### 9.1 Authorization owns eligible authority

`evaluate_permission` establishes eligible grants/denials for the exact Principal/action/target/revisions and current context. Grants retain issuer/subject or canonical eligibility rule, action/resource/tenant scope, purpose where required, constraints, delegability, validity/revocation, applicable Policy and provenance under SEC-017. No universal ACL schema or `resource:verb` syntax is selected.

The issuer must currently possess issuing authority for the proposed grant, including its permitted delegation scope. Resource owner/creator, canonical Role, tenant membership or an admin display label is insufficient. A Grant API cannot authorize self-escalation merely because it is callable. Delegation issuance requires authority both to perform/delegate that scope as applicable; possession of a read Grant cannot produce write or unrestricted redelegation.

### 9.2 Policy owns governing conditions

`evaluate_policy` receives exact action/subject/purpose, classified authorized context and complete applicable Policy authority/version inputs. The local evaluator is deterministic over the explicit versioned rules and attributable inputs. It uses no model judgment as an authority source and performs no uncontrolled Tool calls or hidden arbitrary context fetching. Necessary supporting reads, resource usage and evidence are separately governed and attributed; evaluation does not consume Approval or execute the proposed effect.

Applicability derives from all relevant baseline, tenant, Application, Organization, data, resource, Plugin, retention/residency and external obligations under SEC-023. The consumer cannot submit only favorable policies. Unknown required applicability is unsatisfied, not an empty policy set. The realization supports a declared finite set of policy/control semantics; unsupported mandatory semantics fail rather than disappearing during translation.

**Q-05 remains unresolved where its governing authorities have not supplied precedence.** Conflicting mandatory authorities block the affected action and create an attributable resolution obligation identifying the entitled resolution authority, basis and due/review conditions. This is not a selected universal deny-overrides, platform-over-tenant or administrator-over-all algorithm. Explicit already-authorized combination/exception rules may be applied within their proven scope; none is invented by this ADR. Retention conflict must receive timely governed disposition, not indefinite retention justified solely by default denial.

### 9.3 Combined decision and conditions

`authorize_action` at Boundary Enforcement coordinates Authorization/Policy decisions without owning their records. Its attributable result includes deciding authority, operation, originating/acting Principal and Actor association, tenant, action/exact target and material revisions, acting chain, relevant grants/denials and policy versions, outcome, constraints/obligations, validity/currentness/order assumptions and safe reasons/evidence references.

Use existing allow/deny/conditions-unmet and canonical errors. Indeterminate/unavailable means a required fact could not be established, not a new wire value or proven deny. Conditional findings do not release an effect. An allow is limited to exactly the established scope and currentness guarantee, not a durable Grant. Constraint-bearing results may identify allowed targets, purposes or required Approval; they do not reserve Resource capacity or duplicate its authoritative ledger.

### 9.4 Administration and current commit validity

Creating/revoking Grants, establishing/remapping Principals, changing tenant relationships, Policy or trust roots are protected operations. The administrator needs exact current management/issuing authority, required Approval/separation-of-duties, resources and evidence. An existing grant-management allowance cannot issue arbitrary permissions outside its bound or override a non-waivable Policy. If a required independent reviewer is unavailable, the solo-developer setting does not waive that requirement.

The owning Governance module applies ADR-004 expected-revision/absence checks, conditional durable commit, necessary history, outcome and obligations. Authorization and revision preconditions must both be applicable at the authoritative mutation boundary. A prior permission lookup followed by an unrelated transaction is not enough when revocation can intervene. Local invariant guards can cover same-owner authority facts; foreign authority requires a demonstrated currentness/ordering guarantee. Without it, the mutation is blocked. No global security transaction or hidden write across all Governance owners is introduced.

## 10. Immutable operation security context

### 10.1 Meaning and provenance

One explicit context binds the protected operation's interpretation: acting Principal, Actor association, originating requester, TenantContext, verification/mapping evidence references, acting/delegation references and bounds, operation/causal identity, admitted ceiling, authorization inputs/decision references, policy/grant revisions, purpose/target where material, currentness requirements and relevant control references. Approval/Resource/Secret references remain independently governed facts, not powers conferred by inclusion.

The initial local trust mechanism is an **owner-issued, operation-bound context record/reference**, formed only after the trusted Governance verification/binding/decision path. Protected receivers establish provenance and exact scope against the responsible owner records/decision contracts and validated caller/Actor association. A consumer-supplied copy of the same fields, Python type, `allowed=true`, valid-looking identifier or possession of someone else's context reference is not accepted as proof. A reference is not a bearer credential or Permission.

The operation owner binds this context as an immutable value in its operation/admission record, with Boundary Enforcement's attributable action decision and the source owners' exact references. Issuance means that governed binding, not a new independent SecurityContext entity or central context registry. Boundary Enforcement owns its decision; the operation owner owns its enclosing record; Identity, Tenant, Authorization and Policy owners retain their source facts. Required retained context and decision facts follow ADR-004, while their separate acknowledgments do not imply a cross-owner atomic commit.

This selects a semantic provenance-and-validation mechanism, not a context signing format, Python factory, memory-security technique or universal context service. Different semantic owners retain their source facts; trusted composition links them and does not create a `SecurityManager` owning everything. Unsupported forged/incomplete context is rejected before protected disclosure/mutation. A verification result produced by an untrusted implementation is still untrusted.

### 10.2 Immutability, refresh and equality

Bound operation meaning is immutable. Current revalidation produces new attributable decision/evidence references linked to that meaning, rather than rewriting the old context's Principal, tenant or original decision. A narrower child interpretation creates a new derived context. New verification may refresh eligibility only without silently changing action or widening a retained operation's meaning under CTR-014.

Context equality is not Principal equality: tenant, action, target, origin, actor/delegation, purpose, constraints, operation and evidence coverage matter. Mutable global `current_user`, ambient `current_tenant`, thread-local implicit authority, module permission singletons and process identity are rejected as semantic authority. Python `contextvars` or other conveniences may later transport explicit values but cannot define the security contract across threads, queues, processes, remote adapters or restart.

### 10.3 Bounded authentication context and disclosure

The first runtime permits a conceptually bounded authenticated association/session without requiring a web session. Its verifier/Principal mapping, scope, assurance, validity/revocation conditions, actor binding and applicable environment/purpose are explicit. Its existence may avoid repeating proof presentation while that verification guarantee remains valid, but it is not an authorization cache or permission lease. No universal lifetime is assigned.

Modules receive only references/claims needed for their responsibility. Full identity assertions do not travel through Plugins, Agents or Tools. The public runtime API may derive context through trusted ingress; direct Port use must present or obtain the same verified context and cannot bypass enforcement. Remote transport protection or context attestation is a later qualified realization, not an excuse to trust deserialized fields.

## 11. Protected enforcement and independent gates

| Boundary | Required integration |
|---|---|
| Protected read/existence/status/history query | Current disclosure authority for exact scope, even when returned content is historical |
| Owner state mutation/configuration change | Exact current action authority and owner revision guards; configuration precedence is not authority |
| Plugin initialization/lifecycle/activation | Established performer/context, current governing controls and allowed transition; Plugin admission does not authorize every caller |
| Capability resolution | Scoped discovery/disclosure and candidate evidence; selected Provider is not invocation Permission |
| Capability invocation / external communication | Current authority for exact action plus admitted context and all independent gates |
| Tool/Adapter handoff | Requester/deputy bound, exact target/purpose/input, jointly valid claims and currentness/order under ADR-007 |
| Secret resolution/use | Purpose/consumer/target/current authority under ADR-010; operation allow alone does not release material |
| Resource reservation/consumption | Current applicable authority plus separate Resource-owner arbitration/limits |
| Approval creation/use | Eligible authenticated approver and exact action context; Approval cannot restore revoked Permission |
| Tenant crossing | Explicit crossing Grant, both policies, original scope and distinct destination use/Execution |
| Evidence/diagnostic disclosure | Current access and least disclosure; administration/debugging is not a bypass |
| Migration/recovery/cleanup | Current bounded responsible authority, retained obligations and effects; no unrestricted worker Principal |

Enforcement occurs at the trusted boundary releasing protected data, committing state or handing off work. Ingress and earlier checks are defense in depth. Authorization is necessary but not equivalent to provider health/eligibility, Plugin admission, Approval, available budget, deadline, Secret use, mandatory evidence or isolation. Those conditions must all be satisfied where required. Sequential positive responses do not establish joint validity.

No anonymous Principal semantics are selected for protected operations. Genuinely public, non-sensitive contract operations can be explicitly designated and served through an established bounded ingress responsibility under SEC-015 without per-user protected-work machinery. Missing authorization configuration never makes an operation public, and public ingress creates no wildcard external Principal. Its own internal/evidence actions remain governed.

## 12. Currentness, revalidation and revocation

### 12.1 Current means valid at the relevant boundary

Currentness is demonstrable action applicability under the accepted effective-order, freshness, revocation, expiry and failure guarantees. It is not merely a recent timestamp, a network request, a long-lived session or a database row. Initial operation decisions consult current authoritative owner facts; immutable context pins historical interpretation, not permanent authority.

Revalidate at protected dispatch, disclosure/commit where required, tenant crossing, Secret use, Approval/resource use, Plugin initialization effects/activation, migration, external/destructive action and resumed work. Reverification is required when identity assurance/validity, mapping/Actor association, issuer trust, tenant status, purpose or environment no longer satisfies the requirement. Changed target/input/action/control revisions can invalidate the decision or require renewed Approval.

Reuse within one operation is allowed only for unchanged scope while the original guarantee demonstrably covers the actual next boundary and relevant restrictive updates. Otherwise obtain fresh authoritative validation. An additional read alone cannot close the interval between check and use. ADR-007 must establish final dispatch joint validity and authoritative order; an implementation lacking that proof cannot dispatch. This ADR does not select locks, leases, claims or a global transaction to solve the race.

### 12.2 Different restrictive changes

| Change | Required interpretation |
|---|---|
| Credential expires/is invalidated | No new authentication/use under invalid evidence; preserve safe prior verification references |
| Issuer/verifier distrusted or compromised | Block affected current bindings unless separately justified; reassess descendants under entitled replacement authority |
| Principal disabled/status no longer permits action | Future protected use fails current eligibility; historical actions remain attributable |
| Mapping/Actor association changes | Re-establish correct current association; no retrospective remapping of old actions |
| Tenant relationship changes | Revalidate required relationship/crossing; membership removal is distinct from other Grant facts |
| Grant revoked/restricted | Remove its covered authority from future effective action scope |
| Delegation revoked/restricted | No future dependent use; retain child/in-flight provenance and required obligations |
| RoleAssignment changes | Changes eligibility where a Grant/Policy depends on it, not arbitrary erasure of independent grants |
| Policy changes | Current mandatory restrictions/obligations apply; old interpretation remains historical |
| Approval revoked/consumed | No reusable approval power; Permission alone cannot recreate it |

Revocation records distinguish request, authoritative effectiveness, consumer observation, enforcement and already released effect. Owner acknowledgment identifies subject/scope, expected/produced revision, effective-order basis, impacted future/in-flight uses and remaining propagation/reconciliation obligations. It cannot claim all consumers observed it or all in-flight effects stopped merely because the revocation row committed.

If effective revocation wins order before handoff, no dispatch under that authority. If dispatch wins, report in-flight scope and constrain later protected sub-actions; do not promise rollback. Unprovable order blocks new handoff. Long-running/waiting/suspended work retains original tenant/origin and prior effects; current restrictions use only permitted lifecycle transitions and intervention obligations. A begun Execution never becomes rejected. Cancellation, failure, compensation and revocation never erase earlier effects, liabilities, disclosures or audit facts.

## 13. Cache rules

**Initial choice: do not cache allow/deny decisions across operations.** Avoid both stale authorization and stale denial after a new Grant. This bounded local design prioritizes correctness and inspectability over unmeasured optimization. There is no arbitrary five-minute TTL, disconnected last-known-allow fallback or negative-cache availability promise.

| Item | Permitted initial reuse and required checks |
|---|---|
| Verified identity evidence | Safe immutable verification record may support the bounded authenticated association only while its assurance, validity, issuer trust, binding and revocation/currentness guarantees still cover use; otherwise reverify |
| Principal mapping | Retained exact mapping is historical/reference data; current protected binding checks applicable mapping revision and Principal status, not just a cached object |
| Tenant relationship | Historical evidence retained; current required relationship/scope established through Tenant Governance |
| Grant lookup | Immutable Grant versions may be read by exact reference; current eligible status/revocation/conditions required, not old-head reuse |
| Policy definitions | Exact immutable versions/interpreters may be cached; current applicability/version selection and input facts must be established |
| Policy/authorization result | Retained for attribution; within-operation reuse only under §12's actual guarantee; no cross-operation decision cache |
| Denial result | Retained as evidence; new operation evaluates current facts rather than resurrecting a previous deny |

Any later caching proposal must specify source/owner, tenant/subject/actor/delegation/action/target/purpose scope, revisions/interpretation, freshness/coverage, expiry/invalidity and revocation sensitivity, time uncertainty and dependency-failure bounds. Cache entries never gain authority because they are locally available. Keying only by Principal or action is insufficient; Tenant A's decision cannot authorize Tenant B. Poisoned/unverifiable cached records fail provenance checks.

An external verifier outage blocks when required verification/currentness cannot be established. An already verified bounded association may be used only if its supported guarantee remains demonstrably valid without the failed dependency; this is not trusting a cached raw token or ignoring effective revocation. No such disconnected-currentness guarantee is presumed for the first realization. Wall-clock expiry alone cannot prove there was no revocation or changed Policy.

## 14. Independently established root and local first realization

The accountable environment authority must independently designate bounded identity-establishment and administrative responsibility before protected initialization. This ADR does not appoint the developer by name, treat OS-account/localhost possession as Permission, or let a candidate Plugin nominate itself. The designation is an explicit reviewed trust assumption under SEC-054–056, not an ordinary user request that bootstraps its own authorization.

The root record must identify accountable authority, actual performing Principal/realization/version, accepted evidence/verification basis, tenant, allowed administrative duties/actions/resources, ceiling, configuration, validity/revocation, dependencies, exclusions, threat assumptions, evidence/custody guarantee and failure/replacement/recovery procedure. Root authority is bounded to its designated duties; it does not imply arbitrary Tool, user-data, tenant-crossing or Secret access.

For local use, provision one explicit tenant and an administrative Principal with only the chosen bounded establishment/administration scope; make the local verifier and deterministic Tenant/Authorization/Policy/Enforcement realizations usable under the independent root basis. Persist authoritative facts under ADR-004, and expose ordinary calls through the same verified operation path. Routine direct work uses a separately authorized action Grant, not an admin wildcard. Credential type, credential storage and provisioning UI/command are intentionally not selected.

Initial trust establishment, authorization and evidence dependencies must terminate at finite independently designated roots. Required root evidence is not waived; its bounded custody attestation follows CTR-061 rather than recursively requesting identical authorization forever. If required root authority/evidence is missing or the dependency graph is cyclic, protected work cannot start. ADR-006 chooses executable Plugin/Adapter bootstrap; ADR-009 chooses evidence custody. If the eventual realization uses protected Secret material, ADR-010 must precede that use. This document supplies requirements, not a runnable bootstrap workaround.

Built-in/local Policy or verifier contributions receive no exemption from executable admission. A Policy Plugin cannot self-admit, self-trust or issue itself authority. Trust-root changes are protected owner-local revisioned operations, with lineage, descendant reassessment and explicit overlap/cutover/revocation treatment; changing a configuration file to “latest roots” cannot reinterpret existing authority. Suspected root compromise requires valid recovery authority/evidence independent of that compromised basis, or the affected scope remains blocked.

No magical SYSTEM Principal or generic emergency bypass is selected. Internal cleanup/background workers need an explicit bounded service Principal and duty, preserving original work attribution where required. Future exceptions/emergency access must satisfy SEC-079/080, including entitled basis, exact scope, bounded validity, non-waivable controls, evidence and review; urgency/config flags do not waive them.

## 15. Governance state, restart and historical interpretation

Identity mappings, tenant relationships, Grant/Policy state and trust designations use their respective owners' ADR-004 boundaries. No single security database object becomes owner of all Governance semantics. Current state, immutable history, retained operation results and outstanding obligations commit together where required; cross-owner changes remain explicit partial operations.

After restart, recover verified identity/provenance references and historical action context for interpretation. Re-establish required current Principal, issuer/mapping, tenant, Grant/delegation/Policy and independent control facts before new protected work. Historical G5 allow remains the historical explanation when current G6 is revoked; G5 does not authorize resumed work. If exact history is unavailable, report that unavailability rather than binding it to latest/current evidence.

Recovered session/context records are not automatically live credentials or permissions. Background work preserves origin and acting chain while checking both worker eligibility and current work authority. It cannot replace revoked requester scope with worker administrator privileges. Future checkpoints may preserve safe Principal/Tenant/delegation/evidence references, never raw credentials or frozen future authority; no Workflow mechanism is selected.

Backup restore must satisfy ADR-004's rollback gate. A fresh query against the same unverified old image does not establish current revocation, consumed Approval or account validity. Missing/unverifiable current authority blocks dependent work. Lost acknowledgment to a Governance mutation uses the same retained operation/equivalence and current disclosure rules; non-disclosure of an old result does not imply its effect vanished or authorize a repeat mutation.

## 16. Failure model, canonical errors and safe evidence

Required local Governance state, verifier, Policy adapter, trust root or tenant relationship may be unavailable; decisions may be stale; revocation or mapping conflict may be observed. The deterministic safe result is no protected disclosure/commit/handoff while a mandatory predicate is invalid or unproven. The evidence distinguishes an explicit denial from inability to decide.

| Condition | Canonical category/treatment |
|---|---|
| Invalid credential, untrusted issuer, unknown/disabled Principal | AuthorizationDenied when authority is absent/invalid; malformed unsupported declarations may be ValidationError where more precise |
| Authenticated Principal but missing/contradictory tenant | TenantViolation; never infer scope |
| Wrong tenant or unsupported crossing | TenantViolation or AuthorizationDenied as applicable; withhold unauthorized existence detail |
| Grant revoked/absent or delegation exceeds authority | AuthorizationDenied; no implicit fallback to deputy/service privilege |
| Missing/failed mandatory Policy/control or unresolved conflict | PolicyViolation with safe attributable obligation; no invented precedence |
| Verifier, Grant owner, Policy or trust dependency unavailable | DependencyFailure with safe underlying reason; authorization undetermined, not fabricated deny/allow |
| Required stale cache/currentness cannot be refreshed/proven | Block; DependencyFailure for missing authority dependency, or the precise denial/Policy failure when established |
| Stale expected revision or conflicting mapping/operation reuse | Conflict with no requested new mutation; currently authorized prior equivalent outcome handled separately |
| Forged context/uninterpretable mandatory input | ValidationError or AuthorizationDenied as most precise; no protected use and receiver-attributed rejection |
| Incompatible verification/Policy/state interpretation | VersionMismatch; no silent semantic downgrade |
| Required Provider/binding unusable | CapabilityUnavailable/CapabilityResolutionError where applicable, distinct from proven denial |
| Unauthorized diagnostic/status/history disclosure | AuthorizationDenied or TenantViolation as applicable; retained history/effect remains real |
| Deadline/resource condition fails | DeadlineExceeded/BudgetExceeded; earlier effects and incurred/unknown liability preserved |

Fail closed is a behavior, not a new error taxonomy or lifecycle. Safe wait, permitted suspension/cancellation/failure or intervention obligations follow existing contracts. A dependency failure does not mean nothing happened earlier; effect status remains none/partial/completed/unknown. Retries, credential refresh and compensation cannot erase consumed Approval, claims or external effects.

Security evidence identifies verification source and safe evidence reference, Principal/Actor and origin, tenant, mapping/chain revisions, exact action/target, Grant/Policy inputs, deciding/enforcing authority, outcome/constraints/currentness, effective revocation/order observations, safe reason/correlation and outstanding obligations. Decisions are immutable historical facts; revoke/change source authority for future use, rather than “revoking” the existence of a past allow record.

Ordinary logs, metrics, manifests and evidence payloads must not contain passwords, API keys, bearer tokens, private keys, full authentication assertions or raw Secret material. Any expressly required protected verification evidence custody needs its own authorized handling guarantee, not general logging. Retain minimum safe references/claims with access/retention controls. Private model chain-of-thought is never required. Diagnostics themselves need authorization and may withhold detail without falsely asserting absence. ADR-009 owns mandatory custody/failure handling; ADR-013 later covers operational diagnostics.

## 17. Structural flows

### 17.1 Protected ingress

1. The established ingress responsibility receives raw candidate evidence, explicit requested tenant and exact proposed operation. It treats payload identity/tenant/admin fields as claims.
2. Identity verification validates evidence against independent trusted verifier/issuer requirements; failure stops protected processing with receiver attribution.
3. Identity/Principal resolves an authorized mapping and valid acting association; ambiguity, status or scope failure stops processing.
4. Tenant Governance binds the explicit tenant and validates relationship/resource scope; missing tenant is not filled from process settings.
5. Authorization validates requester/actor/on-behalf-of bounds and Grant eligibility; Policy evaluates all applicable attributable rules. Invalid, unavailable or unresolved mandatory conditions block.
6. Trusted boundary composition issues exact immutable operation context with source/decision references and unmet independent obligations visible.
7. The domain owner/invoker validates context provenance, actual action/scope, current applicability and independent gates at its protected boundary. It commits only its own state or performs the single governed handoff when the required ordering is proven.

### 17.2 Direct deterministic service Capability

A provisioned Service Principal P authenticates through the local verifier, explicitly requests T and is bound by Tenant Governance. A bounded Grant and current Policy permit the exact deterministic Capability/target. Its read or expected-revision mutation enforces current scope and owner invariants; required evidence/resources remain independent. Application/Service → Capability → protected owner needs no Agent, Model, Team, Workflow, RAG or Memory. Direct Port use follows the same path as the facade.

### 17.3 Agent Tool use

Human-origin Principal H authorizes narrowly bounded work for Agent A's established Actor/acting Principal association. A proposes a Tool action; its text does not authenticate, widen context, select a new tenant or create Approval. Mediation validates H's originating bound, the actual actor/deputy ceiling and current target/purpose controls. If the Adapter can access A–Z but the request permits only A, Z is refused before credential use/handoff. Required Secret and joint-dispatch mechanisms remain ADR-010/007 prerequisites.

### 17.4 Administrative change

Administrator A requests a Grant for P. Authorization establishes A's current right to issue exactly that action/resource/tenant/delegability scope; Policy applies approval/separation-of-duties/evidence rules. The Grant owner guards its expected revision/absence and current authority conditions at commit. Success produces bounded Grant/history/result; competing stale administration conflicts. Neither A's label nor P's request authorizes a self-grant.

## 18. Mandatory race and threat timelines

### Timeline 1 — Revocation race

1. T1: Governance authorizes exact action under G5 and records its scope/currentness assumptions.
2. T2: Execution prepares; no preparation step freezes authority indefinitely.
3. T3: Grant owner commits effective restriction G6 with its ordering basis and propagation obligations.
4. T4: Dispatcher must establish current joint validity/order for the actual handoff. G6 winning before handoff prevents it; T1's allow cannot override G6.
5. ADR-007 chooses the mechanism. If order cannot be established, no new dispatch. If handoff already won, report in-flight effect, constrain later actions and reconcile; no revocation rollback claim.

### Timeline 2 — Confused deputy

1. P may read X. S's technical credential can read all files.
2. P asks S/Tool Adapter for Y. The original requester and exact resolved target remain bound.
3. P's applicable authority fails for Y even though S could technically access it.
4. Boundary refuses before external read and retains safe denial evidence. S cannot silently reclassify it as its independent maintenance job.

### Timeline 3 — Delegation escalation

1. P explicitly delegates read of R1 to designated recipient A within the single-hop bound, with no redelegation.
2. A requests write or asks to issue a broader grant to B.
3. Source/recipient scope and delegability checks fail; no new authority or child context is issued.
4. Canonical work Delegation, where used, remains with Work Coordination and its acceptance rules. Future multi-hop support cannot turn read into write or bypass the original ceiling.

### Timeline 4 — Cross-tenant request

1. A request has verified Principal/Tenant A context and names Tenant B's resource in its payload.
2. Owner compares actual target scope with bound scope; payload cannot switch tenant.
3. Without valid crossing Grant and both policies, no protected access; public failure does not reveal B/resource existence.
4. A supported authorized crossing would preserve original scope and establish distinct destination use/Execution, not mutate this context into B.

### Timeline 5 — Stale authorization cache

1. A prior allow records G5; the selected first realization retains it as evidence, not a reusable cross-operation decision cache.
2. Grant/Policy changes to restrictive G6/current rule.
3. New protected work establishes current applicability. G5's timestamp/session does not satisfy it.
4. If the current owner is unavailable and validity cannot be proved, block with truthful dependency failure. A future cache must prove the same outcome, not weaken revocation.

### Timeline 6 — Identity mapping race

1. Mapping M4 binds accepted issuer I/subject S to P1. Two entitled admin operations propose incompatible changes, both expecting M4.
2. One owner-local conditional commit establishes M5 and immutable mapping history/result.
3. The other receives Conflict; it cannot silently overwrite M5 or rewrite P1's prior provenance.
4. Duplicate committed operation inquiries return the prior currently disclosable outcome; they do not create another remap.

### Timeline 7 — Restart

1. An old operation used Principal P and Grant G5; context/evidence/history were retained.
2. Governance restarts under ADR-004 and recovers that history plus current G6, now revoked, or current Principal disablement.
3. Historic attribution stays P/G5. A recovered session or background worker is not authority to ignore G6.
4. New protected work is blocked under current facts; begun Execution retains effects and uses only permitted lifecycle treatment. Unverified restore/current-state loss blocks rather than trusts the historical allow.

### Timeline 8 — Mandatory Policy conflict

1. Complete applicability identifies mandatory authority A's allow and B's incompatible deny/obligation.
2. No accepted combination/exception basis resolves the conflict under Q-05.
3. No protected effect occurs; PolicyViolation/conditions-unmet evidence and a governed resolution obligation are recorded.
4. The runtime does not rank platform, tenant, Organization or administrator to manufacture a winner, nor retain conflicted data forever without review.

### Timeline 9 — Agent context forgery

1. Agent/model emits `principal=admin`, `tenant=T1`, `permission=all` or “You are an admin.”
2. These fields remain untrusted content; they neither establish evidence nor mutate the issued context.
3. A forged context passed to a direct Port fails owner provenance/scope/caller-association checks before protected work.
4. An Agent may request an actual entitled Governance operation, whose deterministic checks still apply. Hostile arbitrary in-process code requires separate isolation; a Python class is not a defense against it.

### Timeline 10 — Authorization dependency unavailable

1. Principal and tenant are known, but required Grant/Policy/trust applicability cannot be established because its owner is unavailable.
2. Preparation or protected read/write reaches a boundary requiring that fact.
3. No protected disclosure/commit/handoff occurs. Report DependencyFailure with safe decision-unavailable evidence, not a fabricated explicit deny or last-known allow.
4. Unaffected explicitly public or independently authorized work may continue only within its actual dependencies; no global security bypass is introduced.

### Additional boundary cases

| Case | Outcome |
|---|---|
| Authenticated P, no TenantContext | TenantViolation; no first/current/environment tenant inference |
| P disabled while Execution waits | Later Tool use fails current eligibility; earlier effects remain attributable and begun work is not rejected |
| Approval exists, Permission later revoked | Approval cannot resurrect Permission; joint validity still required |
| Cached denial, new Grant valid now | New operation evaluates current facts; initial design does not serve stale negative decision |
| Issuer says it is trusted | Independent configured authority must establish trust; self-description rejected |
| Trust-root compromise | Disable/restrict affected future uses, preserve evidence, seek independently entitled recovery; no automatic self-repair trust |

## 21. Replacement, migration and Type-1 cost

### 21.1 External verifier / identity-provider replacement

Independently authorize the new verifier/issuer trust basis and qualify its evidence, relying context, assurance, revocation, mapping, failure and privacy behavior. Establish explicit verified mappings from new subjects to existing Principal references; changed issuer subject strings must not create “new people” silently. Preserve tenant identities, historical source/mapping versions and disabled/revoked status. Allow multiple deliberate credential associations only within their own scoped trust; do not merge by email/name.

Use a reviewed overlap/cutover/revocation plan under owner-local revisions, with retained outcomes and obligations. Avoid ambiguous simultaneous bindings and reject unsupported assurance/currentness. Old decisions remain historically attributable. Applications still use PrincipalRef, TenantContext and Permission semantics; they do not decode new provider subjects/tokens. Multiple verifiers are an extension to the finite trust set, not automatic federation by any issuer named in evidence.

### 21.2 External Policy / Grant / tenant backend replacement

Qualify that the replacement preserves complete applicability, exact actions/targets, constraints, authorized combination rules, conflicts, evidence, currentness and canonical failure mapping. Translating syntax is not proof of semantic equivalence. If a backend cannot express mandatory constraints or unresolved-conflict treatment, the affected use is incompatible rather than broadened to allow.

Move Grant state with issuer/delegable authority, scope, conditions, history and revocation intact. Preserve canonical Tenant references/relationships and Principal identity independent of provider IDs. Migrate owner records/results/obligations according to ADR-004, with guarded/exclusive cutover where needed and explicit partial progress; no cross-owner global migration transaction is assumed. Remote Governance adds network/partition and effective-order proof requirements, not different security meaning.

### 21.3 Reversal costs

Ports keep implementations replaceable; they do not make security migration cheap. Principal/Tenant IDs permeate persistent work/evidence, acting chains carry accountability, and Grant/Policy/mapping history accumulates. Migration needs compatible interpretation, external-reference preservation, trustworthy root transition, result/obligation retention and new qualification. Rolling back to an old backend cannot restore revoked grants, retired mappings or stale balances. After new work commits, reversal is a new reconciled migration, not loading an old snapshot.

## 24. Conformance and future proof obligations

No implementation experiment, IAM integration, test or security assurance claim is produced in this task. The document supplies structural reasoning and threat timelines. Release evidence must qualify actual realization versions, trust assumptions, failure model, policy/identity semantics and dependencies; acceptance of this ADR is not conformance or certification.

Future proof must demonstrate:

- Forged claims, untrusted issuers, ambiguous mappings and caller-constructed contexts cannot establish protected authority; reference possession alone is insufficient.

- Issuing/delegation/admin authority is bounded; self-grant, redelegation and deputy credential escalation fail.
