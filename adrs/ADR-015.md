## 1. Context, question and scope

The accepted readiness plan identifies a concrete supervision gap. ADR-001 selects conventional GIL-enabled CPython 3.14 and ADR-002 its owner/package boundaries. Execution Coordination owns attempt and cancellation semantics, but no accepted mechanism yet maps them to live tasks, workers, queue limits and shutdown. ADR-007 orders final handoff; it is not a lifetime manager for everything after handoff.

How will the first local CPython reference runtime own, bound, cancel, supervise, shut down and recover live work while preserving canonical Execution states, current authority, resource bounds, effect uncertainty and durable recovery semantics?

Initial scope is one local process and exclusive dispatch/state domain, one explicit tenant, admitted trusted built-in code and one deterministic Tool/Adapter path with configurable bounded concurrency. No Model, Agent, Team, Workflow, Memory or RAG is required. No distributed engine, broker, HA scheduler, process-worker system or hostile-code isolation is introduced.

ADR-015 is allocated in the accepted ADR index with the exact eight dependencies above. The readiness plan places this decision before ADR-014 and does not make all stateless foundation source wait for it.

Supervision is a reference realization of Execution Coordination plus bounded technical runtime duties. It does not own foreign effects, balances, Plugin state or authority. Follow ADR-002's `legoai.execution` contracts, `legoai.reference.execution` realization and private technical composition root under `legoai.runtime`. No separate service/distribution, Kernel scheduler or public executor API is created.

Canonical Execution states remain exactly **created, admitted, running, waiting, suspended, cancelling, succeeded, failed, cancelled, rejected**. Technical observations such as queue entry, worker assigned, cancellation signalled or shutdown phase are not new canonical states. Rejected remains limited to never-begun work with no admitted protected execution effect; previously begun/resumed work never becomes rejected. Task return, effect completion, Execution success and canonical Outcome assessment are distinct.

## 3. Alternatives and supporting evidence

### A — Single structured asynchronous supervisor

Owned task scopes provide a natural lifetime tree and cooperative cancellation, with one local coordination loop and inspectable context. It fits nonblocking drivers and reduces infrastructure. Blocking foreign calls can starve the entire loop, and cooperative cancellation does not stop remote effects. Viable for an async-only supported set, but would unnecessarily exclude otherwise qualified trusted blocking Adapters.

### B — Synchronous main runner with bounded worker pool

Straightforward for blocking integrations and sequential scripts. Once cancellation, background repair, status, concurrent children and shutdown must proceed together, lifetime/notification code grows. Worker cancellation and shutdown are difficult, and blocked workers can consume all capacity. A fully serial configuration is useful for initial deterministic baseline tests, but serial execution alone does not settle ownership or responsive control during waits.

### C — Minimal hybrid

One structured async supervisor coordinates bounded scopes and a bounded admission queue. A narrowly controlled thread bridge supports qualified trusted blocking calls. Durable semantic state remains outside live tasks; fail-stop exclusivity governs recovery. This adds bridge and cross-thread result handling, but supports both kinds of real Adapter without introducing another process or workflow platform.

### D — Generic job/workflow engine

An external scheduler/durable queue/workflow engine can support broader deployment and orchestration requirements. It adds infrastructure, delivery/failover/identity mappings and a second operational model before the local slice needs them. It still cannot supply current authority or undo effects. Reject for initial scope; genuine durable domain workflows or distributed availability are reconsideration triggers.

| Criterion | A — Structured async | B — Sync + workers | C — Minimal hybrid | D — Generic engine |
|---|---|---|---|---|
| Semantic fidelity | Good with explicit owner mapping | Achievable, more coordination code | Explicit owner mapping for both paths | Additional translation/failure domain |
| Task ownership | Natural scopes | Explicit worker registry needed | Scopes plus bridge assignments | Engine jobs still need canonical owners |

| Recovery / effects | Durable owners, not coroutine memory | Durable owners, not thread state | Same recovery for both kinds | Engine durability not external atomicity |
| Restart | Reconstruct safe duties | Reconstruct safe duties | Exclusive fail-stop reconstruction | Distributed takeover proof needed |
| Debugging | Local task correlation | Thread and callback correlation | Unified ownership, two driver paths | More correlated systems |
| Local burden | Low | Low initially | Moderate, no external service | Highest initial setup |

### 3.1 Concrete primitive evidence

The CPython 3.14 documentation describes TaskGroup joining children and propagating child failures through cancellation, and warns that suppressing cancellation can interfere with structured mechanisms. These are useful building blocks, not bounded-shutdown or effect guarantees. [Python task documentation](https://docs.python.org/3.14/library/asyncio-task.html)

The executor documentation states that running futures cannot be cancelled, and that pending executor work can delay program exit even after a non-waiting shutdown call. Pool workers can also deadlock while waiting on work in the same exhausted pool. [Python executor documentation](https://docs.python.org/3.14/library/concurrent.futures.html)

The runner documentation places loop creation/closure at a top-level entry and forbids running another loop in the same thread. Its executor shutdown defaults are library behavior, not this runtime's admitted shutdown bound. [Python runner documentation](https://docs.python.org/3.14/library/asyncio-runner.html)

These primary sources were checked on 2026-09-20. They support primitive viability and limitations only. No local benchmark, fault experiment or runtime Conformance result exists for this proposal.

## 4. Decision

**Select C: one runtime-owned structured asyncio supervisor, bounded admission and owned child scopes, plus a separately bounded thread bridge for qualified trusted blocking Adapters; no general process workers initially.**

Use CPython's standard-library `asyncio` as the initial replaceable coordination substrate. Use TaskGroup-style scopes for cooperative owned child lifetimes, with per-Execution wrappers and the result/cleanup rules below. Choose an explicit runtime-owned ThreadPoolExecutor-style bridge, never the incidental default executor as capacity policy; wrapper admission must bound pending submissions as well as active workers. Exact helper APIs, queue/lock classes and public facade syntax remain implementation details. These choices need no external scheduling framework and cannot become canonical Port types.

One runtime lifecycle owns one event loop and its supervision tree, startup and closure. Applications do not create nested loops inside driver callbacks or manipulate arbitrary task groups. ADR-014 will decide safe sync/async consumer-facing entry style; this ADR requires only one clear owner and no implicit nested-loop requirement. A future externally hosted-loop mode needs its own lifetime qualification; it is not silently supported by convenience calls.

Declared finite parameters cover outstanding acceptance, queue entries/bytes, active Execution scopes, child fanout/tasks, worker count and pending worker assignments, bounded control/repair duty capacity, result buffers, timing/deadlines and cleanup/shutdown observation bounds. No universal numbers or CPU-core-derived entitlement is selected. Configuration and Resources supply actual admitted limits before the path runs.

The architecture supports more than one independent operation within qualified bounds. A one-business-action setting is a valid initial baseline, while control, cancellation and bounded repair remain owned duties. Tests must exercise real overlapping operations before advertising concurrency greater than one. No strict fairness SLA, priority scheduler, tenant/provider partitioning or autoscaling is selected.

## 5. Ownership, internal registry and context

Every live task, worker, timer and background loop belongs to an admitted Execution, a named bounded root duty, a named repair/reconciliation obligation or a named runtime-lifecycle duty. Lifecycle duties such as startup/shutdown/task bookkeeping have declared finite purpose and authority; they cannot issue themselves Governance privileges. No unmanaged fire-and-forget task, detached retry loop, immortal worker or hidden executor is allowed.

A supervised item binds existing Execution/operation identity, parent where applicable, accountable owner/driver, actual Principal/requester/delegation context, explicit TenantContext, pinned configuration and relevant activation, deadline, resource scope, cancellation request/observation, effect and obligation references, and diagnostic correlation. Internal scheduler IDs are diagnostic references only. The live registry is a bounded technical index, not authoritative state or a crash journal.

Pass explicit immutable governing context at task, child, worker and protected Port boundaries. Do not reconstruct authority from thread identity or mutable globals. Context variables may later carry diagnostic convenience copies; the explicit verified value and current owner decisions remain authoritative. Context copying cannot widen delegation or silently change tenant. Thread-pool reuse must not preserve the previous assignment's caller context or material.

Before a task can release protected work, its durable semantic owner or established bounded root/lifecycle duty must be valid. Safe task registration/assignment is ordered before driver entry; a callback cannot race ahead of ownership publication. Event-loop scheduling and the GIL are not proof of atomic owner state, invariant conservation, security or correct cancellation order.

Durable facts needed after a crash include accepted scheduling responsibility, original request equivalence, begun-work knowledge, cancellation and handoff observations, results and outstanding duties. They live under ADR-004/008 owner records. Do not serialize coroutines, tasks, threads, closures, stack frames, authenticated clients or live Secret handles.

## 6. Acceptance, admission, queueing and backpressure

### 6.1 Distinct boundaries

| Stage | Actual promise |
|---|---|
| Submission received | Input reached a bounded ingress; no durable acceptance or permission yet |
| Owner creation / durable acceptance | Execution Coordination committed original operation/result and explicit scheduling/disposition obligation; queryable after lost acknowledgment |
| Execution admitted | Canonical current admission/ceiling and required feasibility checks passed; not started and not effect authority |
| Execution begun | Owner records `running`/started evidence after current start conditions; live driver scope has an owner |
| Protected handoff | Invoking plane commits actual ADR-007 acceptance with complete current conditions; independent of queue order |
| Operational result / Execution disposition | Owner postconditions and effect/accounting/obligation evidence determine the permitted result/transition |

Select **durable scheduling responsibility before returning an accepted submission acknowledgment** for this reference runtime. Creation alone does not imply admission; it includes explicit owner responsibility to start eligible work or record its cancellation/rejection/unavailability disposition. If a response is lost around that commit, ADR-008 status/equivalent retransmission determines the outcome. A volatile queue insertion never masquerades as durable acceptance.

### 6.2 Queue mechanics and persistence

Select a bounded in-memory FIFO dispatch-ready queue containing safe references to durably accepted owner work. Queue entries are technical observations while an Execution may still be created/admitted; “queued” is not a canonical state. Eligibility/admission is established before expensive task/worker allocation and revalidated at start and each handoff.

Enforce a durable owner-local bound on accepted unresolved scheduling obligations, not merely the visible in-memory queue. Otherwise restart/paging could hide an unbounded backlog. Resources separately owns any authoritative queue/occupancy allocation; partial capacity acquisition is tracked and reconciled under owner rules. No cross-owner atomic acceptance is implied. Technical queue reservations cannot be reused while a raced durable acceptance outcome is unknown.

Local queue order follows eligible enqueue acceptance order, with a recorded owner-local ordering basis where needed for restart. It is not a global semantic clock. Remove/disposition canceled or expired entries; a path that is currently unavailable need not block independent eligible entries indefinitely. No strict fairness or starvation bound is asserted without evidence. Queue order does not dictate actual start/completion/handoff order, which depends on current eligibility and ADR-007 arbitration.

If capacity is full, the initial submission path returns a truthful canonical resource/capability unavailability result rather than allocating an unbounded waiting coroutine. Waiting is supported only for already accepted work within its finite queue/deadline. Caller retry is separate governed work; capacity refusal is not permission for an infinite retry loop. Wrong authority/version/tenant errors remain more specific when established. If an Execution was already created by an earlier stage, retain that fact and its next disposition; do not report a fictional never-created operation.

Queue memory loss on crash loses an optimization, not accepted responsibility. Recovery discovers pending accepted work through owner queries/indexes in bounded pages, reconciles begun/handoff facts, and rebuilds only safe eligible entries. Recovered unstarted work is not automatically dispatched on stale authority. Work without a committed acceptance receives no durable scheduling promise; status must establish authoritative absence before a safe resubmission is inferred.

### 6.3 Capacity, memory and failure storms

Concurrency is explicit scope configuration plus authoritative Resource admission, not CPU count, executor defaults or a semaphore's initial value. A semaphore can bound technical occupancy but cannot issue capacity, refund usage or establish unknown work stopped. Queue entries, task/child registrations, outstanding accepted work, worker assignments and result mailboxes all have finite bounds; durable history stays in storage, not an ever-growing registry.

Use one local scheduling domain without speculative tenant/provider partitions. Include a bounded control/repair allowance in the total admitted resource envelope so saturated business work cannot consume all capacity needed to cancel, record/reconcile or stop it. This is necessary lifecycle capacity, not a general priority framework. Its actual limits and eligible duties are explicit; unused repair headroom is not permission for unrelated effects.

Failure storms produce durable obligations and bounded backpressured repair discovery, not one task per historical failure. Limit outstanding work admission and recovery page size; when mandatory evidence/state capacity cannot be maintained, refuse affected new work. Retry attempts and delayed timers remain counted, owned and bounded. No universal backoff algorithm is selected. No finite capacity policy can promise progress through an unresponsive driver; §10/13 preserve that limitation.

## 7. Parent/child structure and result handling

Parent scopes own child lifetime. Child work receives no more than the intersected authority, delegated scope and inherited resource/deadline bounds. New task identity cannot reset cumulative consumption, attempt limits or prior effect history. A child that is a separate canonical Execution has its own accepted/admitted identity and parent link; an internal helper task uses the parent's bounded work scope and receives no independent dispatch permission.

Scope exit joins, cancels and settles all owned children or records an explicit transfer to an existing bounded obligation/lifecycle duty when canonical rules permit. A transfer names actual current owner/authority/resource limits and durable duty before the original scope is considered disposed. It does not create a new detached-job entity or silently promote user work into service privilege. If safe disposition cannot be established, the parent cannot claim its stop postconditions succeeded.

Do not occupy every active/worker permit with parents synchronously waiting for children requiring the same exhausted permits. Before spawning, establish bounded fanout and compatible capacity, or use a declared sequential/internal helper path within the admitted scope. If additional child capacity is unavailable, refuse/defer through explicit owner behavior rather than hidden recursive pool submission. No worker may synchronously submit-and-wait on the same saturated bridge. A more elaborate suspended-parent capacity policy would require explicit conservation proof; none is assumed here.

Group related cooperative children within their parent's structured scope. Expected driver/domain failures become attributed structured outcomes through per-Execution wrappers, so one ordinary business failure does not automatically cancel all unrelated business Executions in a single global TaskGroup. For dependent siblings, request cancellation when declared parent postconditions can no longer be met; preserve every relevant failure, effect and unfinished duty.

A supervisor invariant failure instead closes affected admissions/handoff eligibility and initiates bounded fail-stop handling. Do not suppress it as a normal business result. Cancellation signals are propagated after permitted cleanup; arbitrary blanket exception handling must not swallow cancellation or host-termination requests.

Aggregate child observations deterministically using stable child/operation references and canonical cause selection rules, retaining material secondary errors and effects. Python ExceptionGroup and CancelledError remain implementation mechanics, never canonical result/error classes. Expected-revision and ADR-008 equivalence guards arbitrate late/duplicate callbacks; arrival order cannot overwrite a terminal result or erase a prior cancellation decision. Late effect evidence can be appended without reopening the Execution.

Parent completion depends on its declared postconditions, not all coroutine returns. A task may return after scheduling repair while the parent's completion remains blocked. An Execution may reach a permitted failed/cancelled state with effects and continuing reconciliation duties. That is not canonical Outcome assessment, Goal achievement or Task acceptance.

## 8. Cancellation, deadlines and cleanup

Cancellation requested, new child admission prohibited, task signalled, driver acknowledgment, external stop requested, cleanup observed and Execution settled are separate facts. The owner records the request under current authority and expected revision. Local cancellation becomes effective for new affected handoffs through ADR-007's participating ordering; a queued or prepared action cannot use a stale positive check.

For created/never-started admitted work, remove its pending scheduling entry and perform the permitted cancellation/disposition with no driver start. Release only resources proved unused; earlier preparation/custody/claim facts remain. For running/waiting/suspended work, use canonical cancelling transitions and driver-specific stop requests. Record failed cancellation through a permitted failed transition with uncertainty when its criteria hold; do not pretend every stop request eventually proves `cancelled`.

Cooperative async work receives the runtime cancellation signal and must stop new sub-work, perform bounded cleanup and propagate it appropriately. Blocking/remote/non-cancellable work declares its actual interruption capability; the caller can stop waiting while the supervisor retains ownership. Cancellation never implies effect none, refunds consumed Approval or restores used capacity.

Queue wait, worker assignment, running work and ordinary cleanup consume the inherited deadline. Timeout triggers a stop/disposition decision; it does not prove a thread terminated or remote target stopped. Retrying or creating a child cannot extend the deadline except through an explicit authorized parent change. A scheduling timer is not the ADR-007 hard-validity proof at actual handoff.

Cleanup has a named owner, exact scope, finite bound, current authority/resources, safe outcome and remaining obligations. Do not hide failure in a `finally` block and report success. If essential cleanup cannot fit within the original deadline, it may proceed only as separately authorized bounded existing cleanup/repair work, not by extending the expired business action's authority. Record that duty and retain its live owner before transfer; if no authority is available, leave intervention rather than bypass controls.

Any shielding used to record cancellation/cleanup protects only a narrowly bounded owned bookkeeping duty; it is not blanket immunity from cancellation or a guarantee it survives process failure. Timeout/cancellation of a caller must not drop the supervisor's last reference to a still-running task/worker. If observation bounds expire, record or rely on pre-existing durable obligations and follow fail-stop rules; no asynchronous timeout wrapper makes non-cooperative code safe.

## 9. Protected handoff and lock discipline

Supervision controls when work may seek handoff; ADR-007 decides whether actual acceptance is valid. Queue admission, task creation, worker dispatch, healthy Plugin status and an inherited context are not effect authorization. Every later protected action rechecks current Principal/Tenant, revocation, Plugin eligibility, pinned action/configuration, Approval/resources/evidence and any Secret-use predicates.

Worker submission is not automatically protected acceptance. A qualified bridge first assigns bounded technical capacity, then enters the actual admitted Adapter acceptance path with current guards; it cannot validate on the loop and send arbitrary future work to a blocked worker using stale permission. If acceptance is on a worker thread, that thread must participate in the same arbiter/owner guarantees and demonstrate its exact acceptance/timing boundary. A driver unable to provide this is unsupported for the claimed protected path.

The final gate does not encompass child joins, worker waits, remote completion, arbitrary Plugin/application cleanup callbacks or slow evidence production. It permits only ADR-007's bounded final participant commits/checks and non-reentrant acceptance. Async scheduling delay, no-await code and the GIL do not establish a check-to-acceptance bound. Required timing/currentness must be proven for the actual primitive or the path remains unavailable.

Adopt this internal ordering discipline:

1. Supervisor queue/registry locks protect only short technical index changes. Release them before acquiring the handoff arbiter, calling owners or waiting on any task/worker.
2. Participating effect/invalidating mutations acquire ADR-007 arbitration before applicable owner-local transactional locks, in the agreed deterministic participant order. No owner may hold such a lock and then wait for arbitration in the reverse order.
3. Owner commits return bounded results/obligations; they do not call arbitrary supervisor/Plugin callbacks while locked. Notifications are processed after locks/transactions release.
4. No join awaits a child/worker while retaining a resource it must acquire to finish. No blocking Future result wait occurs on the event-loop thread.
5. Plugin stop/shutdown first publishes its ordered restriction; it releases arbitration before draining affected work. Lifecycle cleanup follows its own current bounded duty.

This is not one giant runtime lock. Qualification must inspect all call paths, including owner/storage callbacks and hidden SDK execution. If a dependency cannot obey the order/bounds, redesign or exclude that integration rather than claim deadlock freedom from naming locks. Storage waits inside mandatory final commits retain ADR-007's failure/bound limitations; timeout alone does not license an old holder to continue while a replacement runs.

## 10. Blocking-worker bridge and non-cooperative work

Select explicit bounded threads only for trusted blocking calls whose behavior can meet the admitted scope. No general multiprocessing/worker-process pool is selected: it would add serialization, cross-process authority, recovery and effect hazards. CPU-heavy work or arbitrary unbounded SDKs may be unsupported initially. A later process realization is not automatically security containment; ADR-012 still governs that claim.

The bridge is supervisor-owned with explicit maximum workers, bounded pending assignments and bounded result delivery. Do not submit an unbounded series into an executor simply because active worker count is limited. No protected SDK may create an unknown executor, thread, retry timer or session outside this ownership; discover and qualify all such behavior, or disable it/reject the path.

Each assignment carries immutable explicit context, owner/operation references, actual acceptance requirements, remaining deadline, stop capability and cleanup duties. Register before submission and retain assignment until the worker physically completes or the process is confirmed terminated. Result callbacks only transfer bounded observations to controlled completion handling; they do not directly mutate foreign owner state or trust an unverified result.

A Python thread in blocking foreign code generally cannot be safely force-killed by cancelling its awaiter. A caller timeout can coexist with a still-running worker and unknown effect. Do not release its worker slot for reuse merely because the awaiter ended; that would exceed the real concurrency bound. Resource occupancy and unknown liability are released only under the appropriate owner's actual stop/non-use/settlement proof.

If a worker ignores stop, retain bounded observation and the exact unresolved duty, close new uses of affected capacity/path, and request qualified host termination when required by the admitted failure policy. A narrow separately governed observation/cleanup duty can outlive the caller only with explicit ownership as in §7. It cannot continue new business effects after cancellation. If it cannot be contained/fenced, safety may require stopping the whole local process/domain; do not start replacement workers/supervisors to conceal the hang.

Do not assume `shutdown(wait=False)`, interpreter exit, a daemon thread or a canceled Future provides a safe bounded exit. Graceful join may fail. Forced process termination requires an actual qualified host mechanism and authority; it is not implemented or selected here. Without that mechanism, report shutdown incomplete and keep replacement admission blocked while the old process might act. After forced termination, remote effects can still be unknown and require ADR-008 reconciliation.

The first cooperative deterministic slice need not use the thread bridge. Blocking paths become supported only after their worker acceptance, cancellation/exit and hidden-thread behavior are qualified. This prevents a generic timeout wrapper from silently enlarging the supported guarantee.

## 11. Resource occupancy, background duties and retry scheduling

Supervision tracks technical queue entries/tasks/worker assignments; Resources alone issues authoritative occupancy/spend claims. Admit technical capacity before expensive work, reserve external spend close to actual need, and still meet the full ADR-007 claim set at handoff. Queueing can itself cost memory/control work and therefore has bounded governed scope. Task end alone proves neither unused resource nor absent external charge.

Named background duties include exact evidence repair, effect reconciliation, settlement, Plugin cleanup and state maintenance obligations. Each has accountable owner, purpose, explicit Principal/Tenant, target/revision, finite resource/attempt/deadline scope, observed status and restart/disclosure rules. No unrestricted admin sweeper or infinite catch-all retry loop exists. Root duties obey ADR-005/006/009 finite designation, not a supervisor-created superuser.

Discover pending duties from durable owner indexes in bounded batches. A live duty failure/cancellation leaves the obligation pending/failed/requires intervention as its actual owner rules specify; it is not satisfied by worker exit. Retry eligibility comes from ADR-008 plus current authority, effect safety and remaining bounds; the supervisor merely schedules a permitted next step. Reconciliation is not implicit redispatch, and Evidence repair cannot repeat the producing effect. Delayed retry timers have explicit owners and capacity; no universal delay algorithm is selected.

Failure-storm admission and shutdown use the same finite budgets. The runtime may refuse new business work while preserving a bounded authorized control/repair path. If mandatory repair cannot make progress, retain visible intervention obligations and stop promising full path readiness. Do not queue every historical obligation in memory or erase work to make backlog metrics look healthy.

## 12. Startup, Plugin readiness and partial availability

Process launch is a technical action, not platform authority. Startup is a bounded runtime-lifecycle duty under independently established host/root authority. The safe sequence is:

1. Establish exclusive local runtime/dispatch authority and verify no stale process can mutate participating state or reach acceptance.
2. Establish the finite independently designated roots and qualified storage access needed to read/recover owner facts. No dependent Plugin self-admits; a Secret-bearing root uses ADR-010.
3. Recover owner state, retained operation results, accepted scheduling duties and outstanding effects/evidence/settlement/Plugin cleanup through bounded indexes.
4. Classify uncertain handoffs and prior begun work; re-establish current configuration interpretation, authority and required dependency/custody readiness.
5. Perform required Plugin stage work through admitted bounded lifecycle duties; activation and offer eligibility are separate. Do not eagerly start optional Model/Agent/Secret/observation exporters.
6. Rebuild live scopes only for safe permitted next duties, and open new admissions per qualified independent capability path.

Do not require all historical obligations to be resolved globally before an independent safe path can run. Do require that obligations affecting a path's authority, effects, resources, storage or custody are identified and safely dispositioned before that path is declared ready. A missing authoritative scan/coverage proof cannot be replaced by an empty in-memory list.

Distinguish process running, supervision/control availability and a specific capability's current eligibility. Health does not issue Permission. If mandatory Evidence or an owner is unavailable, block the affected protected path; genuinely independent qualified read/non-effectful paths may remain available with current access. Required storage outage never permits memory-only protected execution. Optional observation degradation follows only its explicit tolerance and cannot imply custody success.

## 13. Shutdown sequence and partial failure

Select stop-admission followed by an ordered no-new-business-handoff barrier, bounded cancellation/drain, durable disposition and safe closure. These are technical phases, not canonical states. Shutdown itself has a named lifecycle owner, current authority and finite resource/time scope; it is not a universal kill or rollback grant.

1. **Close new admission and child expansion.** Serialize the runtime acceptance stop with in-progress owner acceptance. Requests already committed remain owned; incomplete commits are queried under ADR-008. Mark accepted queued work for governed disposition, not deletion.
2. **Establish the handoff barrier.** Through ADR-007 participation, prohibit new business handoff in affected scope. Until that barrier is actually effective, report it pending; do not falsely acknowledge stopped dispatch. If a handoff wins first, it is in flight.
3. **Disposition queued work.** Prevent driver start, cancel or otherwise transition under canonical never-started rules and retain prior facts. Release only proven-unused owner claims. Do not mark queued work succeeded.
4. **Request bounded cancellation / drain.** Notify cooperative drivers, children and supported provider stops. Observe already accepted effects outside the gate. Only explicitly authorized shutdown/cleanup/evidence duties may make required protected calls after the business barrier, with exact separate purpose and current admission; there is no global bypass flag.
5. **Record unresolved and completed facts.** Source owners commit actual results/uncertainty, remaining resource liability and repair obligations; Evidence provides required custody. A failed state/custody write is visible. Durable pre-handoff/acceptance obligations established earlier are the recovery basis if this final recording cannot occur.
6. **Join and close safely.** Join cooperative scopes/workers within demonstrated observation bounds; drain required local result handling; close drivers before the storage/custody they still need. Do not close a store underneath a surviving worker and pretend it is fenced. Non-cooperative work invokes §10's incomplete/forced termination path.
7. **Finish or report incomplete shutdown.** Graceful completion requires the defined local stop/postconditions and no unowned live work; authorized durable external reconciliation can remain explicitly outstanding. Terminate the supervisor/loop only after safe disposition. Required unsettled facts prevent a clean-completion claim.

Graceful drain, authorized forced process termination and accidental crash have different evidence. None erases in-flight work, refunds consumed Approval or turns unknown into none. A deadline expiring during failure-storm shutdown cannot be solved by waiting forever for a clean flag. Retain what is durably known, disclose recording gaps and follow qualified host termination; if no safe termination is available, shutdown remains incomplete and new runtime takeover is refused.

No OS signal mapping, CLI command/exit code or host-management product is selected. Future process-signal handlers merely request this lifecycle behavior; they do not supply authority or guarantees by themselves.

## 14. Restart, exclusivity and orphans

Fail-stop single-process admission is selected. A replacement must establish that its predecessor cannot mutate owner records or reach actual acceptance, under ADR-007's qualified mechanism. Lock-file age, PID change, heartbeat timeout or an epoch label alone is insufficient. If a new fence exists later, both state writes and acceptance must enforce it. No lease-based automatic failover is introduced.

Tasks are not resurrected. Recover semantic Execution/operation/effect/history/obligation records under ADR-004/008, assess exact begun-work and handoff knowledge, then schedule only entitled safe work. A new Execution retry is linked and retains applicable accounting/effect identity; an unstarted durably accepted request may resume admission only if authoritative evidence establishes that disposition as safe. A running record with no live task is not automatically replayable.

| Orphan/uncertainty | Safe disposition |
|---|---|
| Durable accepted/created Execution, no live task | Expected after crash; inspect scheduling/begun/handoff facts, then revalidate safe start or record cancellation/rejection as permitted |
| Durable begun Execution, no live task | Recover driver/effect/obligation knowledge; reconcile, permitted resume/fail/cancel/intervention; never relabel rejected or assume none |
| Live task without valid semantic owner/duty | Enforcement defect; block its protected use, retain safe observations, cancel/contain and escalate fail-stop if needed |
| Worker with missing/unknown parent | Do not free/reassign its capacity or trust output; block new effects, recover assignment/obligation knowledge or stop affected domain |
| Unresolved handoff attempt | ADR-008 uncertainty; query/reconcile or entitled intervention, never blind resend |
| Completed owner result with lost callback | Current authorized status/equivalent lookup recovers outcome; no rerun |
| Background loop missing while obligation persists | Discover and reschedule the exact safe duty under current authority/bounds, not its original business effect |

Startup queries obligations and retained results; it need not load full history. Scope-specific missing/corrupt records remain unavailable, not fresh authority. Old snapshots cannot reset grants, balances, consumed Approval, material validity or deduplication coverage. A stale callback/result must pass original identity/equivalence and owner revision checks; it cannot overwrite a newer disposition.

## 15. Plugin, configuration, Secret and driver interactions

Admission/scheduling validates the contribution's appropriate lifecycle stage. Ordinary invocation requires current initialized/active/eligible conditions; permitted bootstrap/initialization/cleanup duties use their exact admitted stage and ceiling, not an indiscriminate active-only shortcut or general inactive invocation.

Plugin stop/failure/retirement restrictions participate in ADR-007 before new affected handoff. Queued tasks revalidate rather than invoking an old Resolution. Drain/cancel observes in-flight effects and may preserve cleanup/publication duties under ADR-006. Plugin health/lifecycle, task/Execution outcome and effect status remain separate; a Plugin failure is not universally `failed` plus `none` for every associated operation.

Existing work keeps pinned ADR-003 configuration interpretation and activation references; new admitted work can use a different revision without mutating old tasks to latest. Materially incompatible coexistence is not assumed. Future Secret-bearing work uses ADR-010 at actual use; the supervisor does not cache raw material or serialize frames for checkpointing. Cancelled context cannot be silently replaced with a service Principal to keep work running.

Drivers need inspectable start, supported stop request, observation/result and cleanup boundaries, as internal realization contracts beneath canonical Ports. Non-cancellable drivers are admitted only where their stated limits meet the supported path; none is qualified by wrapping it in a timeout. Hidden SDK retries may create multiple transport attempts within one task and must satisfy ADR-008. Hidden threads/callbacks that outlive the apparent call require explicit ownership/limits, otherwise the path is unsupported.

## 16. Diagnostics, Evidence and failure mapping

Basic local diagnosis is required before Gate 2: safe Execution/operation/effect correlation, pinned config and contribution versions, task/duty owner, bounded queue/worker assignment observations, task start/stop, queue delay, cancellation request/acknowledgment, driver/handoff/cleanup observations, shutdown progress, orphan/recovery and outstanding owner obligation references. Latency/time basis and canonical cause/effect references remain explicit; trace IDs convey no authority.

Observation is not Evidence, state or provenance custody. A log saying cancelled does not prove a worker stopped or satisfy a stop obligation. Required source/decision facts enter their owners and ADR-009 custody; optional logging failure neither erases them nor permits missing mandatory evidence. Scheduler inspection requires current tenant/disclosure scope and must not expose payloads, Secrets, private reasoning or another tenant's existence. Bound logs/buffers and report relevant observation gaps.

Internal exceptions become attributed driver/owner observations with safe diagnostics, effect knowledge and bounded cleanup. Map known cause to existing canonical categories, including AuthorizationDenied, TenantViolation, BudgetExceeded, DeadlineExceeded, Conflict, VersionMismatch, DependencyFailure and invoked-family failures. An unclassified internal execution fault may use ExecutionFailure with limitations. Do not introduce Python exception classes, scheduler-specific canonical errors or cancellation-as-none. An error response to a command does not automatically change the Execution lifecycle.

## 17. Structural walkthroughs

### W1 — Direct deterministic Capability

An explicit Application context submits an exact bound local Tool request. Execution Coordination durably accepts scheduling responsibility, admits current scope and queues a reference within bounds. The supervisor starts an owned Direct scope, acquires current resources/Approval/evidence as applicable and the invoking plane executes ADR-007 acceptance. The cooperative or qualified worker path observes result, cleanup and accounting/custody obligations. Owner postconditions determine the result; no Agent, Model, Workflow, Team, Memory or RAG exists on this path.

### W2 — Blocking driver and timeout

An owned async parent obtains a bounded bridge assignment after admission. The worker carries explicit context and reaches qualified current acceptance; the external SDK then blocks. Caller deadline expires and stop is requested, but the worker may continue. Keep assignment/technical occupancy and uncertain effect/liability, prohibit later business handoffs, record bounded observation/reconciliation duty. On actual return, owner guards record late evidence; if it never returns, use incomplete/qualified forced termination handling. No timeout wrapper releases a second worker into the same counted slot.

### W3 — Shutdown with partial failure

Close acceptance with pending commits resolved; establish ordered business-handoff restriction. Disposition queued work and request bounded active cancellation/drain. A receipt effect already completed but its audit write fails: preserve its producing source duty and repair only evidence. A worker still needs state/custody: do not close those dependencies first. At the bound, disclose unresolved duties and invoke only qualified termination; no clean flag is fabricated from loop exit.

### W4 — Crash/restart

Process crashes with accepted queued work, an unresolved handoff and a completed result whose callback was lost. The new process proves exclusivity, recovers exact owner facts/root readiness and queries bounded outstanding indexes. The unstarted request can be newly admitted only after safe absence/currentness checks; unresolved handoff is reconciled; completed result is returned under current disclosure. New live scopes execute only those safe duties. No task object or old credential is restored.

### W5 — Two kinds of orphan

A durable Execution with no live task is normal after crash and is resolved through state/effect knowledge. A live protected task with no valid durable owner/duty is an enforcement defect: stop its release path and contain it. Neither case proves effect absence, and neither authorizes minting a fresh operation identity to escape uncertainty.

### W6 — Future Model and Agent consumers

A later ModelPort call uses the same owned scope, current authority, deadline, provider cancellation limits and unknown-charge handling; qualified Secrets and Evaluation remain separate obligations. A later Agent can own bounded supervised children/tool requests with exact context and parent accounting. This supplies lifetimes, not Agent planning, autonomy or Team semantics. A future Workflow driver owns domain progression and checkpoints; no engine is selected. ForgeAI later consumes the supported facade, not private task machinery.

## 18. Failure timelines

### Timeline 1 — Normal supervised action

1. Accepted scheduling responsibility and current admission are durable; scope/worker ownership is registered.
2. Invoker establishes current complete conditions and actual protected handoff.
3. Driver observes effect, performs bounded cleanup and returns structured facts.
4. Owners commit permitted result/obligations; technical task completion does not substitute for these postconditions.

### Timeline 2 — Cancellation while queued

1. An accepted never-started request occupies a bounded queue entry.
2. Authorized cancellation wins owner/order guards before start; remove eligible entry and prohibit invocation.
3. Perform permitted canonical cancellation and settle only proven-unused claims.
4. Prior preparation costs/custody remain; no driver call is inferred.

### Timeline 3 — Cancellation during cooperative work

1. Parent runs with owned children; an authorized stop request becomes effective.
2. Prohibit new children/affected handoffs; signal cooperative children and join/cleanup within bounds.
3. Record individual child/effect results and unresolved duties.
4. Owner settles only a permitted state; task cancellation cannot erase earlier effects.

### Timeline 4 — Cancellation during blocking SDK use

1. Qualified worker has accepted the protected call and blocks.
2. Async waiter times out/cancels; underlying thread may remain live.
3. Keep assignment, occupancy, effect uncertainty and bounded observation duty; do not claim stopped or reuse the slot.
4. Reconcile actual return or follow qualified fail-stop handling, without blind retry.

### Timeline 5 — Deadline expires while queued

1. Durably accepted work has not begun; queue wait consumes its deadline.
2. Start/currentness validation refuses invocation and records the deadline cause.
3. Apply only the canonical allowed never-started disposition; no invented `queued-expired` state.
4. Preserve earlier costs, claims and evidence; release only owner-proven unused capacity.

### Timeline 6 — Deadline expires after handoff

1. Actual valid handoff precedes expiry; the target may still act.
2. Stop future protected actions/children, request supported cancellation and bounded cleanup.
3. Effect remains none/partial/completed/unknown according to evidence, not the timeout category.
4. Settle allowed Execution state and retain external uncertainty/charge duties.

### Timeline 7 — Driver raises before handoff

1. Owned driver faults during preparation.
2. Invoker evidence must establish no protected handoff to report that named effect as none.
3. Record safe cause, partial owner claims and bounded cleanup.
4. No generic Python exception becomes a canonical rollback or automatic Approval refund.

### Timeline 8 — Driver fails after handoff

1. Protected request is accepted; driver faults before a reliable result.
2. Preserve actual known extent or unknown effect and required resource/evidence duties.
3. Supervision records driver failure and stops related new work as required.
4. ADR-008 reconciliation determines next safe action, never automatic rerun.

### Timeline 9 — Process crash before durable handoff attempt

1. Some owner preparation/claims commit, but intended handoff attempt has not committed.
2. Process crashes; recovery queries authoritative coverage and any related effects, not just a missing task.
3. Only if complete relevant evidence proves no possible handoff may that effect be treated as none; earlier consumed claims persist.
4. Revalidate safe next work or hold if records/coverage cannot establish it.

### Timeline 10 — Crash after durable attempt, acceptance unknown

1. Invoking owner records exact handoff-attempt obligation.
2. Crash occurs before or after actual acceptance with no durable confirmation.
3. Recover unknown; local task/queue absence cannot distinguish the two histories.
4. Query/reconcile or use explicitly qualified ADR-008 continuation under current controls; no blind replay.

### Timeline 11 — Stale prior supervisor

1. A new process observes an old lock/heartbeat while predecessor may still run.
2. Refuse protected admission/takeover until actual termination or enforceable write-and-acceptance fencing is established.
3. A changed PID/epoch alone does not qualify exclusivity.
4. After proof, recover owner knowledge before new work; no dual spending domain.

### Timeline 12 — Shutdown with queued and active work

1. Close admissions, account for racing commits and publish ordered business-handoff restriction.
2. Cancel/disposition unstarted queue entries and bound active drain/cancellation.
3. Record results/uncertainty/obligations, join or explicitly dispose of live duties before closing dependencies.
4. Report exact remaining obligations; shutdown is not global rollback or guaranteed clean completion.

### Timeline 13 — Hung worker during shutdown

1. Blocking worker ignores stop; shutdown observation bound expires.
2. Keep it known and its capacity/uncertainty unresolved; no force-kill-thread claim.
3. Request qualified host process termination or report incomplete shutdown; do not close state beneath live unsafe access.
4. Replacement stays blocked until old authority cannot act; restart reconciles possible effects.

### Timeline 14 — Evidence repair duty crashes

1. A completed business effect has an outstanding custody duty.
2. Its bounded repair task crashes before confirmed custody acknowledgment.
3. Owner obligation remains discoverable; repeated repair uses original evidence operation equivalence/status.
4. No supervisor loop retries the producing business effect to regenerate evidence.

### Timeline 15 — Plugin stop while work queued

1. Request binds P and waits; Lifecycle starts an effective stop/eligibility restriction.
2. Queue/start and final handoff checks cannot use stale P eligibility.
3. Record appropriate unavailability/cancellation disposition, preserving prior claims and already in-flight scope.
4. No silent fallback to another provider or reactivation through task creation.

### Timeline 16 — Saturation and backpressure

1. Accepted-work, live-scope or bridge capacity reaches its configured governed bound.
2. New submission/assignment is refused or already accepted work remains boundedly queued; no extra thread/task allocation.
3. Named control/repair capacity remains within its separate bounded allowance; failure storms stay durably discoverable.
4. Release requires actual technical completion and owner rules; an abandoned waiter does not free a running worker.

### Timeline 17 — Duplicate completion and child failures

1. Two child failures and a duplicate late worker callback arrive in different orders.
2. Keep stable child/effect references and material causes; owner revision/equivalence guards prevent double application.
3. Parent postconditions and cancellation history determine the permitted disposition, not first callback wins.
4. Late effect evidence appends history without rewriting terminal state or hiding another failure.

### Timeline 18 — Configuration coexistence and Secret rotation

1. Existing work binds C1; a new admitted activation uses C2 and a Secret material revision changes.
2. Existing tasks retain C1 semantics while current restrictions/ADR-010 use validity still apply.
3. Revalidation may block old work; no latest-config mutation or material cache supplies permission.
4. Preserve versioned history and obligations; coexistence requires actual qualification.

### Timeline 19 — Live task lacks owner

1. Registry inspection detects a task/worker with no valid Execution or named duty.
2. Prevent protected release and retain safe correlation; do not guess a tenant or attach it to an admin Principal.
3. Cancel/contain under bounded lifecycle authority or stop affected domain if safety cannot be established.
4. Investigate effect facts independently; lack of ownership is not proof of no prior effect.

### Timeline 20 — Storage/custody outage and partial availability

1. Required durable commit or pre-effect custody becomes unavailable.
2. Affected new protected work blocks; do not downgrade to volatile acceptance or logs.
3. Independent qualified status/read paths may continue only if their own access/freshness requirements hold.
4. Recovery scans the outstanding accepted/effect duties; process alive never meant every path ready.

## 19. Threat/failure analysis and qualification

| Threat / mechanism failure | Required defense and limit |
|---|---|
| Task-context forgery / ambient bleed | Explicit verified immutable context at boundaries; reused worker cannot inherit another assignment's authority |
| Cross-tenant task/inspection reuse | Bound identities and current disclosure; initial single-tenant scope does not justify implicit tenant |
| Queue poisoning / resource exhaustion | Bounded validated references, durable acceptance limits and finite buffers; no unauthorized payload-driven task explosion |
| Worker escape / hidden threads | Qualified trusted bridge only; unknown SDK lifetime behavior unsupported; not a sandbox |
| Stale worker after cancellation | Effective new-handoff restriction, retained assignment, actual completion/fencing before reuse |
| Shutdown bypass | Ordered barrier plus exact allowed cleanup duties; no global privileged shutdown flag |
| Detached retry loop | Existing owner obligation, bounded attempts/deadline, current ADR-008 eligibility |
| Plugin callback reentrancy | No arbitrary callback while supervisor/owner/gate locks held; stage/eligibility checks persist |
| Deadlock / starvation | Explicit acquisition order and no same-pool join cycle; no fairness claim beyond qualification |
| Orphan replay / snapshot rollback | Durable knowledge/current checks; missing tasks/records are not absent effects |
| Loop starvation / non-cooperative task | Exclude blocking work from loop, bounded driver contract, fail-stop if safety cannot be maintained; no forced coroutine termination guarantee |
| State/evidence outage | Block required protected paths; preserve prior facts/obligations and explicit unavailable scope |

Actual storage/process restart claims need tests against selected real primitives. Simulated fault seams are useful but cannot establish actual blocking SDK cancellation, thread exit, remote provider behavior or host fencing. The implementation must demonstrate bounded queue/memory/worker occupancy; acceptance/lost-ack recovery; simultaneous cancellation/start/handoff/stop; child and multi-failure aggregation; hung workers; complete lock paths; stale-incarnation rejection; interruption at durable commit and acceptance boundaries; shutdown during failure storms; orphan handling; exact config/context and safe local diagnostics. Fault hooks cannot bypass the actual authorization/resource/evidence path.

Timing feasibility is an early Gate 2 experiment, not a promise deferred until after unsafe execution. Unqualified strict deadline/remote-currentness/termination claims stay unsupported. No benchmark, test or implementation is created by this ADR. ADR-011 will require scope-specific release evidence and retained negative cases.

## 20. Solo burdens, consequences and Type-1 migration

| Burden | Selected mechanism |
|---|---|
| Implementation complexity | Moderate async scopes, durable scheduling reference and narrow bridge; fewer parts than a job platform |
| Operational complexity | One local process with explicit restart/shutdown limits; some hung integrations require host intervention |
| Maintenance burden | Driver stop/lifetime/SDK behavior and owner mappings must remain current |
| Testing burden | Cancellation/worker/commit/handoff interleavings and actual crashes; larger than happy-path unit testing |
| Local-development burden | Start/inspect/fault/stop/restart locally without external scheduler; qualified local store/root setup still needed |
| Deployment burden | Exclusive process authority and bounded config; no new service, broker or worker cluster |
| Learning curve | Distinguish live task, accepted work, Execution disposition and effect evidence; explicit walkthroughs aid review |

Benefits: owned work, bounded admission, truthful cancellation, one substrate for direct and later Model/Agent paths, recoverable duties without task serialization and predictable declared shutdown behavior. Costs: async/bridge complexity, reduced availability on uncertainty/hangs, repeated currentness checks, bounded background progress and substantial failure testing. Structured concurrency reduces accidental abandonment but does not guarantee a bounded return from non-cooperative code.

Accepted limitations include trusted shared-process scope, no forced thread stop, no strict fairness/global ordering, no distributed availability and no default hard real-time promise. Execution/runtime maintainers own supervision qualification; driver maintainers own actual interruption limits; invoking/resource/evidence owners retain their obligations. Missing mandatory evidence is a blocker, not an accepted waiver.

Type 1 follows from task ownership, actual effect timing, cancellation/occupancy and durable begun/attempt knowledge. Replacement must close acceptance, quiesce/fence old supervision and dispatch, reconcile in-flight/unknown work, preserve Execution/operation/effect identities and accepted scheduling duties, transfer exact owner history/obligations, and qualify the new acceptance/cancel/cleanup/shutdown behavior before reopening. Do not run two supervisors against the same spend/dispatch scope, restore coroutine snapshots, reset resource history or infer canceled effects from process migration.

Reconsider on a demonstrated need for multi-process availability, distributed services, high blocking workloads, strict real-time behavior, hostile Plugin containment, very high task counts, cross-region operation or durable domain workflow execution. Measurements and actual consumer/failure evidence must justify expansion; none is prebuilt here.
