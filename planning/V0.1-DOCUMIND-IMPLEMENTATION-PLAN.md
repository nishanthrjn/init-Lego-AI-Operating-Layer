## B. Document Pack capabilities already present

`document.chunking` (sliding-window word chunking) and `document.parsing` (TEXT/MARKDOWN/HTML/PDF via
`pypdf`, no OCR) are both complete and will be reused **unchanged**. `legoai_document` currently
declares **zero** dependency on `legoai` Core (`tests/architecture/test_dependency_boundaries.py::test_no_dependency_on_legoai_core`) — this will change in this milestone (retrieval/embedding/answering
genuinely need Core's `ModelPort`/Catalog/Coordinator), and that architecture test will be updated
deliberately, not silently.

## C. Public Core Ports required by DocuMind that do not exist

Exactly one: **`ModelPort`** (`legoai.intelligence.model.ports`), with two operations — `chat` and
`embed`. Everything else DocuMind needs (Catalog, Resolution, Authorization, Dispatch, Coordinator,
Evidence) already exists and is reused unchanged.

## D. Smallest Model abstraction

Per ADR-002 §7.3/§15 (`legoai.intelligence.model` — "Model Interaction descriptors, validation/usage,
Model Port... I row" foreign-target maximum = K, C, M, A, G, R, O, X — **no E/Execution import from
inside `legoai.intelligence.model` itself**, matching M11's own established pattern of keeping
capability-invocation glue in composition, not in the owner's Port/reference layer):

- `legoai/intelligence/__init__.py`, `legoai/intelligence/model/__init__.py` — inert.
- `legoai/intelligence/model/values.py` — `ModelId`, `ProviderId`, `ChatMessage`/`ChatRole`,
  `ChatRequest`, `ChatResult`, `EmbeddingRequest`, `EmbeddingResult` (per
  `EMBEDDING-CAPABILITY-DESIGN.md` §8-11 for the embedding half; the chat half mirrors the same
  discipline: no `dict[str, Any]`, no provider SDK types, explicit model/provider identity on every
  result).
- `legoai/intelligence/model/ports.py` — **one** `ModelPort` Protocol with `chat(...)` and `embed(...)`.
  ADR-002 names a single "Model Port," not two — splitting into `ChatPort`/`EmbeddingPort` would be
  inventing structure authority doesn't ask for. Both operations on one Port is not "combining for
  convenience"; it is the literal accepted shape.

## E. Smallest provider Adapter boundary

`legoai/reference/model.py` (mirroring `legoai.reference.execution`/`.governance`/`.catalog`'s existing
placement pattern exactly) — `OllamaModelAdapter`, a synchronous, stdlib-only (`urllib.request`) HTTP
client behind the `ModelPort` Protocol, talking Ollama's native `/api/chat` and `/api/embed` endpoints
(per `EMBEDDING-CAPABILITY-DESIGN.md` §12's live-verified recommendation). No `ollama` package, no
`httpx`/`requests` — the reference realization needs a POST-JSON/parse-JSON HTTP client, which
`urllib.request` provides without adding a dependency (Gate-2's zero-dependency invariant is preserved).
Because `legoai.reference.execution`'s `ExecutionCoordinator` is `asyncio`-based, the Adapter's blocking
HTTP calls are invoked via `asyncio.to_thread(...)` at the composition boundary — never inside the
Coordinator's own event loop thread, and never a new blocking-worker-bridge subsystem (ADR-015 §10
explicitly says "the first cooperative deterministic slice need not use the thread bridge"; the correct
reading for v0.1 is the smallest possible bridge — one `to_thread` call per invocation — not the full
bounded-pool bridge ADR-015 describes for a later, qualified batch).

## F. Effectful replay remediation (release blocker, addressed in Phase B before any provider call exists)

`planning/GATE-2-EXIT-REVIEW.md` G2-EXIT-42/43 named the exact trigger: the first effectful capability
activates the previously-inert concurrent-double-invocation gap in `ExecutionCoordinator.invoke_governed`.
Root cause: `_require_running` (a read-only check) and the eventual terminal `_transition` are two
separate lock acquisitions, so two concurrent callers holding the same `RUNNING` `CoordinationResult`
can both pass the check before either commits.

**Smallest fix:** replace the two-step check with one atomic **claim**, still using the Coordinator's
existing `asyncio.Lock` (no new synchronization primitive, no change to the immutable `DispatchPermit`,
no new canonical `ExecutionState`):

```python
async def _claim_invocation(self, execution_id: ExecutionId) -> None:
    async with self._lock:
        if execution_id in self._claimed:
            raise ExecutionTransitionError(f"{execution_id.value} invocation already claimed")
        current = self._states.get(execution_id)
        if current is not ExecutionState.RUNNING:
            raise ExecutionTransitionError(f"{execution_id.value} is not RUNNING under this Coordinator")
        self._claimed.add(execution_id)
```

`invoke_governed`/a new `invoke_effectful` call `_claim_invocation` (not `_require_running`) as their
first step. Exactly one of two concurrent callers wins the claim; the loser fails **before** the
provider closure is ever called — the exact guarantee task item #44 requires, verified with
`asyncio.Event`-gated concurrent tasks (no sleep-based test).

**Exact guarantee, stated precisely (never overclaimed):** *one accepted governed dispatch/RUNNING
state admits at most one invocation attempt through this Coordinator instance.* This is **not**
exactly-once across network failure — if the HTTP request reaches Ollama but the response is lost
(timeout, connection drop), the claim mechanism cannot know whether the provider actually executed the
request; that is exactly why §11/G below assigns `EffectExtent.UNKNOWN`, not a repeat call. Retry after
an `UNKNOWN` outcome is a **new**, separately authorized governed dispatch (a new `coordinate()`/new
`ExecutionId`), never an automatic resend inside the claimed invocation.

## G. EffectExtent for provider calls

The Gate-2 deterministic rule (`failure → EffectExtent.NONE`) does not transfer to a network call.
`OllamaModelAdapter`'s invocation is split into three observable phases, each with its own canonical
mapping, implemented as three distinct exception/outcome classes the Adapter raises/returns and
`invoke_effectful` (§F) maps explicitly — never inferred generically from "an exception occurred":

| Phase | Failure meaning | `EffectExtent` | `ErrorCategory` |
|---|---|---|---|
| Before the HTTP request is sent (config/validation error, connection refused before any bytes leave) | No possible provider-side effect | `NONE` | `DEPENDENCY_FAILURE` (connection) or `VALIDATION_ERROR` (bad request shape) |
| Request sent, no acknowledged response (timeout, connection dropped mid-flight, malformed/truncated response body) | Provider may or may not have processed it — genuinely unknown | `UNKNOWN` | `DEPENDENCY_FAILURE` |
| A complete, well-formed response is received | Provider effect is known | `COMPLETED` (chat/embed succeeded) or `NONE` (a clean provider-side error response, e.g. HTTP 404 model-missing, since the provider explicitly declares it did nothing) | `DEPENDENCY_FAILURE` (model missing/unavailable) or `VALIDATION_ERROR` (malformed provider payload — wrong vector count/dimension/non-finite numbers, per `EMBEDDING-CAPABILITY-DESIGN.md` §18) |

Dedicated tests assert the `UNKNOWN` case specifically (simulated connection-drop-mid-request via a
fake transport), not merely COMPLETED/NONE.

## H. Which capabilities remain deterministic/local

`document.chunking`, `document.parsing`, `retrieval.hybrid` (query embedding is the only Model call;
scoring/ranking itself is deterministic local computation), `retrieval.rerank` (v0.1 identity/truncation
reference implementation, no provider), ingestion composition (pure orchestration over the above plus
one embedding call per chunk batch).

## I. Which capabilities require actual provider invocation

`model.chat`, `model.embedding` (both via `OllamaModelAdapter`) — these are the only two effectful,
governed-dispatch-requiring capabilities in v0.1. `document.answering` composes retrieval + rerank +
one `model.chat` call; it does not add a second provider integration point.

## K. Final runnable CLI/example shape

New distribution `legoai-documind` (import root `documind_app`, or simply an `examples/documind/`
script package — decided in Phase J as a packaging detail, not an architecture question), depending on
`legoai` and `legoai-document`:


## L. Explicitly deferred from v0.1

- Postgres/pgvector retrieval backend (the original DocuMind evidence's choice) — v0.1 uses a
  self-contained local SQLite-backed store (§ storage decision below); Postgres remains a documented
  future Adapter, not required to prove the vertical slice.
- Cohere/any provider reranker — v0.1 ships the identity/truncation reference reranker only.
- Semantic Kernel / Microsoft Agent Framework Adapters.
- Any Agent/Workflow/Team/MCP/A2A construct.
- Multi-provider fallback (no silent Ollama-unavailable-so-use-something-else behavior).
- DEGRADED Catalog publication, untrusted Plugin isolation (ADR-012), production observability
  (ADR-013), distributed dispatch, crash/restart recovery, general resource-gating engine — all
  already-documented Gate-2 deferrals, unaffected by this milestone except where §F's replay fix and
  §45's resource-recording (ACTUAL-kind, non-enforcing) genuinely narrow the gap for the one new
  effectful capability.
- OCR / scanned-PDF support (parsing's existing, documented v1 limitation).

### Retrieval storage decision (task §20)

**Chosen: a self-contained local backend using stdlib `sqlite3`** (already an accepted, zero-new-
dependency technology in this codebase — F4's `SQLiteConfigurationStore` already uses it) for lexical
storage/BM25-style scoring via SQLite's built-in FTS5 virtual table, plus a pure-Python brute-force
cosine-similarity scan over stored embedding BLOBs for the vector half. This is correct and sufficient
to *prove* the vertical slice (small local document sets, no concurrent multi-process access) without
adding pgvector/Postgres/any vector-database dependency. Hybrid combination uses an explicit,
documented deterministic rule (Reciprocal Rank Fusion, `score = sum(1 / (k + rank))` per candidate
across the two ranked lists, `k = 60` — a well-known, simple, parameter-light RRF constant, stated
plainly as a choice, not a research claim). Tenant/document scoping is enforced by a mandatory
`tenant_id`/`document_id` column filter in every query, never a post-filter over unscoped results.
